## P-001 · PowerShell 写文件被编码安全策略拦截

- **现象**：一条 `Get-Content ... | ...` 命令被直接拦下，报错
  `[Craft] Blocked PowerShell command: Get-Content is reading file content without an explicit encoding...`
- **根因**：Windows 下 `Get-Content` 默认按 ANSI/GBK 解码，若再写回文件会把 UTF-8 中文写成乱码；工具侧对"读→写回"链路做了强制校验。
- **处理**：改用 `[IO.File]::ReadAllLines()` 或显式指定 `-Encoding utf8` / `-AsByteStream`。
- **经验**：**项目里所有中文文档都按 UTF-8 存**，Windows 批处理/PowerShell 脚本动文本时一律显式声明编码（这与项目内 `start.bat` 用 `chcp 65001` 是同一类问题的两个面）。

## P-002 · 安装 LangGraph 的连带影响

- **现象**：`pip install langgraph` 成功后，依赖清单出现两类变化：
  - **降级**：`websockets 17.1 → 16.1.1`；
  - **新增**：`httpx2 / httpcore2 / distro / jsonpatch / langchain-core / langsmith / ormsgpack / requests / tenacity / truststore / xxhash / zstandard` 等 20+ 包。
- **根因**：LangGraph 1.x 依赖 `langchain-core`，其传递依赖固定了较宽的版本区间，pip 选了能满足上游约束的组合。
- **为什么值得记**：项目此前**刻意不装 `openai` SDK**，理由正是"它会额外拖进 `httpx2 / httpcore2 / jiter / truststore`"（见 `requirements.txt` 注记与 ADR-012/015）——现在这俩被 LangGraph 带进来了，**这条注释必须同步改写**（阶段 7 文档同步项之一）。
- **处理**：先跑基线回归确认无行为影响（`303 passed in 64.22s` ✅）；`websockets` 仅被 uvicorn（`[standard]`）使用，而本项目用 **SSE 而非 WebSocket**，故实际影响面为零；后续在阶段 6 再做一次端到端确认。
- **经验**：**"刻意不装的依赖"要写清理由**（本项目做到了），但**引入新框架时要回头复查这些理由是否仍成立**——这就是一份好的依赖注释的价值。

## D-001 · 编排层有 13 项隐式状态（图化的真正障碍）

- **现象**：调研发现 `analysis_service.run_once()`（1533 行）的状态并不集中，典型的有：
  1. `EventSink` 把 SSE 推送绑在 `list.append` 副作用上；
  2. `llm_client._CLIENT` 模块级全局（测试靠 `set_llm()` 替换）；
  3. `sandbox_service._POOL` 进程级子进程池（跨请求常驻）；
  4. 超时常量要求"**调用时**读配置，禁止 import 期读"；
  5. `slot_service.FASTPATH_ENABLED` 模块开关；
  6. `calls` 累加器跨 slot / 生成 / 重写 / 解读共享；
  7. `AnalysisResult` 被就地改写（route / retries / sql / events…）；
  8. 重写环内部用 while 里的局部变量承载条件分支；
  9. ORM 会话生命周期（session 关闭后仍读 `conversation.slot_json`、`report.quality_json`）；
  10. `conversation is None` 藏在异常处理里充当路由条件；
  11. 落库副作用回写会话标题/消息数；
  12. 测试用 `ScriptedLLM._counters` 依赖调用顺序；
  13. DB 引擎 `@lru_cache` 进程级缓存。
- **处理策略**：不重写链路，改为 **"图包裹（strangler）"**——
  - 可序列化的纯数据进 **state**；
  - 运行时依赖（`llm` / `emit` / ORM 对象）走 `RunnableConfig.configurable`；
  - 节点薄封装既有函数，先保证行为一致，再逐步把条件环搬到图的边上。
- **经验**：**"能不能图化"不取决于框架，取决于状态是否收敛**。这份清单也是"显式 async 编排 vs 状态图"权衡的真实依据（ADR-017 当初的理由依然成立，只是现在为了技术栈/简历选择接入）。

## D-002 · 事件推送与图化的冲突

- **现象**：现有实现靠 `EventSink`（`list` 子类覆盖 `append`）实现「事件产生即推送」（首字 **10–16ms**，改造前是 5,927ms）。
- **难点**：若改用"图跑完再回放事件"，首字会退化为整条链路耗时（ADR-018 明确反对）。
- **处理方向**：节点内通过 `langgraph.config.get_stream_writer()` 写 `stream_mode="custom"` 通道，保持"即时推送"语义；`emit=None` 的非 SSE 调用方行为不变。
- **验收**：改造后 `sse_probe.py` 首字仍为毫秒级（阶段 6 度量）。

## D-003 · 超时常量不能在 import 期读取

- **现象**：代码注释明确写着：若在模块 import 期读 `get_settings()`，**35 个测试会连锁失败**。
- **难点**：图模块（`graph.py`）天然倾向在模块顶层构建并编译图，容易顺手把配置/超时读在顶层。
- **处理方向**：图**按需构建**（`build_graph()` + `lru_cache` 按配置指纹缓存），超时值仍在**调用时**读取（沿用 `_narrative_timeout()` 的写法）。
- **经验**：**"顶层副作用"是 Python 服务里最常见的隐性耦合**——写框架代码时尤其要克制。

## D-004 · Checkpointer 自动建表 与 「DDL 唯一事实源」纪律冲突

- **现象**：`langgraph-checkpoint-sqlite` 的 `SqliteSaver.setup()` 会自行创建 checkpoint 表；
  而本项目的纪律是：**表结构唯一事实源在 `01.code/scripts/sql/*.sql`**，由 `03_init_db.py` 建库（`app/db/models/base.py` 明确禁止 `create_all()`）。
- **难点**：让框架自己建表 = 绕开纪律；手工纳管 = 要抄它的 DDL 并跟随版本升级维护。
- **处理方向**：**选择手工纳管**——把 checkpoint 的 DDL 抄进 `scripts/sql/`，随 `03_init_db.py` 一起建；同时在文档里说明"由 SqliteSaver 兼容该 schema，版本升级时需核对"。
- **经验**：**引入框架时，先问"它是否绕开了项目的既有约束"**；宁可多写几行 DDL，也别破坏"单一事实源"——这正是数据库文档能保持可信的原因。

## P-003 · 适配层"单向映射"：图内数据对、返回对象却为空

- **现象**：等价性测试报 `字段不一致 row_count: graph=0 legacy=1`，但 `status`、`slot`、事件序列都正常。
- **根因**：`adapters.state_to_result()` 只映射了"十几个字段"里的前 8 个（record_code / status / route / retries …），**漏了表格、解读、错误码**等。图内部（state）一直是正确的，但运行器最后用它构造返回对象时丢了数据 → 调用方（端点 / 评测 / 重跑）拿到空表格。
- **处理**：把 `state_to_result()` 补成与 `result_to_state()` **对称的完整映射**，并在注释里写明"这正是等价性测试抓出的第一个真问题"。
- **经验**：**双向适配层必须成对维护**——只测"跑通了没"发现不了这类问题，**必须比对"两边对象的字段是否一致"**。等价性测试的价值在此。

## P-004 · 图的默认状态 `running` 不是合法留痕状态

- **现象**：图跑通后返回 `status='running'`；更严重的是 `analyses` 插入报
  `sqlite3.IntegrityError: CHECK constraint failed: status IN ('success','failed')`。
- **根因**：`DEFAULT_STATE` 把 `status` 设为过程态 `running`（概念上合理），但**留痕表只接受 `success/failed`**；而图的"最后一步"（persist）并没有把状态收敛。
- **处理**：在 persist 节点显式收敛——`status in (None, "running") → "success"`，其余原样保留（failed 等）。
- **经验**：**"过程态"与"持久化态"要分开**。有状态机的系统里，一定要有一处明确的"终点收敛"，否则默认值会直接漏到数据库约束上。

## P-005 · 澄清轮的 `status` 语义：严格对齐 > 改得更合理

- **现象**：我把澄清轮的状态设成 `clarify`（读起来更合理），但既有实现返回的是 `success`，导致等价性断言失败。

## P-015 · `.ps1` 存成 UTF-8 无 BOM → PowerShell 5.1 解析崩溃

- **现象**：重建的 `stop.ps1` 跑起来报一堆**莫名其妙的语法错**：
  `Unexpected token 'ParentProcessId=$ProcessId")) {'`、`Missing closing ')' in expression`、
  `Missing closing '}'` —— 但对着源码看，括号明明都是配平的。
- **根因**：文件是 **UTF-8 无 BOM**，而 Windows PowerShell 5.1 对无 BOM 文件**按系统 ANSI（GBK）解码** →
  中文注释被解成乱码，其中某些字节序列会**吃掉引号/括号**，于是解析器报"括号缺失"。
  （同一个坑在更早的 `_test_bats.ps1` 上已经踩过一次，这次因为脚本是新写的又踩回来了。）
- **处理**：写入时用 **UTF-8 with BOM**（`New-Object System.Text.UTF8Encoding($true)`），
  并加一道**语法自检**：
  ```powershell
  $err=$null
  $null=[System.Management.Automation.Language.Parser]::ParseFile($path,[ref]$null,[ref]$err)
  @($err).Count   # 必须为 0
  ```
  自检后 `start.ps1` / `stop.ps1` 均为 **0 语法错误** ✓。
- **经验**：**中文 + PowerShell 脚本 + 无 BOM = 定时炸弹**。要么写纯 ASCII（我最初的 `stop.ps1` 就是纯 ASCII，
  所以一直没出事），要么强制带 BOM；并且**改完脚本立刻做语法自检**，比跑一遍再猜错在哪快得多。

## P-016 · `uvicorn --reload` 的父子结构：杀掉监听进程后端口"复活"

- **现象**：`stop.bat` 的日志里明明写着 `[kill] PID 59188 port 8000 -> backend`，
  可 1 秒后检查端口，**8000 仍在监听**，并且最终提示"仍有端口在监听：8000"。
- **根因**：`uvicorn --reload` 采用「**监督进程（父）+ 工作子进程**」结构，**监听套接字在工作子进程手里**。
  只杀掉按端口找到的那个子进程，**监督进程会立刻把子进程重新拉起** → 表现为"杀不死"。
- **处理**：在按端口停止之后，再加一道**兜底清扫**：按命令行特征
  （`*uvicorn*app.main*` / 前端目录 + `vite`）把相关进程一并停掉，
  并**按 PID 升序处理**（父进程 PID 通常更小 → 先断掉"重新拉起"的源头）；
  仍然保留祖先链保护与进程名白名单，避免误杀终端/IDE。
- **一个环境性细节（值得记住）**：排查时发现占着 8000 的 PID 在
  `Get-CimInstance Win32_Process` 里**查不到**（名称、父进程、命令行全空）——
  那是**被外部工具"托管启动"的服务监督进程**（IDE/命令面板），属于它的作用域，脚本无权也不该去动。
  判定方法很简单：**能查到进程信息 = 自己启动的；查不到 = 外部托管的**。
- **经验**：**"进程杀了但端口还在"几乎总是"监督/守护进程又拉起来了"**。
  停服务要按"**父 → 子**"顺序或直接连监督进程一起停；只盯着端口持有者是不够的。

## P-017 · 残留错误字段让路由误判："重写成功后不执行，又进了重写环"

- **现象**：拆分后的等价性用例报 `字段不一致 route: graph='pandas' legacy='sql'`——
  图里第一次执行失败、**重写成功后并没有执行那条新 SQL**，而是直接换路 pandas，
  最终返回了脚本模型的兜底代码 `result = df.head(5)`；事件序列里也**多出一次 `code`**。
- **根因**：重写节点只更新了 `sql`，**上一次的 `last_error_code` 仍留在 state 里**；
  而 `route_after_guard` 用 `if state.get("last_error_code"): return "rewrite"` 判断"这一轮是否失败" →
  守卫一放行就被误判成"又失败了"，直接回到重写环；第二次进环时"重写额度"已用掉 → 走"换路"分支 → pandas。
- **处理**：给守卫节点加一个**本轮显式写入**的标志 `guard_blocked`（拦截 True / 放行 False），
  `route_after_guard` 只看它，不再看可能残留的 `last_error_code`。
- **经验**：**拿"错误字段是否为空"当路由条件，在重试环里天然不安全**——错误是历史，状态是当下。
  要让每个节点**显式声明本轮结论**，而不是让下游去猜一个会累积的字段。

## P-018 · pandas 分支的 SSE 事件顺序写反了

- **现象**：等价性用例在事件序列第 6 项报 `'status' != 'code'`（图与既有实现分叉）。
- **根因**：为了少写一行，我把 `status(executing)` 提到执行分支之前统一发；
  而既有实现的顺序是 **先 `code`（告诉前端"这次跑的是这段代码"）再 `status(executing)`**。
  SQL 路径因为 `code` 由守卫提前发出，看不出差别；pandas 路径就露馅了。
- **处理**：按分支分别发事件——SQL：守卫发 `code` → 执行发 `status`；pandas：执行发 `code` → 再发 `status`。
- **经验**：**SSE 的"事件顺序"是前端契约的一部分**（前端按顺序点亮五阶段时间线）。
  这类东西只能靠**逐事件比对**守住，代码 review 时极容易觉得"顺序无所谓"。

## P-021 · 检查点单例"绑定事件循环"

- **现象**：接入检查点后测试直接崩：

  换掉锁之后又冒出 `Called get_config outside of a runnable context`（编译产物跨循环复用的连锁反应）。

## P-022 · 另开连接清理检查点会 `database is locked`

- **现象**：删会话时清理检查点，用"独立短连接"实现会在控制面事务开着时撞
  `sqlite3.OperationalError: database is locked`。
- **根因**：控制面删除会话时正持有写事务；另开连接执行 DELETE 需要写锁 → 互相等待。
- **处理**：新增 `delete_threads_in_session(session, ids)`——**在调用方事务内**执行删除；
  同时保留 `delete_threads()`（独立短连接）供离线清理。删除失败只记日志、不阻断主流程。
- **经验**：**级联清理要和被清理的数据处在同一个事务里**——既避开锁冲突，也保证"要么都删、要么都不删"；
  这正是数据库设计文档"删除语义"章节要写清楚的东西。

## D-005 · 中断节点在恢复时会**整体重跑** → 副作用必须前置

- **风险**：若把"建澄清卡 + 落 messages×2 + 发 `clarify` 事件"直接写在调用 `interrupt()` 的节点里，
  用户回填后这些副作用会**再执行一遍**——历史里会出现两组相同的"用户问 + 澄清卡"消息，
  前端也会收到重复的 `clarify` 事件（还会重复调模型）。
- **根因**：LangGraph 的 HITL 语义是"**从被中断的节点重新执行**"：恢复时该节点从头跑，
  只有 `interrupt()` 那一行改为"返回恢复值"。也就是说，**`interrupt()` 之前的代码 = 会执行两次的代码**。
- **处理**：拆成两个节点——
  ① `clarify_card`：建卡 / 落库 / 发事件（**只执行一次**，其状态写入被检查点保存）；
  ② `clarify_wait`：只做 `interrupt({...})` 与"把恢复值写回 state"。
- **经验**：写 HITL 时先问一句"**这个节点恢复后会不会重跑？**"。
  凡不可重复的副作用（落库、发事件、调模型、扣额度），一律放到**中断之前的前置节点**里。

## P-023 · 条件边的两条"名字约定"

- **现象（两连击）**：
  ① 把澄清分支映射写成 `{NODE_CLARIFY_CARD: NODE_CLARIFY_CARD}`，而路由函数返回 `"clarify"`
     → 运行时 `KeyError: 'clarify'`；
  ② 改成 `{"clarify": NODE_CLARIFY_CARD}`（key 与返回值对齐）后运行正常，
     但 `graph_mermaid()` 导出的图里**少了 `extract_slot → clarify_card` 这条边**（其它条件边都在）。
- **根因**：`add_conditional_edges(source, route_fn, mapping)` 的 **mapping key 必须等于 `route_fn` 的返回值**；
  而 Mermaid 导出是**按节点名**画条件边的——返回值不是节点名时，那条边不会出现。
- **处理**：让路由函数**直接返回节点名**（`"clarify_card"` / `"generate"`），映射也写成节点名到节点名。
- **经验**：**"运行通过"不等于"结构正确"**。图是要当架构图给人看的（阶段 5），
  所以除了"能跑"，还要**校验导出的边是否齐全**——这次正是结构断言把问题挡住的。

## P-024 · 异常分支里 `final` 可能未绑定

- **现象**：`UnboundLocalError: cannot access local variable 'final'`——`_stream()` 抛异常时它还没被赋值，
  而 except 分支要拿它去落失败留痕。
- **处理**：进入 `try` 之前先 `final: dict = {}` / `events: list = []`（运行器两处都补上）。
- **经验**：**"try 里赋值的变量，except 里不能直接用"**——这类错误在正常路径上永远不暴露，
  只有"第一刀就失败"（例如模型输出不可解析）时才炸；**异常分支要用异常路径去测**。

## P-025 · 补发的事件要"推送 + 入表"两不误

- **现象**：澄清轮的 `meta` / `done` 已推给 SSE 回调，但 `result.events` 里没有这两个事件
  → 等价性用例报"事件序列差两个"（非 SSE 调用方读的正是 `result.events`）。
- **根因**：运行器补发时只调了 `emit(...)`，忘了同时 `events.append(...)`。
- **处理**：补发统一走"先 append、再 emit"（同一份对象）。
- **经验**：**"推送通道"与"返回对象"是两套消费者**（前端 vs 评测/重跑），任何事件都要**同时**照顾到——
  这也是本项目 `EventSink(emit)` 设计一开始就规避的问题。

## P-026 · 文档头部版本号落后于变更记录

- **现象**：给《系统架构设计文档》加新版本前先核对现状，发现**头部写 `v1.0.13`**，
  而附录 B 变更记录里**最新的一条是 v1.0.14**（2026-09-19：守卫第 6 条规则 + 结果形态自检）。
  也就是 v1.0.14 那次改动**更新了变更记录、忘了改头部**。
- **影响**：读者按头部判断"文档停在 v1.0.13"，会低估文档的追平程度；
  更糟的是——**下一次改文档的人可能把新版本号也写成 v1.0.14**，造成两条不同内容同号。
- **处理**：本次直接落 **v1.0.15**（跳开冲突号），并把正文里引用旧版本号的注记（4.2 的"v1.0.14 如实记录"）一并更正；
  附录 B 的排序不整齐（v1.0.14 插在 v1.0.13 之上、v1.0.0 在最上）**不重排**——避免制造无意义的 diff。
- **经验**：**"版本号"要有单一来源**。最省事的做法是：**每次改文档先看变更记录的最后一条，再决定新号**；
  提交前自查"头部版本 = 变更记录最新条目"。这也正是本项目"表结构唯一事实源""DDL 唯一事实源"
  那套纪律在文档侧的翻版：**同一个事实只允许有一处权威**。

## P-027 · `Start-Process -ArgumentList` 会按空格拆参数

- **现象**：跑评测批次时给 `--name '编排迁移验证·langgraph（selfcheck 120 题）'`，
  脚本立刻报 `eval_run.py: error: unrecognized arguments: 120 题）`——**批次根本没起来**。
- **根因**：PowerShell 的 `Start-Process -ArgumentList <数组>` 会把数组元素**用空格拼成命令行**，
  且**不会为含空格的元素自动加引号**；于是 `--name` 只吃到 `编排迁移验证·langgraph（selfcheck`，
  后面 `120 题）` 变成了位置参数 → argparse 直接拒绝。
- **处理**：把备注名改成**不含空格**（`编排迁移验证-langgraph-selfcheck120`）即刻成功。
  需要保留空格时，应自己把引号写进参数里（`'"带 空格的名"'`）。
- **经验**：**PowerShell 传参给外部程序时，"引号"要自己负责**（同类坑见 `P-009`：`cmd` 里 `set VAR=` 是删变量）。
  更稳妥的姿势是：① 备注名、路径尽量不含空格；② 复杂参数改用**写 .cmd/.ps1 脚本再执行**；
  ③ 长任务一律**重定向到日志文件**再读（本项目的工具脚本 docs 就是这么用的）。

## P-028 · 自检批次的 `set_llm` 注入会**残留在进程里**（"real 模式"实际跑了脚本模型）

- **现象**：按需求方指示发起 **120 题真实评测**（`--impl real`，打 8001）→ **12 秒跑完**、正确率 **0.8%** ❗；
  查库发现该批次 `llm_calls.model_name = **scripted-qwen**`（1,037,132 记账 tokens、**真实额度 0**）；
  而同一进程的 `/system/health` 却报 `configured=True`**且** `impl=scripted` ——**两边不一致，正是线索**。
- **根因**：`llm_client.get_llm()` 的 `_CLIENT` 是**进程级缓存**、且**只在为 `None` 时才创建**；
  而 `eval_service` 在 **selfcheck** 模式下会**逐题 `set_llm(ScriptedLLM(...))` 注入 gold 回放模型**、批次结束时还原。
  一旦注入后**未被还原**（批次被中断 / 多批次共用进程 / 并发跑），脚本模型就**留在进程里**，
  之后所有请求（含"real 模式"评测）都继续用它 —— 而 `configured` 读的是**配置**（真 Key），于是出现
  "配置是真的、跑的是假的"这种最难察觉的错。
- **处理**：① 改打**自己可控的进程**（换空闲端口 8003 起独立实例）；
  ② 加**飞行前门禁**：`impl` 必须等于真实客户端名（`kuaipao`）+ `configured=True` + `orchestrator=langgraph`，否则**中止**；
  ③ 口径写进文档：原提醒"两个自检批次不要并发跑"要**扩展为"自检批次与真实批次也不要共用同一进程"**。
- **经验**：**"全局可变客户端"是测试便利与运行安全的冲突点**。进程级单例 + `set_llm` 注入 =
  只要**有一次没还原**，整个进程静默降级；**动手前必须验证"实际用的是哪个实现"**（本次靠 `impl` 字段一眼看穿），
  而不是只验证"跑通了"。

## P-029 · "重启没生效"，但健康检查是绿的

- **现象**：为保证配置新鲜，我停掉 8001 再用当前 `.env` **干净重启**，健康检查 `status=healthy` ✓……
  但随后 `impl=scripted` ❗，而我新起的实例**日志文件是空的**（根本没跑起来）。
- **根因**：8001 的持有者在 `Get-CimInstance` 里**查不到**（PID 31628，无名称、无命令行）——
  **外部工具（IDE / 命令面板）托管**的进程；我的实例因**端口被占绑定失败即刻退出**，
  而健康检查回答的是**那个托管进程**（它持有端口）。
- **处理**：改到**空闲端口 8003** 起自己的实例；验证时**同时核对两件事**——
  ① 进程归属（端口持有者能在进程表里查到名字/命令行 = 自己起的）；
  ② 关键字段（`impl` / `orchestrator` / `configured`），不只看 `healthy`。
- **经验**：与 `P-016` 同源（外部托管进程杀不掉），但这次多了一层：
  **"我的重启"可能静默失败，而健康检查会"替别人回答"**。
  凡"重启后验证"，都要能回答"**这是不是我这个进程**"（比对 PID / 启动时间 / 日志是否有输出）。

## P-030 · 长评测批次是"单进程内存态"：机器一停，120 题白跑一半（已救回）

- **现象**：新端点 120 题真实评测跑到 **102 条落库**时机器停止 → 回来时批次 `status` 卡在 `running`、
  `finished_at` 为空、8003 后端已不在监听；**聚合指标与报告全丢**（`result_json` 只在批次收尾时才写）。
- **根因**：评测批次在**单进程内存里**累积逐题明细，收尾时统一 `_aggregate()` + `_write_report()` 落库；
  进程一停（休眠 / 关机 / 被停），"跑过的东西"就只剩**逐题留痕**（`analyses` / `llm_calls`），聚合态并不存在。
- **处理**：新增 **`01.code/tools/eval_rebuild.py`**——按落库结果**本地重算**已完成题目的评分
  （复用 `eval_service` 的同一套判分函数，口径与在线同源），生成新批次并**补链** `llm_calls`，
  源批次如实标 `failed` 并写明中断原因；随后只**补跑剩余 19 题**（27.5 万 tokens），
  两段用 `eval_merge.py` 合并成 120 题成绩。**实测效果**：整批不必重跑（约 110 万）→ **省下 ≈82 万 tokens**，
  已跑的部分一条没丢。
- **经验**：① **长批次按 20–30 题分批跑、再合并**（工具本就支持），单批越长"中断损失"越大；
  ② 评测的服务端进程必须**自己可控、且机器不休眠**（本次中断正发生在"以为它在跑"的时候）；
  ③ **逐题落库 + 判分函数可复用**是这套评测设计里最值钱的一条——正因为判分与在线同源，才敢本地重算。
- **2026-10-14 二次复现（同一天内第二次）**：单批 120 题（`run_20261014_16`）跑到 **64/120** 时，
  **8003 后端与评测进程一起消失**（16:41 之后再无活动，端口都不再监听）→ 用同一套打法抢救：
  `eval_rebuild.py` 重建前 64 题评分（0 额度）+ **按 28 题分批**补跑剩余 56 题。
  **教训升级**：`P-030` 当时写的"长批次按 20–30 题分批"**没有执行**（这次又跑了单批 120）→
  已按 28 题分批执行；**代价**：二次中断浪费了 64 题的重跑机会（若不中断，这 64 题不必重算耗时）。
  ⇒ 结论写死：**评测发起一律 `--codes` 分批（≤30 题/批）+ `eval_merge.py` 合并**，不再跑单批 120。

## P-031 · 聚合端点在同一批次里返回**不同的模型标识**

- **现象**：核对新端点 120 题的 token 时两个口径对不上——按 `model_name='deepseek-v4.1-flash' + 日期`
  统计得 **827,065**；按**批次关联**（`llm_calls.eval_run_id`）统计得 **1,088,865**，差了 26 万 ❗
- **根因**：聚合端点会在响应里返回**不同的 served model 名**——同一批内实测出现
  `deepseek-v4.1-flash`（214 次）/ `cb/deepseek-v4.1-flash`（62 次）/ `deepseek-v4-1-flash`（11 次）/
  `P2deepseek-v4.1-flash`（3 次）。本项目把响应里的模型名记进 `llm_calls.model_name` →
  **凡按字符串分组的统计全部漏计**（本次漏掉 90 次调用 ≈ 26 万 tokens）。
- **处理**：① 统计口径改为**批次关联**（`llm_calls.eval_run_id`，评测服务收尾时回填）或"日期 + 链路"；
  ② 结论写进《测试报告》12.3 与《配套变更》§9，避免日后有人拿"按模型名"的数字下结论；
  ③ `analyses.llm_model` 记的是**本项目配置的模型名**，与端点的 served 名分开看待。
- **经验**：**"模型名"不是可靠的统计主键**——聚合/代理端点随时可能改 served 名（甚至同批内不一致）。
  凡是成本 / 用量 / 性能统计，都要挂在自己可控的标识上（批次号、会话号、request_id），**别挂在外部返回值上**。

## P-033 · `E_EVAL_RUNNER: Called get_config outside of a runnable context`（偶发、会静默丢题）

- **现象**：评测批次里偶发 0 秒失败：`status=failed`、`error_code=E_EVAL_RUNNER`，
  题面与模型都无关（`run_20261014_03` 的 q030、`run_20261014_04` 的 q051 各命中一次）；
  昨天 120 题批次**零命中**。
- **影响**：批次会**静默丢题**——若不看 `error_code`，会被误读成"模型答错"。
- **根因（后端日志的两段堆栈定案）**：不是缓存/循环问题，而是**异常处理路径自己踩了坑**：

  ```
  gen 返回空内容 → BizError(模型输出为空)
    → run_once_graph 的失败兜底 _persist_failure()
      → node_persist() 里 ctx.emit_event(error 事件)
        → adapters.py:68 stream_writer(event)
          → langgraph: get_config() ❌ Called get_config outside of a runnable context
  ```

  custom-stream 写入器**只在图运行上下文内可调用**（内部要读 LangGraph 的 config 定位检查点命名空间），
  而失败兜底恰恰是在**图流已经结束之后**执行的 → 必然抛；于是"失败留痕"自己把题目又打了一次 0 秒失败。
- **处理**：`GraphContext.emit_event()` 调用写入器时**兜住 `RuntimeError`**，一旦发现"图外"就把该写入器
  **作废**并回落到既有 SSE 回调（事件该发还是发）。配套 4 条回归用例
  （`tests/test_generate_robustness.py`：空输出重发 / 生成软超时 / 写入器失效回落 / 正常路径仍走流）。
  **复测（`run_20261014_05`，同样 3 题）：`E_EVAL_RUNNER` 零命中，3 题全部干净收尾** ✓。
- **经验**：① **"失败路径"必须当成一等公民来测**——本次错误只在"模型返回空"时才暴露，
  正常路径永远测不到；② **框架的"上下文内可用"对象不能跨生命周期使用**（图外的流写入器、
  关闭后的连接、跨循环的锁，本质是同一类）；③ 评测里 **"0 秒失败"要单独归因**，
  否则会把它算成模型能力问题（本次正是靠 `diff_detail` 里的异常文本才发现）。

## P-034 · 千分位被"未授权数字"检测误判为**编造**

- **现象**：新增的「自动摘要」用千分位展示（`1,200`）时立刻触发误报——
  `解读中出现未在查询结果里的数字（200）`（会写审计告警、也在界面上多一条提示）。
- **根因**：`_NUMBER_RE = -?\d+(?:\.\d+)?` 遇到 `1,234` 会拆成 `1` 与 `234`，后者 ≥ `_STRAY_NUMBER_MIN=100`
  → 被判成"表外数字"。更根本的问题是**两处口径不一致**：允许值侧走 `_numbers_in()`（会做归一化），
  而**解读文本侧直接用了正则**（`_unauthorized_numbers()` 第 1517 行）。
  **对真实模型解读同样成立**：模型写"合计 1,234 kWh"也会被误判为编造。
- **处理**：定义 `_THOUSANDS_RE = (?<=\d),(?=\d{3}(?!\d))`，在 `_numbers_in()` 与
  `_unauthorized_numbers()` 的**文本提取处都先归一**；加两条用例守两侧
  （`1,200.5` 不再误报 ✓；真正的表外数字 `25,979` 仍被抓出 ✓ —— 证明没有放宽红线）。
- **经验**：**同一个判定要在所有入口调用同一个函数**——本项目里"未授权数字"有"允许值侧"与"文本侧"两条路径，
  只改一边就会出现"**自己写的东西被自己判违规**"。凡是"多入口同一判定"，都应抽成一个函数供各处复用。

## P-035 · 为提速去掉 `enable_thinking=false`，生成质量掉了 **17 个百分点**

- **现象**：依据"探针显示发它更慢（4.88s vs 2.42s）"的判断去掉该开关后，**120 题全量从 118/120 掉到 101/120**
  （84.2%）：**18 题由对变错**，且全是**生成质量**问题——`empty_result` 9 题（SQL 把数据过滤空）、
  `column_count_mismatch` 9 题（多吐列；q119 反而**丢了 `GROUP BY`**；q097 自己算比率）。
- **根因**：该端点把"关闭思考"翻译成**额外注入一段系统提示**（同一请求 `prompt_tokens` 200 → 528，实测）。
  那段提示让模型**更守 JSON、更照题面** —— 对"解读"只是拖慢（写一小段文字，慢一点无所谓），
  对"生成"却是**服从性保障**：去掉后模型变"过度热心"（多给一点、顺手多算一点），
  而这些在"与 gold 严格对齐"的判分口径下**全算错**。
- **处理**：① **恢复该开关**；② `LLM_MAX_TOKENS` 4096 → **8192**（残 6 题里 q115 的生成
  `completion_tokens=4095` **正好顶上 4096 被截断**，JSON 不完整 → 列数/取值错）；③ 解读改用**独立档**
  `LLM_MODEL_NARRATIVE`（此前它与 slot 共用轻量档，换解读模型等于换 slot 模型）。
  **A/B 复测：18 题 15 题恢复；合并口径 116/120 = 96.7%**（详见 `提速实验-20261014.md` §6）。
- **经验**：① **同一个参数对不同用途可能反向**——"参数无副作用"必须**按用途分别验证**
  （本次只测了解读形态就改了全局，代价 17 个百分点）；② **小样本探针不能替代全量评测**：
  5 题小批当时"更快更稳"、毫无异样，只有 120 题全量才照得出来；
  ③ **配置分档要按用途切**，复用别人的旋钮会让排查多一个无关变量。

## P-036 · 失败留痕撞 CHECK 约束：`route` 写了空串

- **现象**：q119 第二轮（"只看工作日。"）在评测里表现为"**没有调用记录、却是空结果**"，看起来像模型答错；
  后端日志里是：
  ```
  sqlite3.IntegrityError: CHECK constraint failed: route IS NULL OR route IN ('sql', 'pandas')
  [参数: (..., '只看工作日。', '{}', '', ..., 'failed', 'E_LLM', '槽位解析超时（超过 12s）…')]
  ```
- **根因**：`analyses.route` 上有 CHECK 约束（只允许 NULL / `sql` / `pandas`），
  而 `AnalysisResult.route` 的字段默认值是**空串**——"还没走到生成"就失败的路径（如 slot 超时）
  会把 `''` 原样落库 → **INSERT 被拒** → 失败留痕丢失、异常继续上抛。
- **处理**：落库前归一化 —— `route=result.route if result.route in ("sql","pandas") else None`；
  新增用例直接**查库**断言（接口层会把 NULL 渲染成默认值，验不出真伪）。
- **经验**：**"默认值"要和数据库约束对齐**——空串与 NULL 在 SQLite 里是两个不同的值，
  而业务上它们往往是"同一个意思"（此处都是"还没选路"）。凡是往受约束的列里写值，
  都要在**写入前**归一化，别指望约束帮你兜（它只会让整条 INSERT 失败，连留痕一起丢）。

## P-037 · 追问轮 slot 超时被判"认不出指标"

- **现象**：多轮题的第二轮（如「只看工作日。」）在**慢时段**（slot 调用 >12s）整题失败：
  `E_LLM：槽位解析超时（超过 12s），且无法从问题中识别指标`。
- **根因**：超时兜底 `fallback_slot()` 一律要求**本轮问句里能认出指标**；
  而追问轮常常只说"过滤/换维度"（"只看工作日。""按时段再看一遍"），指标要从会话继承——
  这与多轮语义（"未提及即继承"）相悖。
- **处理**：兜底新增 `allow_inherit` —— **本轮认不出、但会话已有指标**时，返回"指标留空"的增量，
  由 `merge_slot()` 继承；只有"本轮认不出 **且** 会话也没有"才如实失败（**不编造**）。
  与 `P-036` 一并修复后，q115/q119 两道多轮题在真实模型下**均通过**（生成与 gold 逐字段一致）。
- **经验**：**"规则兜底"要与"多轮语义"对齐**——LLM 路径天然会继承会话条件，
  而规则路径很容易写成"只看本轮问句"，于是**同一个语义在两条路径上不一致**；
  兜底路径越多，这种"两条路径语义漂移"越要专门测（本项目已有 9 条等价性用例守着图/legacy 两条链，
  但"规则 vs LLM"这条缝是本次才补上的）。

## P-038 · 端点慢时段撞上"生成 25s / 槽位 12s"软超时 → `E_LLM` 失败（看着像模型答错）

- **现象**：2026-10-14 16:30–16:41 的单批 120 题里，**连续多题**以 `E_LLM` 失败、耗时集中在 **33–37 s**
  （如 a_003001/003002/003003），另有 1 题 `E_INTERNAL`（9.2 s）；同批 avg **24.0 s/题**，
  而当天上午同配置只要 ~11.7–22 s/题。
- **根因**：**端点进入慢时段**（单次生成 15–25 s+）→ 撞上我们自己设的**软超时**：
  `GENERATE_TIMEOUT_SECONDS=25`（超时即 `E_LLM` 失败，生成不能像解读那样"跳过"）+ `SLOT_TIMEOUT_SECONDS=12`。
  这是"**上限策略在慢时段的副作用**"，**不是模型能力问题**。
- **影响**：慢时段批次的正确率会被**显著低估**——本批前 64 题重建为 **43/64 = 67.2%**，
  而同一配置在快时段（上午各小批）是 **96.7% 量级**。⇒ **引用成绩必须注明时段**。
- **处置（已定口径，2026-10-14）**：选 ② **放宽上限** —— `GENERATE_TIMEOUT_SECONDS` 25 → **40 s**（`.env`）、
  `SLOT_TIMEOUT_SECONDS` 12 → **20 s**（代码常量）；已重启生效 + 文档/演示清单同步。
  取舍依据：**上限只在慢时段被触发、一触发就是整题失败**，而快时段"零成本"（上限是天花板）；
  慢时段"多等十几秒拿到答案"优于"25 秒报错、什么都没有"。（若演示更看重"快失败"，把 40 改回 25 即可。）
- **追加（2026-10-16）**：慢时段重现 —— 20 题现状读数里 **5/23 条记录撞 40 s 上限**（47.9–53.4 s，`E_LLM 生成超时`），
  读数被压到 **15/20 = 75%**（未超时的 15 题 15/15 全对）；**上限再提到 60 s**（`.env`，代码默认仍 25）后
  同 5 题补跑 **5/5 全对**（其中 q113 用 52.6 s，确实靠新上限才过；其余 4 题窗口回暖只需 12.8–14.9 s）。
  ⇒ **上限提额依旧是"有限保险"**：治本方向是**减少单题串行调用数 / 提高端点稳定性**，而非无限抬上限（抬上限 = 伤 P95）。
  证据：`02.data/tmp/_cur20_why.txt`、`_retry5_detail.txt`、测试报告 §9-1。
- **经验**：**超时值必须与"端点的时段波动"一起看**——同一配置在快/慢时段的表现差异
  （11.7 s 正常 ↔ 37 s 失败）**比配置本身的影响还大**；评测报告里必须带"时段"这一维，
  否则会把"端点今天慢"误读成"改动把质量改坏了"（今天已经发生过一次同类误读，见 `P-035`）。
- **实证（同日）**：单批 120 题首轮有 **19 题**以 `E_LLM`/`E_INTERNAL` 失败（33–37 s 撞 25 s 上限）；
  把这 19 题**重跑一遍**（同配置、无任何改动）→ **18 题通过（94.7%）** ⇒ 失败原因是"**时段**"，不是能力。
  这条实测同时也说明：**评测的"重试一次"应当是默认动作**（尤其对 `E_LLM` 语义的失败）。

## P-039 · 端点返回**非 JSON 正文** → `JSONDecodeError` 裸穿 → `E_INTERNAL`

- **现象**：单批 120 题里有 3 题以 `E_INTERNAL` 失败，耗时仅 **2.8 s / 9.2 s**（远快于超时失败），
  后端日志里的真实异常是
  `json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)`，
  调用栈停在 `app/core/llm_client.py` 的 `body = response.json()`。
- **根因**：端点抖动时会**在 2xx 下返回非 JSON 正文**（空响应体 / 网关 HTML 错误页）——
  旧代码直接 `response.json()`，`JSONDecodeError` **裸穿到编排层**，被兜成 `E_INTERNAL`。
  后果有二：① **归因被误导**（看着像代码 bug 或模型问题，而不是"上游可重试的抖动"）；
  ② **一次抖动 = 整题失败**（本该按 `E_LLM` 语义重试或至少如实说明）。
- **处理**：`llm_client` 里给 `response.json()` 加兜底 —— 捕获 `ValueError` 后抛
  `BizError(502, E_LLM, "端点返回了非 JSON 响应（HTTP …，正文 N 字符）", {...body_head...})`；
  新增回归用例（`tests/test_llm_provider.py`：2xx + 非 JSON → 必须 `E_LLM`、不得 `E_INTERNAL`）→ 全量 **340 passed**。
- **经验**：**"解析响应"是外部边界，必须当成不可信输入**——`response.json()` 这类"看起来不会失败"的调用，
  正是失败时最难归因的地方。凡是"边界解析"，都要显式兜底并**映射到项目自己的错误语义**（此处：可重试的 `E_LLM`），
  而不是让它以"内部错误"的形态出现。
