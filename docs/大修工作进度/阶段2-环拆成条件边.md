## 1 拆分结果

```
generate ─┬─(sql)──→ guard ─┬─(被拦截)→ rewrite ─┬─(重写/换路)→ guard | execute
          └─(pandas)→ execute ─┬─(成功·pandas)→ publish_table → chart → narrate → persist → END
                               ├─(成功·sql)──→ shape_check ─┬─(形态不对)→ rewrite
                               │                            └─(形态 OK)→ publish_table
                               └─(执行失败)──→ rewrite ─┬─(额度用尽)→ persist(failed) → END
                                                       └─(重写/换路)→ guard | execute
```

| 新节点 | 对应既有实现 | 语义 |
| --- | --- | --- |
| `generate` | `run_once` 380–403 | 首次生成，模型自报 route |
| `guard` | `_ga` 1045–1069 | SQL 守卫；**拦截也照发 `code` 事件**（前端能看到被拦的 SQL） |
| `execute` | `_ga` 1070–1108 | 只读执行 / pandas 沙箱 |
| `shape_check` | `_ga` 1075–1084 | 三类形态自检（**仅 SQL 路径**） |
| `publish_table` | `run_once` 423–428 | 形态过关才发 `table` 事件 |
| `rewrite` | `_ga` 1110–1198 | 带错误重写一次 → 换路 pandas 一次 → 额度用尽如实失败 |

**三条原语义逐条保留**（验收点）：`_NO_RETRY_CODES` 不重写；**安全拦截仍重写一次但不换路**；
生成调用总量 ≤3（首次 + 重写 + 换路）。

## 3 拆分过程中抓出的 3 个真 bug（都已修 + 已记档）

| 编号 | 现象 | 根因 |
| --- | --- | --- |
| `P-017` | 重写成功后**不执行就又进重写环**，最终变成"换路 pandas"（与 legacy 分叉） | 重写只更新了 `sql`，**旧的 `last_error_code` 还在 state 里**，`route_after_guard` 拿它当判断依据 → 误判"又失败"。改用守卫**本轮显式写入**的 `guard_blocked` |
| `P-018` | pandas 分支事件顺序与既有实现相反（`status` 在前、`code` 在后） | 我把 `status(executing)` 提到分支外统一发；既有实现是 **`code` → `status`** |
| `P-019` | 形态自检用例怎么都不触发（`row_count` 恒为 0） | 测试库里**预置报表只有元数据、物理表是空的** → 必须用"上传的真实数据表"才能观察到行数类判定 |

> 这三个都是"**只有做逐字段/逐事件比对才会暴露**"的问题——再次印证等价性测试的价值：
> 光看"跑通了"是发现不了的。
