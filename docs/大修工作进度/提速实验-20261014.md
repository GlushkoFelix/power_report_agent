## 2 三处真因（都有真实探针数据）

### A. `enable_thinking=false` 在本端点**反噬**（真因之首）

| 探针组合（同模型同提示词） | 平均 | 最慢 | completion | JSON 解析 |
| --- | --- | --- | --- | --- |
| 短 prompt · 裸调用 | **1.67 s** | 2.97 | — | — |
| 短 prompt · **+该开关** | 2.50 s | 2.58 | — | prompt **凭空 200 → 528 token** |
| 解读形态（真实提示词）· **+该开关** | 6.03 / 8.19 s | — | 628 / 1061 | **失败 / 失败** |
| 解读形态 · **不发该开关** | 6.95 / 9.53 s | — | 548 / 1020 | **失败 / 失败** |
| 解读形态 · 不发该开关 + `max_tokens=512` | **1.19 s** | 5.08 | 93 | **成功**（另一轮 0 字符） |

- 2026-10-13 的结论"该参数被端点接受但无副作用"**是错的**：当时只用 `max_tokens=8` 的极短探针，量太小看不出差别。
- 该端点收到"关闭思考"后，会**另行注入约 328 token 的系统提示**，并让"思考"继续抢占输出额度。
- ⇒ 结论：**不再发送该字段**（`.env` 已注释；`.env.example` 同步）。

### B. 端点对**同一提示词**的行为会**逐日漂移**（这是"空解读"的来源）

| 批次（同模型、同提示词、prompt 长度一致） | narrative 平均耗时 | 平均 completion |
| --- | --- | --- |
| `run_20261013_05`（昨天 17:26，101 题） | 5,941 ms | **165** |
| `run_20261013_04`（昨天 20:36，19 题） | 5,030 ms | **223** |
| `run_20261014_02`（今天 09:43，2 题） | **18,121 ms** | **2,536** ❗ |
| `run_20261014_03`（今天 09:48，2 题） | **15,390 ms** | **1,945** ❗ |

今天上游会为解读请求产出 600–900 字符**散文**（JSON 解析失败 → `analyses.narrative` 为空 → 界面无解读），
token 全烧在"思考"里。**代码与提示词都没动过**——属聚合端点上游行为变化。
⇒ 对策：解读**换模型**（见 C）+ 超时回到 8 s **兜住坏时段**。

### D. 顺带澄清的两个"假象"

- **"换模型不提速"（E1 的中间结论）只在"整批换模型"意义上成立**：那次把 LIGHT 换成
  `deepseek-v4-flash-0731`（直连实测 **6.89 s**，比主力的 1.87 s 更慢）→ 自然更慢。
  **要按阶段挑模型**：生成用准的、解读用稳的。
- **"端点有 5–6 s 地板"也不成立**：同端点直连短调用 **1.67 s**；慢是**特定提示词 + 特定时段**的组合。

## 3 已按建议实施的三项修复（2026-10-14 下午）

### 3.1 修掉 `P-033`：事件推送的"图外调用"兜底

**根因（日志里的两段堆栈定了案）**：

```
gen 返回空内容 → BizError(模型输出为空)
  → run_once_graph 的失败兜底 _persist_failure()
    → node_persist() 里 ctx.emit_event(error 事件)
      → adapters.py:68 stream_writer(event)
        → langgraph: get_config() ❌ Called get_config outside of a runnable context
```

即：**图已经结束之后**还想往图的 custom stream 里写事件 —— 写入器内部要读 LangGraph 的 config 来定位检查点命名空间，
必然会抛。后果是"失败留痕"自己把题目打成 `E_EVAL_RUNNER` **0 秒失败**（看起来像模型答错）。

**修法**（`agent/adapters.py::GraphContext.emit_event`）：调用写入器时**兜住 `RuntimeError`**，
一旦发现"图外"，就把该写入器**作废**并回落到既有 SSE 回调 —— 事件该发还是发，进程不被带崩。

### 3.2 生成阶段：**软超时 + 空输出重发一次**

- 新增 `GENERATE_TIMEOUT_SECONDS`（默认 **25 s**）与 `analysis_service._chat_generate()`：
  生成不能像解读那样"跳过"，超时按 **`E_LLM` 失败**如实留痕（长尾观测值：53.9 s）；
- **空输出重发**：该端点会偶发"思考吃光输出额度 → content 为空"，空输出不含任何语义，
  **重发同样的请求**既安全又能救回整题；返回"实际发生的调用序列"，两次调用**逐次计费、逐次留痕**。
- 接线：`nodes/execution.py::node_generate`（图路径）与 `analysis_service`（legacy 路径）两处同源。

### 3.3 解读提速：**不采用"更短解读指令"**（数据驱动否决）

| 解读指令（同一份真实提示词，glm-5.3-flash，各 2 次） | 平均 | completion | 正文 | JSON |
| --- | --- | --- | --- | --- |
| 现行（≤200 字 / 2–4 个数字） | 5.96 s | 84 / 434 | 168 / 166 字 | 2/2 |
| 收紧（≤60 字 / 1–2 个数字） | 4.74 s | 210 / 65 | 112 / 131 字 | 2/2 |
| 折中（≤100 字 / 2–4 个数字） | 7.57 s | 361 / 65 | 116 / 130 字 | 2/2 |

**差异落在噪声内**（同一档两次可差 3 s；上一轮"现行"档还测到 8.98 s），
而收紧会**动到 prompt-v3.9 的"结论命中率"口径**（该指标就靠解读里出现的数字计分）→
**否决**：不值得为一个不稳的收益去扰动已建立的评测基线。

## 5 解读"永不掉线"：规则化自动摘要兜底（2026-10-14 需求方决定）

**决策依据（需求方原话）**：*"`NARRATIVE_TIMEOUT_SECONDS` 保持 8s 是最好的，但是解读是必要的——
这个项目就是对能源电力的数据进行解读分析，给用户分析结果和结论。"*

⇒ 于是把"要速度"与"要解读"**同时满足**：**8s 上限不变**，但超时/解析失败时不再交出空解读，
而是用**结果表能直接算出来的事实**生成「自动摘要」。

| 场景 | 改造前 | 改造后 |
| --- | --- | --- |
| 模型解读在 8 s 内返回 | 正常解读 | 正常解读（不变） |
| 模型解读超时（慢时段） | `narrative=""` + 一条"已跳过"提示 → **界面无结论** | **「自动摘要」**：首末/极值/占比 + 标识列，并注明"模型解读超时，由结果表自动生成" |
| 模型解读**解析失败** | 整题抛 `E_LLM` 失败 ❗ | 退化为**自动摘要**，整题仍成功（解读是增值项，不该拖垮主体） |
| 结果为空 / 被截断 | — | 如实说明（"本次查询未返回数据（共 N 行）"／"结果已截断"），不编造原因 |

**实现要点**（`analysis_service._rule_narrative()`，两条链路共用）：

- **只用结果表里的数字**（行数 / 首末 / 极值 / 占比），**不做表外推断**、不引用上传阶段元信息（守 P4「不编造」红线）；
- 正文以「**自动摘要**」开头、结尾注明生成方式 —— 读者一眼能分辨这不是模型写的；
- 比率列按**百分比**展示（库里是 0.0621 这类小数），与人工核对口径一致；
- `key_numbers` 与正文一致，供"结论命中率"统计与人工核对；
- 复用 `chart_service` 的 `COLUMN_LABELS` / `_label_of` / `_is_frac` / `_fmt_number`，列名标签与图表**同一处权威**。

**验收**：新增 7 条用例（`tests/test_rule_narrative.py`），其中一条用**项目自己的未授权数字检测**
反向校验自动摘要（"同一把尺子量自己"）；既有用例 `test_narrative_timeout_is_not_fatal`
按新口径更新（原断言 `narrative == ""` → 现断言 `startswith("自动摘要")`）→ 全量 **334 passed**。

### 5.1 顺带修掉一个检测器缺陷：千分位被当成"编造"

自动摘要用千分位展示（`1,200`）时，`_unauthorized_numbers()` 把它拆成 `1` 与 `200`，
`200` 超过 `_STRAY_NUMBER_MIN=100` → **误报"解读中出现未在查询结果里的数字"** ❗
（对**真实模型解读**同样成立：模型写"合计 1,234 kWh"就会被误判）。

**修法**：`_numbers_in()` 与 `_unauthorized_numbers()` **统一先做千分位归一**
（`_THOUSANDS_RE = (?<=\d),(?=\d{3}(?!\d))` → `1,234` 归一为 `1234`），
并加用例守住两侧：`1,200.5` 不再误报 ✓，而真正的表外数字 `25,979` 仍被抓出 ✓。

### 6.2 机制（为什么那个开关会影响正确率）

该端点把"关闭思考"翻译成**额外注入一段系统提示**（同请求 `prompt_tokens` 200 → 528，实测）。
那段提示让模型**更守 JSON、更照题面**（"更慢但更听话"）：
- **对解读**：它只是拖慢（本来就要写一小段文字）→ 换掉划算；
- **对生成**：它决定**服从性** —— 去掉后模型开始"多给一点"（多吐列、自己算比率、丢掉 GROUP BY），
  而这些在"逐题判分、与 gold 严格对齐"的评测口径下**全算错**。

### 6.3 最终配置（与基线的差异一览）

| 配置项 | 基线（2026-10-13 晚，118/120） | **最终（2026-10-14 晚，116/120）** |
| --- | --- | --- |
| `LLM_ENABLE_THINKING` | `false` | **`false`（与基线一致，事故后已恢复）** |
| `LLM_MODEL_MAIN` | `deepseek-v4.1-flash` | 同（不变） |
| `LLM_MODEL_LIGHT`（slot） | `deepseek-v4.1-flash` | 同（**事故期曾被换成 glm，已回退**） |
| `LLM_MODEL_NARRATIVE`（新增） | —（解读走主力） | **`glm-5.3-flash`**（专用档，与 slot 解耦） |
| `LLM_MAX_TOKENS` | 4096 | **8192**（思考 + 正文都放得下） |
| `NARRATIVE_TIMEOUT_SECONDS` | 30 | **8**（产品默认；慢时由自动摘要兜底） |

**净效果**：速度（单题 19.8s → 11.7s 量级）+ 解读永不空白 + 输出上限更安全；
正确率 116/120 = 96.7%，与基线 118/120 差 2 题（q051 在基线也错；新增 q102/q115/q119
均属"占比语义 / 列形态"类，见 §4 遗留项的专项建议）。

### 6.4 三条硬教训

1. **"参数无副作用"要对每个用途分别验证**：同一个开关，对"解读"是纯拖慢，对"生成"却是服从性保障 ❗
   —— 我当初只用解读形态探针测了它，就据此改全局配置，代价是 17 个百分点。
2. **小样本探针不能替代全量评测**：5 题小批（`run_20261014_04/05`）当时看起来"更快更稳"，
   完全没暴露问题；**只有 120 题全量**才把它照出来 —— 这正是"跑得少=看得少"。
3. **配置分档要按用途切，不要复用别人的旋钮**：把解读塞进"slot 的轻量档"，
   等于让 slot 跟着解读模型一起换（事故期定位被搅乱，多了个无关变量）。现已拆成独立的 `LLM_MODEL_NARRATIVE`。

## 7 靶向修错题：prompt-v3.10（4/4 修复）＋ 顺带挖出两个真 bug

**起点**：合并口径下仍失败的 4 题（`q051 / q102 / q115 / q119`）。做法是**先取逐题证据**（gold SQL vs 生成 SQL、差异类型、行/列数），再**按证据改提示词**，最后**靶向复测**。

### 7.1 证据与修法

### 7.2 顺带挖出的两个真 bug（与"逐题翻转"直接相关）

**① 失败留痕撞 CHECK 约束 → 留痕丢失 + 异常上抛（问题 P-036）**

```
sqlite3.IntegrityError: CHECK constraint failed: route IS NULL OR route IN ('sql', 'pandas')
[参数: (..., '只看工作日。', '{}', '', ..., 'failed', 'E_LLM', '槽位解析超时（超过 12s）…')]
```

`analyses.route` 上有 CHECK 约束，而 `AnalysisResult.route` 的默认值是**空串**——slot 超时这类
"还没走到生成"的失败会把 `''` 写进去 → INSERT 被拒 → **失败留痕没写成、异常还上抛**。
评测侧的表现是"这题**没有调用记录、却是空结果**"，看起来像模型答错（q097/q102/q119 都中过）。
**修法**：落库前归一化，非 `sql`/`pandas` 一律写 NULL。

**② 追问轮 slot 超时被判"认不出指标"（问题 P-037）**

`fallback_slot()` 以前**一律要求本轮问句里能认出指标**；而"只看工作日。"这类追问本身没有指标词，
会话里却早就有（多轮语义 = 未提及即继承）→ 判失败。
**修法**：兜底模式新增 `allow_inherit`——**本轮认不出、但会话有指标**时返回"指标留空"的增量，
由 `merge_slot` 继承；只有"本轮认不出 **且** 会话也没有"才如实失败（不编造）。

**③ 顺手补的一格：半成品也重发**

`_chat_generate` 的"不可用就重发一次"以前只判**空输出**；实测 q119/q110 会出现
"**解析得动但没有 `sql`/`code`**"的半成品（同样不含可执行语义）→ 现在两种情况都重发一次（逐次留痕、逐次计费）。

### 7.3 一条重要的测量学教训（影响所有评测结论）

做回归样本（20 题）时出现 **4 处"退化"**（q098/q099/q100/q110，全是"多吐列"）→
**同一批题、同一个提示词，间隔几分钟复跑就是 3/4 通过** ❗
⇒ **该端点存在明显的逐题不稳定性**：同一题在小时级内可来回翻转，
**20 题样本的 ±4 波动属正常范围**，不能据此判定"提示词引入退化"。
**推论**：① 判断提示词/配置改动，**要么跑全量 120，要么对同一题集做多轮重复取均值**；
② 引用"116/120"这类单次结果时，应同时说明**±3–4 题的噪声带**。
