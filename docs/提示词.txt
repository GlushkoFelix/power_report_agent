【E. 第 5 轮：鉴权与首个业务接口（12 题）】
--------------------------------------------------------------------------------
E1  错误码体系（双轨制）：HTTP 语义化状态码 + 包络 code 与 HTTP 同值（成功 0）+ 业务错误码放 data.error_code（E_*）。
E2  预置报表所有权与活跃报表权威：预置 5 条保持 user_id = NULL 全用户共享可见（GET /reports 条件 user_id = :me OR is_preset = 1）；会话内唯一权威 = conversations.active_report_id。
E3  uploaded_reports.is_active 语义：系统默认活跃报表（仅预置中一张为 1，当前 r_daily）；不是「当前用户最近活跃」。
E4  令牌策略：单 access token 24h；JWT_SECRET_KEY 必须显式配置，缺失则启动报错并打印生成命令；登出仅前端清除 token + 服务端落 auth_logout 审计；不引入黑名单表。
E5  注册校验：用户名 ^[A-Za-z0-9_]{4,20}$；密码 8–64 字符、须同时含字母与数字、UTF-8 编码后 ≤72 字节（超出直接拒绝，不静默截断）。
E6  审计事件：audit_logs.event_type 白名单由 5 个扩为 10 个（新增 auth_register / auth_login / auth_login_failed / auth_locked / auth_logout）；改 DDL 并重建 power_agent.db。
E7  报表列表契约：GET /reports 全量返回（不分页），13 字段 + table_exists（查 reports.db 的 sqlite_master 自检）；不含 schema_json / quality_json 正文；排序 = 预置在前（id 升序）+ 上传按 created_at 倒序。
E8  登录锁定语义（严格策略）：密码错 401；第 5 次失败起锁定 5 分钟并返回 429 + E_AUTH_LOCKED（含 locked_seconds）；锁定期内不校验密码；成功登录才清零计数；锁定到期不清零；用户名不存在与密码错同文案（防枚举）；is_active=0 返回 403。
E9  测试策略：建 01.code/backend/tests/，pytest + httpx AsyncClient + 临时库（用真实 DDL 建），新增 requirements-dev.txt。
E10 数据访问层：ORM Declarative models（app/db/models/），只做查询映射、不调 create_all()。
E11 注册契约：注册成功即自动登录，返回 { token, token_type, expires_at, user }；审计只写一条 auth_register。
E12 用户名大小写：不区分大小写，服务端统一转小写存储与比对。

【F. 第 6 轮：报表读路径接口（5 题）+ 自增主键过滤】
--------------------------------------------------------------------------------
F1  URL 标识：全模块统一用**对外业务编号** —— `/reports/{report_code}`（r_daily）、`/conversations/{conversation_code}`（c_20260915_0001）、`/analysis/records/{record_code}`（a_000123）、`/eval/runs/{run_code}`；不使用自增主键。PRD 9.1 全表同步，9.2 请求字段同步为 conversation_code / report_code。
F2  预览契约：`GET /reports/{report_code}/preview` 默认 50 行，`?limit=` 取值 1–200（越界返回 400 E_VALIDATION，不走框架 422），对象数组返回；按时间列正序（minute→dt / hourly→dt_hour / daily→date / monthly→year_month / structure→year；未知上传表按候选名探测，兜底 rowid）；columns 取 PRAGMA table_info；total_rows 取元数据、不跑 COUNT(*)；返回 truncated 标记。
F3  Schema / Quality 数据来源：**回填入库** —— 扩展 03_init_db.py 给预置 5 条写 schema_json（取自 02.data/schema/<table>.schema.json，紧凑化）与 quality_json（按表裁剪：minute→A5；hourly/daily/monthly→A1+A5；structure→A2/A3/A4+A5）；接口只读库，上传表由上传入库服务写同一列。
F4  Schema 文本：取 02.data/schema/schema_text.md 中以 `### <table_name>` 开头的**原文段落**（前端数据字典与注入给模型的文本逐字一致）；上传的动态表没有该段落 → 回退为由 schema_json 渲染；响应用 `text_source` 标明来源（schema_text.md / rendered）。
F5  边界（自定）：他人上传的报表返回 403 E_FORBIDDEN（文案不泄露是否存在）；不存在/已删除返回 404；`POST /reports/{report_code}/activate` 归会话模块；upload 与 confirm 属写路径下一批。
F6  自增主键过滤：预览接口**过滤自增主键 id 等代理键**（依据：① schema_json 本就不含 id，保留会导致「预览列数 ≠ Schema 字典列数」；② 代理键对分析无意义）。响应新增 `excluded_columns` 回显被过滤列。

【G. 第 7 轮：会话模块（4 题）】
--------------------------------------------------------------------------------
G1  置顶字段：`conversations` 新增 `is_pinned`（NOT NULL DEFAULT 0，CHECK 0/1）与 `pinned_at`，并新增索引 `(user_id, is_pinned, pinned_at)`；置顶组按 `pinned_at DESC` 排序；每用户**上限 5 条**，超出**自动取消最早置顶**的那条并在 PATCH 响应 `evicted_pinned_code` 回显（不弹错误）。

G4  消息历史：**游标式分页** —— 默认最近 50 条（内部按 `seq_no DESC` 取、返回按 `seq_no ASC` 正序），`?limit=` 1–200，`?before_seq=` 向历史翻页，响应含 `has_more` / `oldest_seq` / `newest_seq`；直接命中 `UNIQUE(conversation_id, seq_no)`，无 offset 漂移。
G5  自定边界：会话列表**不分页**（与报表列表一致）+ 支持 `?q=` 与 `?date_from=`/`?date_to=`，置顶组在前；`conversation_code = c_YYYYMMDD_NNNN`（当日最大序号 +1，冲突重试 3 次）；删除会话写 `audit_logs(cascade_delete)` 并回显级联删除消息数；`message_count` 由列表接口用一次分组 COUNT 实时计算。

PRD 9.2 的 clarify 事件排在 slot 之后（与第十七轮计划写的 status→clarify→slot 相反）；
SLOT_SYSTEM 现有指示是「用户没提时间填 null（不要猜）」；原生 EventSource 不支持 POST/鉴权头。

── 决策 1：澄清（clarify）的触发条件 ──
问：澄清触发定成什么？
选项：A 混合（metric 规则必澄清 + 语义歧义交模型）｜B 严格规则（任一关键 slot 缺失即澄清）｜
      C 纯模型（intent=澄清 才澄清）
答：A（推荐）。
  ① metric 缺失 → 必澄清（UIUX 6.3 已定 metric 必填、不可清除）；
  ② time_range 缺失 → 不澄清：继承会话 slot，都没有则默认「全期」（与 UIUX 6.3「清除后回到默认全期」
     一致，避免每题都弹澄清框）；
  ③ 语义级歧义（报表歧义 / 指标歧义 / 粒度歧义）→ 由模型输出 intent=澄清 + missing_slot 触发。
  理由：演示流畅；规则部分确定可测；模型兜住规则覆盖不了的歧义。代价：两类触发并存，测试分别覆盖。

── 决策 2：澄清轮的落库与事件收尾 ──
问：澄清轮怎么落库、事件怎么收尾？
选项：A 不落 analyses，落消息×2，clarify 后发 done｜B 落 status=failed + E_CLARIFY｜
      C 改 DDL 加 status=clarified
答：A（推荐）。
  事件序列 status → slot → clarify → done(record_id=null)（澄清没执行任何东西，不产生记录，零 DDL 改动）；
  落 messages×2（user=原问题、assistant=澄清问题文案、analysis_id=NULL）——历史对话里能看到澄清卡；
  会话 message_count+2，但 slot_json 不回写（没执行成功，不产生脏芯片状态）；
  已解析的部分 slot 放在 clarify 事件的 partial_slot 里给前端回显（对应 PRD「已解析条件不丢失」）。
  理由：语义干净（失败页签不被澄清污染）、历史可回溯、零 DDL；代价：done.record_id 多一个 null 分支。

── 决策 3：POST /analysis/clarify 的「继续执行」实现 ──
问：继续执行发生在哪一侧？
选项：A 回填后就地继续执行（clarify 返回 SSE）｜B 只回填，前端再发 chat｜C 服务端保存待续状态
答：A（推荐）。
  请求体 {conversation_code, question（原问题）, missing_slot, value}（或 slot_patch 对象支持一次回填
  多字段）→ 校验归属与取值 → 把回填值合入会话 slot_json → 本请求内继续跑完整链路（合并后的完整 slot
  → SQL → …），返回 SSE（事件序列与 chat 相同，slot 事件是合并后的完整 slot）。
  无状态：不保存待续状态，原问题由前端从澄清卡上下文回传。
  附带修正：PRD 9.1 该接口鉴权标「否」是笔误，回填为「是」（要写会话必须鉴权）。
  理由：一次请求完成、语义与 PRD 一致、前端只需 POST 点选结果；代价：响应也是 SSE（前端复用同一套
  流式解析）。

── 决策 4：slot 合并细则 ──
问：_merge_slot 的合并语义怎么定？
选项：A null=继承 + filters 同 field 替换 + 清除本批不做｜B filters 一律追加｜C 支持显式清除（三态）
答：A（推荐）。
  ① 标量字段（time_range/granularity/metric/dimension/compare/intent/chart_hint）：增量非 null 即覆盖、
     null 即继承；
  ② filters（数组）：同 field 替换、异 field 追加（「只看周末的」再问「只看工作日的」→ 替换而非并存，
     避免两条矛盾过滤）；
  ③ 本批不做「显式清除」（无法区分未提及与刻意清除，三态哨兵复杂度高）——清除交给前端条件芯片
     （UIUX 6.3 已有交互），后端后续批次再加。
  合并实现为纯函数 _merge_slot(base, increment)，三类规则各自可单测。

── 决策 5：澄清卡片的选项生成 ──
问：选项从哪来？
选项：A 纯规则零 LLM｜B LLM 生成（轻量模型）｜C 规则生成 + 模型润色文案
答：A（推荐）。按 missing_slot 查表：time_range → 固定四选【全期/今年/近 30 天/自定义】；
    metric → 从 schema 可用指标取前 3（复用 _available_hints 清单）；granularity → 小时/日/月/年；
    报表歧义 → 用户可见报表前 3 张（预置 + 本人上传，排除 pending）；question 文案按模板拼。
  理由：零延迟零成本（不吃 N2 的 8s 预算）、确定性可测、value 值域绝对合法（点选即可直接合入 slot）；
  代价：选项不结合语境，但演示与评测足够。

── 决策 6：切换活跃报表时的 slot 处理 ──
问：跨报表的 slot 污染怎么处理？
选项：A 切换即清空 slot｜B 只保留通用字段（time_range/granularity）｜C 不清靠提示词兜底
答：A（推荐）。set_active_report 里顺带把 slot_json 置空，前后端提示「已切换到 report_monthly（月报），
    条件已重置」。
  理由：从根上杜绝跨表脏 slot（旧表的 metric/dimension/filters 对新表可能不存在），不需要维护
  「哪些字段跨表通用」的白名单；代价：切回来要重说条件（报表切换本就是换分析对象，可接受）。

── 决策 7：沙箱的隔离模型与资源限制 ──
问：超时/内存/禁网禁写在 Windows 上怎么落地？
选项：A 子进程隔离｜B 线程 + 超时放弃等待｜C 只做 AST 预检不做资源限制
答：A（推荐）。
  模型生成的代码放**独立子进程**执行：超时 → process.kill()（Windows 可行，「10s 超时」是真的）；
  内存 → 子进程内 psutil 轮询自身 RSS，超 512MB 自杀式退出（也是真的）；
  禁网/禁写 → 靠 AST 预检白名单（禁 socket/urllib/httpx/open 等），文档如实写「不做 OS 级断网」
  （Windows 无 unshare，做不到就明说）；行数上限（≤5000 行）在父进程收结果时截断。
  代价：子进程冷启动要重新 import pandas（约 1s，N2 预算内，后续可用常驻 worker 优化）；
  新增依赖 psutil（纯轮、体积小）。
  理由：三条资源限制全部真实可验证，答辩能现场演示「死循环代码 10 秒被杀」。

── 决策 8：沙箱的 df 注入范围 ──
问：df 怎么给？（与决策 7 强耦合：子进程方案下 df 必须序列化传给子进程，r_minute 有 207 万行）
选项：A 行数闸门（小表全量，大表禁走 pandas）｜B 按 time_range 过滤子集｜C 全表注入
答：A（推荐）。plan_route 阶段按**报表行数**决定 pandas 可用性：行数 ≤ 阈值（默认 10 万，config 可配）
    才允许 pandas（df = 全表 pickle 传子进程）；超过阈值 → 工具描述写明「该表数据量大，请用 SQL 聚合」，
    模型仍生成 pandas 代码则拒绝并回退 SQL。
  效果：r_minute（207 万行）天然只走 SQL（其分析需求 SQL 全覆盖），上传小表才享受 pandas。
  理由：内存/序列化时间可控（10 万行 pickle 约 150MB/2s）、规则简单可测；代价：大表的多步变换类问题
  只能用 SQL 表达（SQLite 窗口函数/CTE 能覆盖大部分）。

── 决策 9：失败重试 / 换路径矩阵 ──
问：哪些失败触发重试/换路径？重试几次？
选项：A 分类型矩阵（可修复的重试，恶意拦截不重试）｜B 一切失败都重试 2 次｜C 只换路径不回灌
答：A（推荐）。
  ① SQL 执行报错（E_SQL_EXEC）→ 换 pandas 路径重试；
  ② R3 混加命中 → 原路径回灌重试一次（把「两套拆分不可混加」原因喂回模型——可自动修复的错误）；
  ③ pandas 代码被 code_guard 拦或执行异常 → 换 SQL 路径；
  ④ 守卫基础拦截（非 SELECT / 表不在白名单 / 危险函数）→ 不重试直接失败
     （越权/恶意信号，重试等于教模型试探守卫边界）；
  总预算：额外尝试 ≤2 次；retries / path_switched 落库（DDL 已有这两列）。

── 决策 10：前端骨架范围与 SSE 客户端 ──
问：本批做到哪一步？SSE 用什么方案？
选项：A 骨架最小集 + fetch-event-source + 回填 TBD1｜B 骨架 + 登录页真实对接｜C 只建工程
答：A（推荐）。Vite react-ts + 装齐依赖（antd / tailwindcss @tailwindcss/vite / plotly.js / axios /
    zustand / @microsoft/fetch-event-source）+ StyleProvider layer + MainLayout + 5 路由占位页 +
    3 个空 store（chatStore/reportStore/slotStore）+ axios 实例（token 拦截器 + 401 跳登录）+ SSE 封装；
    验收 = npm run dev 能跑、路由能跳；回填 PRD 10.4 / UIUX U1 实际版本号（关闭 TBD1）。
  关键事实：原生 EventSource 不支持 POST 和自定义鉴权头，而 chat/clarify 都是 POST+Bearer+SSE，
  必须用 @microsoft/fetch-event-source（或自写 fetch reader）。
