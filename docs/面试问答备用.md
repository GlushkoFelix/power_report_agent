## 二、三个可讲 3 分钟的主故事

### 故事 A｜把"隐式编排"包进图里（技术判断）

1. 原实现是 1533 行的显式 async 编排，状态分散在 **13 处**隐式变量里（SSE 副作用、进程级 LLM 客户端、子进程池、ORM 会话生命周期……）。
2. 直接重写 = 行为全变。所以选 **strangler 包裹**：节点只薄封装原函数，纯数据进 state，运行时依赖走 `configurable`。
3. 真正的难点不是画图，是**保住"事件产生即推送"**——迁完若改成"跑完再回放事件"，首字会退化到整条链路耗时。解法：节点内用 `get_stream_writer()` 走 custom 通道。
4. 另外两个坑：澄清中断节点恢复时**会整体重跑**，所以建卡/落库/发事件必须前置到独立节点；检查点单例绑定事件循环，测试里必须按 loop 缓存。
5. 收尾：9 条等价性用例（逐字段 + 逐事件）全绿后才切默认实现。

**一句话总结**："能不能图化不取决于框架，取决于状态是否收敛。"

### 故事 B｜把生成代码关进笼子（安全设计）

1. 前提：LLM 生成的是**不可信输入**。
2. SQL 侧：sqlglot 解析成 AST 再判——单条 SELECT/UNION/WITH、表白名单、危险函数黑名单、强制 LIMIT 1000，外加业务红线。
3. pandas 侧：AST 预检（禁 import/文件/网络）+ 子进程隔离（10s / 512MB / 5000 行）。选进程不选 RestrictedPython，因为要的是**资源边界**。
4. 边界诚实说：守卫管"不许干什么"，评测管"干得对不对"。
5. 证据：18 道陷阱题全拦对；真实数字见简历。

### 故事 C｜评测中断后怎么救回数据（成本取舍）

1. 现象：120 题跑到 102 条，机器停止，聚合与报告全丢，只剩逐题留痕。
2. 两个选项：整批重跑（约 110 万 tokens）vs 写工具本地重算。
3. 拍板依据：判分函数可复用——**import 在线同一套函数**，不是重写，所以口径不会漂；唯一偏差是耗时取逐轮求和（毫秒级）。
4. 结果：省约 82 万 tokens，一条不丢；第二次又省 37 万，累计约 119 万。
5. 代价：耗时类指标不可重建（在线含轮间开销），所以**重建批次的耗时不能当成绩引用**。

## 四、四个高风险问题（几乎必问）

**1.「这项目 AI 参与了多少？」**
> 代码大量由 AI 生成，我是架构、验收和口径的负责人——**判断"算不算对"的标准是我定的**，361 条用例和 39 条问题记录就是这么来的。
（不要给比例，不要说"每一行都是我写的"。）

**2.「任务书要求的 8s 没达到，是不是没做完？」**
> 主链路是通的，8s 这一条没达标，我如实写在简历里。根因是单题串行 3 次模型调用叠加端点时段波动：快时段 96.7%、慢时段 67.2%。已做的优化是规则快通道（省掉 1 次 slot 调用，覆盖从 14% 提到 49%）与生成超时自动重试；没做的是合并 slot 与生成调用。

**3.「有没有部署上线？」**
> 没有公网部署，只做本机可运行演示；移动端适配也没做。这两条是任务书要求但未闭环的部分。

**4.「LangGraph 是你选的还是任务书要的？」**
> 任务书指定的。我原来的实现是显式 async 编排且能跑，所以我没推翻重写，而是用图包裹 + 等价性测试把行为锁住再逐步迁移——这个过程比"选框架"更有价值。
