## 1. 文档说明

### 1.1 目的与读者

| 读者 | 用途 |
| --- | --- |
| 部署者 | 第 3–6 章：从零把系统跑起来（环境、建库、配置、启动、探活） |
| 运维者 | 第 7–9 章：配置项含义、日常巡检、备份、升级 |
| 排障者 | 第 11 章：按"症状 → 原因 → 处置"查表 |
| 评审者 | 第 2、12 章与附录：了解部署形态、安全边界与端口/路径清单 |

### 1.2 设计前提（决定了本手册的形态）

- **单机部署、无外部中间件**：不需要 Redis / MQ / 向量库；两库是 SQLite 文件，
  模型走 HTTP 调用外部厂商（OpenAI 兼容协议）。
- **模型可换、可离线**：未配置 `LLM_API_KEY` 时，后端自动使用**离线脚本模型**——
  链路仍然端到端可跑通（便于无网演示与环境自检），但结果**不是真实模型产出**，
  `/system/health` 会如实回报 `llm.configured=false`。
- **路径与启动目录无关**：所有路径以「项目根」为基准解析，因此从任意目录启动 uvicorn 都能正确连库。

**两库职责边界（务必记住）**

| 库 | 角色 | 应用侧权限 | 例外 |
| --- | --- | --- | --- |

## 5. 首次部署（从零到可用，7 步）

### 5.1 准备虚拟环境与后端依赖

```powershell
Set-Location E:\power_report_agent

# ① 创建虚拟环境（已存在则跳过）
python -m venv .venv

# ② 安装后端依赖（含 pandas / numpy / plotly）
.venv\Scripts\python.exe -m pip install -U pip
.venv\Scripts\python.exe -m pip install -r 01.code\backend\requirements.txt

# ③（可选，跑测试用）开发依赖
.venv\Scripts\python.exe -m pip install -r 01.code\backend\requirements-dev.txt
```

> 依赖清单里有两条**刻意不引入**的说明，部署时不要"顺手补上"：
> **不装 `openai` SDK**（兼容端点用已装的 `httpx` 直调，装了反而多拖 4 个包）；
> **不装 `kaleido`**（图表 PNG 导出是预留能力，未装时接口如实返回 501，装上即生效、无需改码）。

### 5.2 配置 `.env`（**唯一必须人工填写的文件**）

```powershell
Copy-Item 01.code\backend\.env.example 01.code\backend\.env

# 生成 JWT 密钥并填入 .env（缺失会导致后端启动失败，这是刻意设计）
.venv\Scripts\python.exe -c "import secrets;print(secrets.token_urlsafe(48))"
```

`01.code\backend\.env` 最少需要填写：

| 变量 | 是否必填 | 说明 |
| --- | --- | --- |
| `JWT_SECRET_KEY` | **必填** | 缺失 → 启动报错（避免每次重启换密钥导致 token 全失效） |
| `LLM_API_KEY` | 选填 | 不填 → 走离线脚本模型（链路可跑通，结果非真实模型） |
| `LLM_BASE_URL` / `LLM_MODEL_MAIN` / `LLM_MODEL_LIGHT` | 选填 | 换厂商只改这四项，**代码零改动** |

完整参数表见 **第 7 章**。

### 5.3 准备前端依赖

```powershell
Set-Location E:\power_report_agent\01.code\frontend
npm install            # 首次；后续用 npm ci（按 lock 精确还原）
```

### 5.4 生成数据、Schema 与两库（按顺序执行 4 个脚本）

```powershell
Set-Location E:\power_report_agent

# ① 解析原始 txt → 清洗 → 4 张报表 CSV + 质量报告 + manifest（--force 强制重算）
.venv\Scripts\python.exe 01.code\scripts\01_build_reports.py

# ② 生成 Schema JSON 与**注入文本** 02.data/schema/schema_text.md
.venv\Scripts\python.exe 01.code\scripts\02_build_schema.py

# ③ 执行 DDL 建库并灌数（207 万行，实测 ~17.8s；--force 删除既有库重建）
.venv\Scripts\python.exe 01.code\scripts\03_init_db.py

# ④ 构建 120 题评测题库（写 JSON + 入 power_agent.db）；--check 只校验分布与 gold 可执行性
.venv\Scripts\python.exe 01.code\scripts\04_build_eval_set.py
```

各脚本产物与日志：

| 脚本 | 产物 | 日志 |
| --- | --- | --- |
| `01_build_reports.py` | `02.data/reports/*.csv`、`manifest.json`、`02.data/quality/quality_report.json` | `02.data/logs/01_build_reports_<时间戳>.log` |
| `02_build_schema.py` | `02.data/schema/<table>.schema.json`、`all_schemas.json`、**`schema_text.md`** | 控制台 |
| `03_init_db.py` | `02.data/reports.db` + `02.data/power_agent.db`（建表 + 灌数） | `02.data/logs/03_init_db_<时间戳>.log` |
| `04_build_eval_set.py` | `02.data/eval/eval_questions.json` + `eval_questions` 表 120 行 | `02.data/logs/eval_set_<时间戳>.log` |

> **口径一致性保证**：`03_init_db.py` **直接调用 `01_build_reports` 的聚合函数**（同一份清洗逻辑），
> 而不是读回已舍入的 CSV —— 因此库内数值为未舍入的精确值，三级总量（分钟/小时/日）严格相等。

### 5.5 校验数据口径（部署后的第一道自检）

A1–A5 口径校验**已内建在数据脚本里**，不需要额外命令：

| 校验发生处 | 说明 |
| --- | --- |
| `01_build_reports.py`（步骤 ①） | 基于**未舍入**的聚合结果算 A1–A5；**A1 / A2 不通过时脚本返回非 0**（可直接当门禁） |
| `03_init_db.py`（步骤 ③） | **在库上重跑 A1–A5**——校验的是"真正被分析的数据"，而不是 CSV |

**查看结论**（两个入口，同一份事实）：

```powershell
# ① 数据质量报告文件（含 A1–A5 结论与数据集级质量）
Get-Content 02.data\quality\quality_report.json -Encoding UTF8 | ConvertFrom-Json | Select-Object -ExpandProperty checks

# ② 接口口径（登录后按报表查：checks 里能看到 A1_levels_equal / A5_row_counts）
Invoke-RestMethod "http://127.0.0.1:8000/api/v1/reports/r_daily/quality" -Headers @{Authorization="Bearer $TOKEN"}
```

> 交付基线（实测，测试报告 6 章登记）：**A1 三级总量 37283.7477 kWh（偏差 0）**、
> **A2 未计量占比 51.1977%**、A3 有效分钟 2,049,280/2,075,259 = 98.7486%、
> A4 异常日 81/1442。数字对不上说明数据脚本或原始数据有问题，**先别急着上业务**。

## 7. 配置参数手册（`.env` 全量）

> 全部变量名与 `.env` 大小写不敏感匹配；下表按区块排列，**改完必须重启后端**（配置在进程内单例缓存）。

### 7.1 LLM（换厂商 / 换模型只改这一组）

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `LLM_API_KEY` | 空 | 正式名；**留占位值（`sk-xxxxxx` / `请填入`）等同未配置**（会回落脚本模型） |
| `DASHSCOPE_API_KEY` | 空 | 历史别名，兼容用；与上者同时填写时 `LLM_API_KEY` 优先 |
| `LLM_PROVIDER_LABEL` | `dashscope` | 厂商标识，仅用于健康检查展示与日志（不影响协议行为） |
| `LLM_BASE_URL` | 百炼兼容端点 | 该厂商的 OpenAI 兼容端点（**含 `/v1` 等路径**，以厂商文档为准） |
| `LLM_MODEL_MAIN` | `qwen-max` | **生成**（SQL / pandas 代码）用：正确率的关键档。**本项目取 `deepseek-v4-flash-0731`**（2026-10-16 端点换代别名；上游仍是 `deepseek-v4.1-flash`——120 题 118/120 那一档，**历史口径仍可比**。⚠️ 换端点/额度后先用 `GET /v1/models` 对清单） |
| `LLM_MODEL_LIGHT` | `qwen-turbo` | **slot 抽取**用。**本项目取 `deepseek-v4-flash-0731`**（同上） |
| `LLM_MODEL_NARRATIVE` | 空（回落 LIGHT） | **解读专用档**（2026-10-14 新增：与 slot 解耦，避免"换解读模型 = 换 slot 模型"）。**本项目取 `qwen3.8-flash`**（2026-10-16 换：原 `glm-5.3-flash` 在同一端点上**JSON 与纯文本两种模式都返回空正文**，还照扣 token；`qwen3.8-flash` 实测 2.9–3.7s、正文正常）。选它而非主力档的理由仍是：主力"推理型"模型在解读上会**"推理洪水"**（completion 165 → 2,536、正文解析失败 → 界面无解读） |
| `LLM_TEMPERATURE` | `0.0` | **评测固定 0**（同题可复现） |
| `LLM_ENABLE_THINKING` | `false`（**本项目发送**） | 思考开关。**本项目最终口径＝发送 `false`**，但这是**两轮实测结论相反**后的定稿，务必连读：<br>① **解读形态**探针（prompt≈300 token、JSON 模式，各 3 次）：发它 **4.88s（3 次 1 次正文为空）**、不发 **2.42s（3/3 正常）** → 倾向"不发"；<br>② **120 题全量**（生成形态，决定正确率）：不发它时模型变"**过度热心**"（多吐列 / 丢 `GROUP BY` / SQL 过滤成空）→ **旧对→新错 18 题，118/120 掉到 101/120** ❗<br>⇒ **最终发送**（保生成服从性），解读的慢由「**自动摘要**兜底」吸收。机制：端点把"关闭思考"翻译成**额外注入一段系统提示**（prompt +328 token），那段提示让模型**更守 JSON、更照题面**（"更慢但更听话"）。<br>⚠️ 各厂商语义差异极大（有的**只允许 `true`**，发 `false` 直接 400）→ **换端点必须用真探针 + 小批真实评测复测** |
| `LLM_MAX_TOKENS` | `8192` | 输出上限（`0` = 不发送）。**本项目 4096 → 8192**：思考先占额度，实测有题 `completion=4095` 正好顶到 4096 被截断（JSON 不完整 → 列数/取值错） |

| `NARRATIVE_TIMEOUT_SECONDS` | `8` | 解读超时（秒）。**超时或解析失败时改用「自动摘要」**（服务端用结果表算出的结论，正文标注"自动摘要"）→ 界面**永远有解读**；表格与图表早已产出、不受影响 |

**其它厂商示例**（`01.code/backend/.env.example` 里已给可直接取消注释的模板）：
DeepSeek / Moonshot(Kimi) / 智谱 GLM / 本地 Ollama·vLLM / 阿里云百炼专属 MaaS 端点。

### 9.2 数据库结构变更的处理方式（**本项目的重要约定**）

SQLite **无法 `ALTER` 一个已有的 `CHECK` 约束**，因此"白名单类字段扩容"必须**重建表**：

- 迁移脚本：`01.code/scripts/05_migrate_audit_events.py`（`audit_logs.event_type` 白名单扩容）；
- 设计：全过程**单事务**，关闭外键检查（无表外键指向 `audit_logs`），
  `INSERT ... SELECT *` 保数据一行不丢，**幂等**（重复执行安全）；
- 真实案例（务必引以为戒）：`audit_logs` 的 `event_type` / `action` 是白名单字段，
  历史上新增事件类型时**漏改 DDL**，导致审计插入被 CHECK 拒绝、又被调用处的
  `try/except` 掩盖 —— **静默失败**，只在后端日志可见。
  因此本项目立了一条流程要求：**白名单类字段新增取值，必须同步 DDL + 考虑存量库迁移**。

### 9.4 交付打包前：密钥核对清单（**每次打包都做，约 2 分钟**）

> 背景：开发树的 `.env` 里有**真实 Key**（`.gitignore` 已排除，但"打包"往往是 `robocopy` / 压缩包这类
> 绕过 git 的动作）。本清单把"密钥不外流"变成**可执行的检查**，而不是靠记性。
> 当前开发树有两份敏感文件：`.env`（真实 Key）与 `.env.bak_20261013_aliyun-maas`（历史 Key）——**都不得进包**。

```powershell
# 0) 记下待打包目录；以下命令把它替换成实际路径（例：<包根> = 部署版code）
$pkg = "<包根>"

# ① 不能出现任何真实 .env（.env.example 例外）——期望输出为空
Get-ChildItem $pkg -Recurse -Force -Include '.env','.env.*' -File |
  Where-Object { $_.Name -ne '.env.example' } | Select-Object -ExpandProperty FullName

# ② 全包扫密钥串（百炼/OpenAI 风格 sk-…）——期望输出为空
Get-ChildItem $pkg -Recurse -File -Include *.py,*.md,*.json,*.txt,*.ts,*.tsx,*.yaml,*.yml |
  Select-String -Pattern 'sk-[A-Za-z0-9]{20,}' | Select-Object -First 5

# ③ .env.example 必须恰好 1 份（部署者据此自行生成 .env）——期望输出 1
(Get-ChildItem $pkg -Recurse -Force -Filter '.env.example').Count

# ④ 顺手确认没有把运行产物打进去——期望输出为 0 或很小
(Get-ChildItem $pkg -Recurse -Force -Directory |
  Where-Object { $_.Name -in @('node_modules','.venv','dist','__pycache__','.vite') }).Count
```

**通过标准**：① 与 ② **无输出**（或仅命中文档里的示例串且已确认非真钥）、③ 等于 1、④ 等于 0。

> **实测记录（2026-10-14 复检并处置 `部署版code/`）**：① 无真实 `.env`（仅 `.env.example`）✓；
> ② `sk-` 密钥串**零命中** ✓；③ `.env.example` **1 份** ✓；
> ④ 复检时 **不符合**（仍有 `node_modules` 7 个 / `__pycache__` 10 个 / `dist` 19 个，
> 全包 **13,390 文件 / 34.8 MB**，与其 README 的"165 文件 / 约 5 MB"不符）
> → **已处置**：`frontend/node_modules`（29.7 MB）**移出**交付包（暂存 `02.data/tmp/_snapshot_junk/`，
> 可随时删）、10 个 `__pycache__` 删除 → **复检 ④ = 0 个、全包 165 文件 / 5.0 MB** ✓。
>
> **教训（写进流程）**：快照生成是 `robocopy /E` + 排除清单的**手工动作**，**排除清单会被漏执行**；
> 因此本节 4 条检查必须**每次打包后实跑**，不能只看 README 的自我声称。
> （另：批删一次超过 500 个文件会被工具的批量删除保护拦下 —— 交付包清理用"**移出**"比"删除"更稳、也更可逆。）
>
> **实测记录（2026-10-15 复检并刷新 `部署版code/`）**：快照已于 10-14 整树刷新（`robocopy` + 排除清单），
> 10-15 又**按文件**同步了当日代码改动（代码拦截审计 3 个文件），随后实跑本节 4 条 ——
> **① 无真实 `.env`（0）✓ ② `sk-` 零命中 ✓ ③ `.env.example` 1 份 ✓ ④ 产物目录 0 个 ✓**；
> 全包 **184 个文件 / 5.24 MB**，并与开发树逐文件核对：**183 个源码文件逐字节一致（差异 0）**。
> **④ 的盲区（当日踩到）**：它只统计**目录**型产物，**漏了文件型产物** —— 快照里混进过一个
> `01.code/frontend/tsconfig.tsbuildinfo`（`tsc -b` 的增量缓存，1,647 B），已删除（文件数 185 → **184**）。
> 因此 ④ 之后**顺手再跑一条**：`Get-ChildItem $pkg -Recurse -File | Where-Object Name -match 'tsbuildinfo$|\.log$'`
> （期望为空）。

## 10. 数据与安全运维要点

| 要点 | 说明 |
| --- | --- |
| 密钥 | `.env` **严禁入库**；`.env.example` 里的占位值会被识别为"未配置"（避免用假 Key 反复调用厂商） |
| 日志脱敏 | 后端不记请求体与 `Authorization` 头；审计 `payload` 严禁写密码 / token 明文 |
| 两库只读 | `reports.db` 应用侧只读（`PRAGMA query_only`）；唯一例外是上传入库的受控写连接 |
| LLM 代码只读 | pandas 代码经 AST 预检（双下划线属性、危险调用、import 白名单）+ 子进程隔离 + 只读库连接 |
| SQL 只读 | 按语法树判定（sqlglot），只允许单条 SELECT，并强制 LIMIT 兜底 |
| 越权 | 资源归属一律按 `user_id` 过滤，他人资源返回 404（不泄露存在性） |
| 审计 | 安全拦截、认证、个人中心四件事全部落 `audit_logs`；**账号删除后日志保留、`user_id` 置空** |
| 账号删除 | 删上传报表（含物理表）→ 删评测批次 → 删用户行级联业务数据 → 审计保留 |
| 生产建议 | 启用 HTTPS；`APP_HOST` 收窄为 `127.0.0.1` 或置于反向代理之后；按需增加访问频率限制 |

## 11. 故障排查（症状 → 原因 → 处置）

| 症状 | 可能原因 | 处置 |
| --- | --- | --- |
| 后端**启动即报错**：`缺少 JWT_SECRET_KEY` | `.env` 未填或仍是 `请填入` | 生成密钥填入 `.env`（见 5.2）；这是刻意设计，避免重启换密钥导致 token 全失效 |
| 后端起不来：`Address already in use` | 8000 被占用（旧进程未退） | 按 6.3 停止占用进程，或改端口 |
| `/system/health` 返回 `llm.configured=false` | 未配置或仍是占位 Key | 填 `LLM_API_KEY`；**此时链路仍可跑通，但结果是脚本模型产出**（非真实模型） |
| 分析总以 `E_LLM` 失败 | Key/端点/模型名不对；或额度耗尽；或端点不支持 `response_format` | 逐项核对 `LLM_BASE_URL`（含 `/v1`）与模型名；查额度；`LLM_JSON_MODE_FALLBACK=true` 已默认开启降级重试 |
| 首字很慢（要等好几秒才出状态） | 前端未走 SSE 真流式（旧版本）；或反向代理**缓冲了 SSE** | 确认前端用 `fetch-event-source`；反代需关闭响应缓冲（Vite 代理已配置） |
| SSE 中断/无输出 | 代理或网关超时；客户端断开（服务端会取消链路） | 关缓冲、放大超时；看后端日志 `rid=` |
| 上传报 `E_NO_TIME_COLUMN` | 表头没有可识别的时间列 | 按 `hint` 加日期/时间列（如 `Date,Time,Global_active_power`） |
| 上传报 `E_HEADER_INVALID` | 空列名 / 重复列名 | 按 `hint` 给重复列名加序号 |
| 上传报 `E_ENCODING` | 文件非 UTF-8/GBK | 另存为 UTF-8 后重传 |
| 上传后报表 `status=pending` 不见了 | 超过 `UPLOAD_PENDING_TTL_HOURS` 被回收 | 重新上传并**及时调 confirm** |
| 执行报 `E_CODE_FORBIDDEN`（不支持 import） | 模型写了白名单外的 import | 白名单已放行预置库（`pandas/numpy/plotly`）+ 提示词要求不写 import；其余 import 属真实拦截，查看 `rule_id` |
| 分析结果为空表 | 条件无匹配（如该月份无数据） | 属正常业务结果；换时间范围再问 |
| 图表不出图但表格有数据 | 数据形状不支持该图型 | 属**降级不报错**；换图型或看 `E_CHART_UNSUPPORTED` 的 `hint` |
| 前端页面空白 / 改了代码不生效 | dev server 缓存异常（曾遇 Vite 对单模块缓存空产物） | **重启 dev server**；必要时删 `node_modules/.vite` |
| 页面能开但接口全 404 | 生产部署未配 `/api` 反代 | 按 9.3 在静态服务器/网关配置反代 |
| 评测批次一直 `running` 不动 | 模型调用卡住；或额度耗尽导致逐题失败重试 | 查后端日志与额度；`GET /eval/runs/{code}?include_questions=false` 看进度 |
| 评测报告下载 400/404 | 批次未完成（400）/ 报告文件缺失（404） | 等批次 `finished`；或重跑批次生成报告 |
| 查看接口很慢（个人中心/评测历史） | 记录量大、单页拉全量 | 用分页参数；详情用 `include_questions=false`（轮询时） |
