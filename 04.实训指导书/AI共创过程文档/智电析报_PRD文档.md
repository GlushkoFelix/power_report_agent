## 1. 文档概述

### 1.1 文档目的

本文档面向「智电析报——基于LLM的能源电力报表智能分析Agent」的开发全过程，用于：

1. 明确系统的功能边界、业务规则与验收标准，作为开发、测试、验收的唯一需求依据；
2. 固化**用电报表的数据口径**（量纲换算、未计量用电公式、两套正交拆分、比率类字段语义），避免大模型与开发者在数据计算上产生口径分歧；
3. 作为后续 UI/UX 设计文档、数据库设计文档、API 接口文档、测试报告的输入；
4. 作为「AI 共创开发」流程中喂给 AI 编程助手的核心上下文材料。

### 1.2 文档范围

| 范围 | 说明 |
| --- | --- |
| 包含 | Web 端报表上传、Schema 理解、自然语言对话分析、Text2SQL 与 pandas 代码沙箱执行、图表与表格联动、多轮追问、评测模块、用户管理、本地部署 |
| 不包含 | 实时数据采集（本系统只分析上传的离线报表）、用电负荷预测与优化调度、电费结算与账单出具、系统内置向量知识库（RAG 语料仅作为 AI 共创素材交付，不进入运行时） |

## 2. 产品背景

### 2.1 行业背景

能源电力行业日常产生大量用电报表数据。园区能耗管理员、售电公司分析师与企业设备管理人员需要频繁开展用电量统计、峰谷时段分析、异常用电识别等工作。传统分析流程依赖专业人员编写 SQL 或手工操作 Excel，门槛高、周期长，管理层与非技术岗位难以直接用自然语言获取数据结论。

### 2.2 问题现状

| 痛点 | 具体表现 |
| --- | --- |
| 工具门槛高 | 需要掌握 SQL 或 Excel 透视表/公式，非技术岗位无法自助分析 |
| 口径不统一 | 功率（kW）与电量（kWh）混用、总量与分表口径混算、比率类字段被求和，导致结论错误且难以察觉 |
| 重复劳动多 | 同一套日报/月报统计口径每月重复计算，无法沉淀为可复用资产 |
| 结论不直观 | 纯数字表格难以呈现趋势、峰谷结构与异常突变 |
| 异常发现滞后 | 依赖人工比对，用电异常（尖峰、零值、缺采）不能及时暴露 |

### 2.3 产品定位

**面向非技术用户的对话式用电报表分析助手**：用户上传用电报表 CSV，用自然语言提问，系统自动完成「问题解析 → SQL/分析代码生成 → 受控沙箱执行 → 图表绘制 → 文字解读」，把数据查询与分析能力下放给非技术人员。

产品形态定位为**轻量级分析工具**，而非数据平台：不做数据接入调度、不做建模预测、不做实时监控。

### 2.4 同类方案对比

| 维度 | 通用 BI 工具 | 开源 ChatBI（如 PandasAI） | 智电析报 |
| --- | --- | --- | --- |
| 上手方式 | 需拖拽建模与配置 | 对话式，但需自行提供数据与提示词 | 上传 CSV 即可对话 |
| 领域口径 | 无行业口径 | 无行业口径，易算错量纲 | 内置电力报表口径规范与 Schema 注入 |
| 代码安全 | 不涉及 | 直接执行生成代码，风险高 | sqlglot 白名单 + RestrictedPython 沙箱 |
| 多轮上下文 | 一般有 | 依赖聊天历史，条件易丢失 | 结构化 slot 持久化，条件可显示可编辑 |
| 评测体系 | 无 | 无 | 内置 ≥100 题评测集与自动化判分 |

## 3. 产品目标

### 3.1 业务目标

1. 为能耗管理与电力分析人员提供「上传报表 → 对话提问 → 图表结论」的一站式分析入口；
2. 将一次报表分析的平均耗时从「小时级人工写 SQL」压缩到「分钟级对话」；
3. 统一用电报表口径，让总量、分表、峰谷、未计量用电等指标在同一套规则下计算，杜绝量纲混算。

### 3.2 技术目标（可量化）

| 编号 | 目标项 | 指标 | 验证方式 |
| --- | --- | --- | --- |
| G1 | Text2SQL/代码执行正确率 | ≥ 85% | 评测模块自动比对结果集 |
| G2 | 平均响应时间 | ≤ 8 秒 | 评测运行时统计端到端耗时 |
| G3 | 首字响应时间 | ≤ 2 秒 | SSE 首个事件到浏览器的时间 |
| G4 | 评测问题集规模 | 120 题（任务书要求 ≥100 题） | 覆盖 6 类提问类型 |
| G5 | 分析结论准确性 | 关键数值命中率 ≥ 90% | 规则判定 + 抽样人工复核 |
| G6 | 沙箱安全 | 危险代码 100% 被拦截 | 安全用例集（≥ 20 条恶意样例） |
| G7 | 上传解析能力 | 单文件 ≤ 200MB 可解析 | 边界测试 |

### 3.3 非目标（明确不做）

1. 不做用电负荷预测、电价优化、设备诊断等需要额外建模的任务；
2. 不做电费结算与账单出具（不内置电价，仅提供可选的单价换算示例）；
3. 不做系统内置向量知识库问答（RAG 语料仅作为交付物与 AI 共创素材）；
4. 不做多租户与组织级权限管理（仅用户级数据隔离）；
5. 不做移动端原生 App（响应式适配移动端浏览器即可）。

> **本版本对"系统管理员"的落地口径（v1.19.3 明确，v1.19.4 需求方确认）**：上表是**用户画像与诉求**，
> 不等于角色权限模型。本版本**不做 RBAC**：`users` 表没有 `role` 列，评测中心对**所有登录用户**开放，
> 账号级差异只有"数据隔离"（他人会话 / 报表 / 记录一律 403 / 404）。
> **需求方确认（2026-09-16）：既然用户间已做数据隔离，即不做管理员权限功能**——P2 条款保留备查，本版本不实施。
> 理由：① 任务是单机实训项目、无多租户运维场景；② 评测中心本身不产生业务副作用（只读题库 + 跑批次），

> 前端菜单与全部接口的归属校验，收益与工作量不匹配。
> 若后续需要（P2）：最小方案 = `users.role`（`user` / `admin`）+ 依赖项里加 `require_admin`
> + 仅对"用户管理""题库维护"两类接口生效（评测中心仍开放）；表结构变更见数据库设计文档 5.2。

### 5.2 模块 F1：数据源接入与 Schema 理解

#### F1.1 CSV 上传与校验

| 项 | 内容 |
| --- | --- |
| 输入 | 用户选择的 `.csv` 文件（也支持 `.txt` 分号分隔文件，如原始数据集） |
| 处理 | ① 扩展名与大小校验（≤200MB，超限 413 `E_FILE_TOO_LARGE`）；② 编码探测（UTF-8 / UTF-8-BOM / GBK / GB18030）；③ 分隔符探测（`,` `;` `\t` `|`）；④ 表头校验（非空、无重复列名）；⑤ 时间列识别（支持 `Date`+`Time` 双列、单列 datetime、多种日期格式如 `16/12/2006`、`2020-07-01`） |
| 输出 | 校验通过 → 返回推断结果预览（列名、推断类型、前 20 行、**行数**）；不通过 → 返回具体错误码与 `data.hint` 修复建议 |
| 验收 | 上传原始 `household_power_consumption.txt` 能成功识别 9 列、识别 `Date`+`Time` 组合为时间列；缺少时间列的文件返回 `E_NO_TIME_COLUMN` 并提示 |

**两段式落盘与状态**（v1.10.0 落地）：`upload` 阶段**全量解析一次**（分块流式，不采样），把清洗后的数据写成
**规范化中间文件**（与原始文件同目录、同生命周期），元数据落 `uploaded_reports.status='pending'` 与
`upload_files.status='parsed'`；`confirm` 阶段只做「建表 + 灌数 + 建索引」的 IO 工作，成功后删除中间文件。
好处是 200 万行只解析一次（N4 的 60s 预算不被吃两遍），且预览里的行数、质量报告都是**真实值**而非估算。
`pending` 上传超过 **24 小时**未确认时，由启动时与每次上传前的**惰性清理**回收（删元数据行 + 删落盘目录）；
用户若只是想找回传了一半的文件，重新上传同一份即可命中 sha256 复用。

#### F1.2 字段类型推断与时间列识别

- 数值列：可完整解析为数值 → 判为数值型，并统计 min/max/mean/null 比例；含 `?`、`None`、空字符串等缺失标记统一归一为缺失值。
- 时间列：识别后生成标准时间戳字段，并额外派生 `year`/`month`/`day`/`hour`/`weekday`/`is_weekend` 维度列，供对话提问使用。
- 比率列：列名含 `ratio`/`rate`/`factor`/`coverage` 等关键词时，标记为**比率型（不可求和）**。
- 结果随 Schema 一起入库，供 F1.4 与前端字段面板使用。
- **标准时间戳列统一命名 `dt`**（与预置 `report_minute.dt` 一致），派生列统一为
  `year`/`month`/`day`/`hour`/`weekday`/`is_weekend`（与预置表同名同义）；源表已有同名列时保留原值不覆盖。
- **列名规范化**（v1.10.0 落地）：物理列名一律为 **ASCII 小写下划线**（避免中文标识符在 SQL 里漏双引号导致
  语法错误）。规则为「内置词典翻译 + `col_n` 回退」——词典命中（如 `总用电量` → `total_kwh`）则用语义英文名，
  未命中则回退 `col_<序号>`；**原始列名保存在 `schema_json.columns[].origin_name`**，前端字段面板与注入文本
  并列展示原名与安全名，用户不会"丢失"自己的列名。

#### F1.3 动态建表入库

- 表名由文件名规范化生成：转小写 → 非字母数字下划线替换为 `_` → 冲突时追加序号（如 `report_daily_2`）；
  **文件名净化后为空**（例如纯中文文件名）时回退为 `uploaded_<时间戳后缀>`。
- 同时生成安全列名（`sanitize` 后的英文列名），**原始中文列名作为注释保留**在 Schema 元数据中（`origin_name`）。
- 入库 SQLite，并建立时间列（`dt`）与常用维度列（`year`/`month`/`day`/`hour`）索引。
- **灌数分批提交**（默认 5 万行/批）：`reports.db` 是回滚日志模式，写事务会独占全库，分批提交把写锁持有
  时间切成小段，保证上传期间其他用户的预览/查询不被长时间阻塞；失败时以 `DROP TABLE` 整体回滚
  （动态表本身可丢弃），元数据落 `status='failed'` + `error_message` 待重传。
- **动态表归属与权限**：用户上传生成的动态表**同样落在 `reports.db`**，与预置表适用完全相同的权限规则——**只由「上传入库服务」写入，LLM 生成的 SQL/代码永远只读**（详见 7.4 约束说明）。
- 预置 5 张报表（见第 8 章）在系统初始化时写入 `reports.db`，作为默认数据源。

#### F1.4 Schema 描述文本生成

- 生成结构：表名 → 一句话表说明 → 数据范围（时间起止/行数）→ 字段清单（字段名、类型、单位、口径说明、可否求和、示例值）→ **口径红线规则**（第 8 章规则的机器可读摘要）→ 常用问题示例。
- 该文本同时用于：① 注入系统提示词；② 前端「数据字典」面板展示；③ 导出为 `schema_text.md` 交付物。
- 长度控制：单表 Schema 文本 ≤ 2000 tokens（超出时对示例值裁剪、字段说明压缩）。

**实现（v1.11.0 落地，交付物 3）**：

| 项 | 预置 5 张报表 | 用户上传报表 |
| --- | --- | --- |
| 文本来源 | `02.data/schema/schema_text.md` **原文组装**（全局头 + 本表段落 + 「二、口径红线」+「三、SQLite 可用函数」+「四、常用问题示例」+ 使用提示），逐字不改写 | 由 `schema_json` + `quality_json` **生成**，生成时机在 `upload` 阶段并随 `schema_json["injection_text"]` 落库（零 DDL） |
| 红线 | 项目口径规则 **R1–R7** | **U1–U5**：U1 口径未知声明（不得套用 R1–R7）；U2 比率/均值列清单（不可 SUM，须分子分母分别求和）；U3 时间列用法（`dt` + 派生维度列不可 SUM）；U4 **本表真实质量提示**（重复时间戳数、缺口、恒定值列、越界行数）；U5 单位与量纲 |
| 常用问题示例 | 人工撰写 8 条 | **列名启发式 + 模板池筛选**（≤6 条；无电气特征命中时给 3 条通用兜底），完全离线、结果可复现 |
| 预算控制 | 不裁剪（交付物原文即权威） | 超预算按固定顺序降级：① 字段说明截断到 40 字 → ② 示例值只留 1 个 → ③ 示例问题减到 3 条；**字段清单骨架（字段名/类型/单位/可否 SUM）永不裁剪**，响应回显 `est_tokens` 与 `truncated` |

- **token 度量**：字符启发式（`est_tokens ≈ 中文字符数 × 1 + 其余字符数 / 4`），不引入 tiktoken —— Qwen 分词与 `cl100k_base` 本就不同，精确计数同样是近似，而字符估算零依赖、可断言测试。
- **一致性要求**：`GET /reports/{report_code}/schema` 的 `text` 字段与 `GET /system/schema-text` 的 `text` **同源同构**（前端数据字典与模型注入文本逐字一致，见 UIUX 5.3 区域 4）。

#### F1.5 数据质量报告

统计并展示：总行数、缺失行数与占比、各列缺失分布、重复行、时间轴缺口（与理论分钟数对比）、数值越界提示（如电压偏离 200–260V、功率为负）、恒定值列（如某时段分表长期为 0）、时间覆盖率（coverage）。

输出 `quality_report.json` 并在前端以卡片 + 表格形式呈现「清洗提示」。

#### F1.6 多报表管理与切换

- 报表列表：文件名、类型（小时/日/月/结构/分钟/用户上传）、时间范围、行数、上传时间、状态。
  **列表返回 `is_deletable`**（预置 `false`、上传 `true`），前端据此禁用删除按钮，不自行推断规则；
  已解析未确认（`pending`）的上传**不出现在列表**。
- 切换活跃报表：同一会话内切换后，后续提问与新对话默认作用于新报表，历史消息保留原报表标记。
- 删除报表：级联删除该报表的 Schema 元数据与关联分析记录（需二次确认）。
  **系统预置报表不可删除**——`DELETE` 返回 **403 `E_FORBIDDEN`**；上传报表的删除顺序为
  「标记 `deleted` + 落审计 → `DROP TABLE` → 删除元数据行」，
  元数据行删除会触发 `conversations.active_report_id` 置 NULL（会话仍可用，只需重新选择报表）与
  `upload_files`、`analyses` 级联；`DROP TABLE` 失败时置 `status='failed'` 留待重试，不静默丢失。
  删除**不执行 VACUUM**（空闲页留给后续上传复用），接口以 `freed_pages` 如实报告回收页数。

### 5.3 模块 F2：自然语言转 SQL 与分析编排

#### F2.1 问题解析与 slot 抽取

将用户问题解析为结构化 slot：

| slot | 说明 | 示例 |
| --- | --- | --- |
| `time_range` | 时间范围 | 2020 年 7 月 / 最近 30 天 / 全期 |
| `granularity` | 时间粒度 | 小时 / 日 / 月 / 年 |
| `metric` | 指标 | 总用电量 / 峰段用电量 / 未计量用电 / 最大功率 / 负荷率 |
| `dimension` | 分组维度 | 无 / 月份 / 星期 / 时段 / 设备（分表） |
| `filters` | 过滤条件 | 仅周末 / 仅工作日 / 电压 > 250 / 排除缺失日 |
| `compare` | 对比方式 | 无 / 同比 / 环比 |
| `intent` | 意图 | 查数 / 趋势 / 对比 / 占比 / 排行 / 异常 / 澄清 / 拒答 |
| `chart_hint` | 图表偏好 | 折线 / 柱状 / 饼图 / 表格 |

抽取失败或关键字段缺失时进入 F2.6 澄清流程。

**实现（v1.12.0 落地，交付物 4 第一批）**：

| 环节 | 落地方式 |
| --- | --- |
| slot 抽取 | **轻量模型**（`llm_model_light`，PRD 10.3 模型分级）+ 精简提示词，`response_format=json_object` 强制 JSON；提示词附带该表「可用指标 / 分组维度」清单，降低编造列名的概率；输出只保留上表 8 个字段，未知字段丢弃后再落 `conversations.slot_json` |
| SQL 生成 | **主力模型**（`llm_model_main`），同样 JSON 模式（`{"sql": "...", "reason": "..."}`），SQL 作为字段可避免"从代码块里抠 SQL"的解析脆弱性 |
| 输出解析 | **三层容错**：`json.loads` → `json-repair` 修复 → 正则提取 ```json 代码块/最外层花括号；三层都失败按 `E_LLM` 处理（本批不调模型重试，重试环留后续批次） |
| 结果解读 | 主力模型，输入**只含已执行完成的表格数据**（最多 50 行）与数据质量提示，输出 `{"text", "key_numbers", "anomalies"}`；`key_numbers` 供"结论准确性"判分 |
| 失败归因 | 守卫拦截（`E_SQL_FORBIDDEN`，并落 `audit_logs(sql_blocked)`）/ 执行报错（`E_SQL_EXEC`）/ 输出不可解析（`E_LLM`）三类分别落 `analyses.error_code`，便于统计"格式错"与"SQL 写错" |

> 本批**不做**多轮 slot 继承：继承与澄清回路强耦合（追问缺条件时应先澄清），单独做继承会把半成品
> slot 直接拿去生成 SQL，产出"看似正常、范围错误"的答案（违背 P4）。`slot_json` 照常回写，供下一批
> 「继承 + 澄清」一并实现。

#### F2.2 SQL 生成与只读白名单校验

- 生成 SQLite 方言 SQL；执行前经 `sqlglot` 解析并校验：
  - 只允许 `SELECT`（含 `WITH` 子查询）；
  - 拒绝 `INSERT`/`UPDATE`/`DELETE`/`DROP`/`ALTER`/`CREATE`/`ATTACH`/`PRAGMA`/`VACUUM` 等；
  - 拒绝多语句（分号拼接）；
  - 表名必须在当前会话已注册的报表白名单内；
  - 强制追加 `LIMIT`（默认 1000 行）防止结果集爆炸；**对聚合查询，`LIMIT` 仅作为安全兜底，不改变业务语义**（聚合结果行数远小于上限）；明细查询若被截断，必须在返回结果中标注“结果已截断（上限 1000 行）”；
  - 校验失败返回结构化错误 `E_SQL_FORBIDDEN`，并触发一次带错误信息的重写。
- 校验通过后在 `reports.db` 的**只读连接**上执行（`mode=ro`）；该库在应用运行期不接受任何写入——报表数据只能由数据清洗脚本（离线）或上传入库服务（受控代码、独占写连接、事务提交即关闭）产生，从根上保证分析对象不被篡改。

> **实现（v1.16.0 落地，交付物 5 沙箱/守卫批次）**：守卫第 ⑤ 步新增 **R3 混加检测**
> （`sqlguard:r3_mixed_partition`）——**同一个加法表达式**（sqlglot `Add` 节点子树）内同时出现
> 「按用途」列与「按时段」列即拒绝；并列选择多列、单套拆分内部求和（峰+平+谷）放行。
> 列语义映射与图表层**共用同一份来源**（`chart_service.PURPOSE_SERIES` / `PERIOD_SERIES`），
> 杜绝两处口径漂移——F3.1 的"R3 SQL 层待办"就此销项。"校验失败触发一次带错误信息的重写"
> 由 F2.4 的重写链统一实现（见下）。

#### F2.3 pandas 分析代码生成与沙箱执行

- 生成代码的输入约定：沙箱内预置 `df`（当前活跃报表的 DataFrame）、`pd`、`np`、`plotly.express as px`、`plotly.graph_objects as go`；输出约定：把最终结果赋值给 `result`（DataFrame/Series/标量），把图表赋值给 `fig`（可选）。
- 执行前 AST 预检：禁止 `import` 非白名单模块、禁止访问 `__` 双下划线属性、禁止 `open`/`eval`/`exec`/`compile`/`__import__`/`subprocess`/`socket`/`os`。
- 在 RestrictedPython 沙箱中执行，限制：执行超时（默认 10s）、结果集大小（≤5000 行）、内存占用（≤512MB）、禁网络与文件写。
- 超时或异常返回结构化错误（错误类型 + 堆栈精简 + 行号），供 F2.4 重试。

> **实现（v1.16.0 落地，交付物 5 沙箱/守卫批次）**：
>
> | 环节 | 落地方式 |
> | --- | --- |
> | 工具路由 | 生成阶段（prompt-v3.0）模型**自报 `route`（sql/pandas）+ 理由**，`sql`/`code` 二选一非空；模型未自报时按"给了什么"推断，兜底 sql。prompt 给出适用场景与反例（聚合/分组/排名 → SQL；移动窗口/迭代计算/复杂派生 → pandas），对应 T2「双工具路由选错」的缓解 |
> | AST 预检 | `app/core/code_guard.py`（纯函数，主/子进程各跑一道）：import 白名单（math/statistics/datetime，pandas 等已预置**禁止重复 import**）、双下划线名称/属性、危险调用（open/eval/exec/compile/__import__/getattr/globals/…）与属性形式危险方法（.system/.popen/.unlink/…）、危险模块名作裸名；**未过预检的代码根本不进沙箱**（400 `E_CODE_FORBIDDEN`） |
> | 执行隔离 | **子进程隔离**（`app/services/sandbox_service.py`，spawn 进程池常驻 1 worker）：超时用 `async_result.get(timeout)` **真强制**（超时 terminate worker、池丢弃重建，主进程永不挂）；worker 崩溃（OOM 等）由池重建兜底。**与 PRD 字面的差异**：原定 RestrictedPython 进程内沙箱，实测在 Windows 上 `signal` 超时不可用、内存超限（C 扩展分配）根本拦不住——改为"AST 预检 + 子进程隔离"双防线；**RestrictedPython 8.5 已装但未接入**，保留为进程内第三道防线的候选。内存上限 `resource.setrlimit(512MB)` 仅 POSIX 生效，Windows 属"尽力而为"（进程隔离保证崩溃不影响服务） |
> | 数据供给 | worker 内从 `reports.db`（`mode=ro`）把活跃报表整表读成 `df`（与 SQL 路径同一只读库） |
> | 结果回传 | `result`（DataFrame/Series/标量）→ 与 SQL 路径同构的 columns/rows（≤5000 行，超出截断标记）；`fig` → plotly figure JSON（剔 template）。**fig 只作兜底**：图表统一由图表服务生成（保证语义色/R3 收敛/`layout.meta` 口径一致），仅当图表服务画不出时用沙箱 fig 补位 |
> | 留痕 | 代码原文落 `analyses.code_text`、路径落 `route`、重试次数落 `retries`、是否换路落 `path_switched` |

#### F2.4 执行失败自愈重试

- 最大重试 2 次；每次把「失败代码 + 错误信息 + Schema 相关片段」回灌给模型要求修正。
- 首次失败后允许**换路径**：SQL 失败 → 尝试 pandas 路径；pandas 失败 → 尝试 SQL 路径。
- 仍失败则返回明确的失败反馈（含失败原因、已尝试路径），**严禁编造结果**。
- 全链路记录：每条分析记录保存原始问题、slot、生成 SQL、生成代码、执行结果快照、图表 JSON、重试次数、耗时。

> **实现（v1.16.0 落地，交付物 5 沙箱/守卫批次）**：重试额度比原设计**收紧**——
>
> - **带错误重写一次**（SQL 与 pandas 共用额度）：守卫拦截 / 执行报错 / 沙箱超时 / 代码运行报错，
>   把 `rule_id` / SQLite 报错原文 / `error_type` + 行号 + 堆栈尾行回喂模型（temperature=0）；
> - **换路一次**（仅 SQL → pandas 单向，且**仅限执行类失败**）：重写后仍执行失败才换路，
>   `analyses.path_switched=1` 留痕；
> - **安全拦截不换路**：`E_SQL_FORBIDDEN` / `E_CODE_FORBIDDEN` 的重写必须留在原路径——
>   否则"删表"这类恶意请求会换来一次无关的 pandas 成功结果，且多给一次生成机会；
> - `E_LLM`（输出不可解析）/ `E_OUT_OF_SCOPE` / `E_VALIDATION` 不参与重试（重写也不会好）；
> - 额度用尽仍失败 → 落库 `status='failed'` + 最后一次错误，`retries` / `path_switched` 留痕；
>   每次生成调用在 `llm_calls.is_retry=1` 记录重试链。
> - 生成调用上限 3 次（首次 + 重写 + 换路），保住 G2 平均响应 ≤8s 的预算。

#### F2.5 结果文字解读与异常识别

- 解读内容要求：① 直接回答数字结论（含单位）；② 趋势/结构描述（最大最小、占比、同比环比）；③ 异常提示（如有）；④ 口径说明（用了哪张表、哪个时段、是否含缺失日）。
- 异常识别规则（可在 config 中配置阈值）：
  - 用电量偏离近 30 天均值 ±3σ；
  - 单日功率为 0 或负值；
  - 连续多日数据缺失；
  - 峰段占比异常（超过近 30 天均值一定比例）；
  - 电压越界（**<210V 或 >250V**，阈值按实测电压分布 223–254V 收紧；且要求**当日累计越界 ≥ 30 分钟**才计入异常，避免零星 1 分钟越界造成噪声——实测"≥1 分钟"会命中 110 天、"≥30 分钟"命中 34 天）。

#### F2.6 拒答与澄清策略

| 情形 | 处理 |
| --- | --- |
| 问的字段不在 Schema 内（如电价、水费） | 明确拒答：说明报表不含该字段，并给出可问的相近指标建议 |
| 关键 slot 缺失（如「用电量多少」未给时间） | 主动澄清：给出 2–3 个候选时间范围按钮，用户点选即可 |
| 问题涉及预测/建议（如「下个月会用多少电」） | 拒答并说明系统只做历史数据分析，不做预测 |
| 诱导越权（如「把表删了」「执行 ls」） | 拦截并提示不支持该操作，记录安全日志 |

**实现（v1.15.0 落地，交付物 4 第四批）**：「关键 slot 缺失 → 主动澄清」已落地，触发为**混合式**：
`metric` 缺失 → 规则必澄清；`time_range` 缺失 → **不澄清**（继承 / 默认「全期」，避免每问必澄清）；
语义级歧义（报表/指标/粒度歧义）由模型输出 `intent=澄清 + missing_slot` 触发（模型优先、规则兜底）。
澄清选项由**规则查表生成**（零 LLM，value 值域绝对合法）；卡片经 SSE `clarify` 事件下发，
回填走 `POST /analysis/clarify` 就地继续。其余三类（超范围/预测/越权）由提示词 + 守卫 + 评测覆盖。

### 5.4 模块 F3：可视化输出

#### F3.1 图表自动生成

- 后端依据 `intent` + 数据结构选择图表类型：时间序列趋势 → 折线；分类对比/排行 → 柱状；占比/结构 → 饼图或环形图；相关性 → 散点。
- 后端生成 Plotly figure 并序列化为 JSON，经 SSE 推送给前端由 `Plotly.react` 渲染；数据表格与图表使用同一份结果数据。

**实现（v1.14.0 落地，交付物 4 第三批）**：

| 环节 | 落地方式 |
| --- | --- |
| 数据来源 | 与 `table` 事件**同一份结果快照**（原文要求），图表生成为**本地计算、不调 LLM**；`chart` 事件固定在 `table` 之后、`narrative` 之前（UIUX 8.1 的 ≤7s 卡点） |
| 列语义识别 | 按列名 + `schema_json.columns[]` 的 `unit`/`agg` 识别：时间列（`dt`/`dt_hour`/`date`/`year_month`）、时间维度列、指标列、比率列（R6 关键词）、维度列（`period` 列靠**取值**判定拆分归属；`peak_hour`/`days_in_month`/`expected_minutes` 等编码值列不算指标） |
| 类型选择 | `slot.chart_hint` 优先 + **数据形状校验**（饼图要求数值非负且 ≥2 类；折线要求时间轴且 ≥2 点；散点要求两个数值列），不合法按形状兜底（时间+数值→折线、分类+数值→柱状、`intent=占比`→饼图、两数值列→散点、其余→表格）；`rerender` 显式指定的类型是**指令**，不支持则 400 `E_CHART_UNSUPPORTED` |
| 红线 R3（图表层） | 指标列同时出现用途类与时段类 → 只画一套（优先级 `slot.dimension` → `slot.metric` → 默认按用途），被略去的列回显 `dropped_columns` 并附 `r3_note`；**分类轴不受影响**（"某一路的时段分布"属单一拆分，合法） |
| 量纲 | 多指标列按 `unit` 分组：同量纲多系列；跨量纲只画与 `slot.metric` 同单位的一组（`excluded_columns` 回显）；散点例外（两轴各带单位，本就用于跨物理量关系） |
| 点数 | 分类类图（饼/柱）类别数 > 12 → 取前 12 并把余项**合并为「其他」**（直接截断会让占比之和 ≠ 100%，属口径错误）；折线/面积/时间轴柱状 > 500 点**等间隔抽稀**（保留首末点），均回显 `top_n`/`merged_count`/`downsampled_from`；**时间轴不做「其他」合并**（日期归堆没有意义） |
| 缺采断开 | 时间轴相邻点间隔 > 粒度基准 × 1.5 → 插入 `y=null` 断点（**不插值**）+ 缺采灰 `#ADB5BD` 虚线连接段；必须在抽稀**前**计算缺口（抽稀会把间隔拉大造成误判） |
| 语义色 | 峰/平/谷用语义色板、用途用用途色板（UIUX 4.2），由后端写进 figure；无语义归属的多系列用**青灰色阶**（刻意避开全部语义色，防止"总电量"被读成"平段"）；单系列折线用平段蓝（UIUX 7.2）；折线自动标注峰值点（峰段橙红） |
| 主题边界 | 后端 figure **只写语义色与文案**，不写 `paper_bgcolor`/`plot_bgcolor`/`font.color`/网格色，并剔除 plotly 内置 `template`——亮/暗主题由前端在 `Plotly.react` 时覆盖；口径标记（类型/单位/TopN/合并/R3）写进 **`figure.layout.meta`**，随 `chart_json` 落库，详情页重新打开也看得到 |
| 失败降级 | 任何画不出的情形**不阻断主流程**：仍发 `chart` 事件但 `figure=null` + `fallback="table"` + `reason`，`status` 仍为 `success`、解读照常；`analyses.chart_json` 写 NULL（不写空对象） |

> **待办销项（v1.16.0，交付物 5 沙箱/守卫批次）**：R3 的 SQL 层混加检测**已落地**——
> `sql_guard` 第 ⑤ 步用 sqlglot AST 检出"同一加法表达式内同时聚合用途列与时段列"
> 并拦截重写，列语义映射与图表层共用同一份来源（见 F2.2 实现注记）。

#### F3.2 图表类型切换与重绘

- 前端提供图表类型切换（折线/柱状/面积/饼图/散点/表格），切换时使用已返回的数据重绘，**不重复调用大模型**。
- 支持聚合粒度切换（小时/日/月）与 topN 调整的重绘。

> **实现（v1.14.0 落地，交付物 4 第三批）**：`POST /charts/rerender` 请求体
> `{record_code, chart_type?, granularity?, top_n?, sort?}`（9.1 原文只给路径，请求体为本批契约）。
> 换类型 / topN / 排序用**已返回的数据**重绘；换粒度从**结果快照**重聚合（**只能由细变粗**；
> 聚合方式按量纲：`kWh`/分钟求和、`kW`/`V`/`A` 取均值、比率列**丢弃**——R6 要求分子分母重算而快照里没有）；
> 不可重聚合 → 400 `E_GRANULARITY_UNAVAILABLE`。成功后把新 figure **回写 `analyses.chart_json`**
> （右栏切过的图在「我的分析记录 → 详情」保持一致），离线预览工具以只读方式（不落库）调用。
> 前端控件暴露折线/柱状/饼图/表格四种主类型（UIUX 5.1），面积/散点为本接口的可选扩展。

#### F3.3 图表与表格联动

- 图表某点/某柱被点击时，下方表格自动滚动定位到对应记录并高亮；表格行悬停时图上对应点高亮。
- 表格支持排序、分页、列宽调整。

#### F3.4 图表图片导出

- 前端使用 Plotly `toImage()` 导出 PNG（可选 2x 高清）；
- 后端 kaleido 提供相同内容的服务端导出兜底（**预留能力**：为后续 P2「导出 Word/PDF 报告」保留实现路径，本版本不提供界面入口）。

> **实现（v1.14.0 落地，交付物 4 第三批）**：本版本导出入口即前端 `toImage()`（2 倍图、亮色底）；
> `GET /analysis/records/{record_code}/chart.png` **保留端点但如实返回 501 `E_NOT_IMPLEMENTED`**
> （`data.hint` 指向前端导出）——本机未安装 kaleido（1.x 还需额外下载约 200MB 的 Chrome，对离线
> 演示是真实成本）。接入点已写好：`kaleido_available()` 探测 + 亮色底 2 倍图渲染，**环境里装上
> kaleido 后无需改代码即自动真实导出**；装了但缺浏览器时提示执行 `kaleido_get_chrome`。

### 5.5 模块 F4：多轮追问管理

#### F4.1 结构化 slot 提取与合并

- 每次用户提问先抽取「本轮增量 slot」，再按合并规则更新会话 slot：
  - 显式给出即覆盖（「改成 2020 年 8 月」）；
  - 未提及即继承（「只看周末的」保留原时间与指标，仅加 `filters`）；
  - 维度变更即替换（「再按月汇总一次」把 `granularity` 由日改为月，`time_range` 不变）。
- slot 持久化于 **`conversations.slot_json`**（控制面库），支持会话中断后继续、按会话回放。
  （**v1.19.5 校正**：原写"由 `langgraph-checkpoint-sqlite` 持久化"，当时实际未引入该库；**v1.19.31 起**该库已随状态图接入，
  用于**图级检查点**（`checkpoints` / `writes`，`thread_id = 会话编号`），但 **slot 的权威来源仍是 `conversations.slot_json`**——
  检查点存的是"跑到哪一步"，不替代业务字段。取值与写入时机见数据库设计文档 5.3 / 5.11；编排形态见 6.6 与架构文档 ADR-021）

**实现（v1.15.0 落地，交付物 4 第四批）**：

| 环节 | 落地方式 |
| --- | --- |
| 增量抽取 | `SLOT_SYSTEM`（prompt-v2.0）改为**增量抽取**：只输出本轮新提及/变更的字段，未提及填 null；输入附「会话现有条件」作为继承基线；`intent=澄清` 时附加 `missing_slot` 字段（不入 `slot_json`，仅作澄清决策） |
| 合并 | `slot_service.merge_slot(base, increment)` 纯函数：标量非 null 即覆盖、null 即继承；`filters` **同 field 替换、异 field 追加**（避免两条矛盾过滤并存）；本批无「显式清除」语义（清除属前端芯片交互） |
| 归一化 | `time_range` 仍缺 → 默认「全期」（与 UIUX 6.3 一致）；`intent=澄清` 归一化时重置 null |
| 基线 | `run_once(slot_base=…)`：chat/clarify 用**会话 slot_json**；**replay 用原记录的 slot_json**（增量抽取照常跑，保住「整轮重跑」，后续追问不污染并排比较） |
| 芯片编辑 | `POST /analysis/chat` 请求体新增可选 `slot_patch`（与 clarify 共用键白名单 + 类型/长度校验，**不做值域校验**）：先合入会话 slot 并持久化，再做本轮抽取——UIUX 6.3「编辑后重算」本批即可用 |
| 切表重置 | 切换活跃报表（`PATCH /conversations` 与 `/reports/{code}/activate` 共用路径）**即清空会话 slot**：旧表的 metric/dimension/filters 对新表可能不存在，不维护跨表通用白名单 |

### 5.6 模块 F5：评测模块

#### F5.1 评测问题集管理

- 规模 **120 题**（满足任务书"不少于 100 条"要求），每题字段：`id`、`question`、`type`、`difficulty`、`report_table`、`gold_sql`（或 gold 代码）、`gold_answer`（真实执行得到的标准结果）、`key_numbers`（用于结论判定的关键数值）、`tags`。
- 题型覆盖与占比：

| 题型 | 占比 | 示例 |
| --- | --- | --- |
| 统计（总量/均值/极值） | 25% | 2020 年 7 月总用电量是多少 |
| 聚合分组（按时段/月份/星期/设备） | 20% | 各月用电量分别是多少 |
| 对比（同比/环比/分组对比） | 15% | 2020 年 7 月比 2019 年 7 月增长多少 |
| 异常分析 | 15% | 哪些日期用电量异常偏高 |
| 结构占比 | 15% | 厨房用电占总用电的比例 |
| 多轮追问 | 10% | 先问全年趋势，再追问「只看周末的」 |

- 问题集中包含**口径陷阱题**（约 15%）：涉及量纲换算、比率不可求和、两套正交拆分不可混加、结构报表「全期」行不可与年份行同时求和。

> **实现（v1.17.0 落地，交付物 8 / M5）**：题库是**脚本产物**而非手写数据——
> `python 01.code/scripts/04_build_eval_set.py` 按 6 类题型 × 3 难度批量生成题面，
> **每题 `gold_sql` 对真实 `reports.db` 执行反算** `gold_answer_json` 与 `key_numbers_json`
> （手写 gold 一旦写错，会把正确回答判成错误且极难发现）；产物为
> `02.data/eval/eval_questions.json`（快照，可 diff/入档）+ `eval_questions` 表（幂等重建）。
> 脚本内置 `--check` 校验分布（G4 验收口径）：**实测 120 题**（stat 25 / agg 25 / compare 20 /
> anomaly 20 / structure 15 / multi_turn 15），陷阱题 **18 题 = 15%**（R1×5、R3×4、R6×5、R7×4），
> 每题的 `gold_answer_json` 与 `key_numbers_json` 均非空。**多轮题的编码约定**：`question` 内两轮
> 用换行分隔（第一轮在前），跑批时顺序提问、**判分只看最后一轮**（避免为多轮另立列而改 DDL）。

#### F5.2 批量评测执行与结果集比对

- 执行：逐题走完整 Agent 链路（可配置是否包含文字解读与图表生成）。
- 判分（执行正确率）：
  1. 生成 SQL 在库上执行得到结果集 R_gen；gold 结果为 R_gold；
  2. 列名归一化 + 列序无关匹配；行序无关（排序后比较）；
  3. 数值容差 `max(1e-6, |值| × 1e-3, 5e-3)`（普通列）/ `max(1e-4, |值| × 1e-3, 5e-3)`（比率列）：**允许"展示级舍入"**——模型常输出 `ROUND(x, 2)`，误差上界即半个末位 0.005；低于该量级的差异不算算错（v1.19.6 调整，原为 1e-6 绝对容差，见下方说明）；
  4. R_gen 与 R_gold 完全一致 → 正确；否则 → 错误，并记录差异类型（列缺失/行数不符/数值偏差/类型不符）。
- 判分（结论准确性）：检查 `key_numbers` 是否出现在文字解读中（数值按有效位数匹配），命中率 ≥90% 为达标。

> **实现（v1.17.0 落地）**：`app/services/eval_service.py` 的判分引擎为**三级兑底**
> （全不过才判错并给 `diff_type`）：
>
> | 档 | 规则 | 解决什么 |
> | --- | --- | --- |
> | ① 列位置 | gold 列序即答案列序，**行序无关**（排序后逐格比对，数值容差 1e-6 / 比率 1e-4） | 常规情形（含模型自起别名，位置即语义） |
> | ② 列名归一 | 列**顺序不同**时按归一化列名（小写+去符号+同义表 `total≈total_kwh`、`cnt≈days`）重排再比 | 模型调换列序 |
> | ③ 单列格式宽松 | **仅单列结果**：日期 `2006-12-17` 与 `2006-12-17 00:00:00` 视为同值 | 日期/时间写法差异 |
>
> 容差按 PRD 字面取**绝对**值（不做相对容差）；`diff_type` 归因：`column_count_mismatch` /
> `row_count_mismatch` / `value_mismatch` / `type_mismatch` / `empty_result` / `runner_error`。
> **为什么第③档限定单列**：多列时"忽略列身份"会把"列搞反"误判成正确（决策 8-2 的缓解条款）。
> 结论命中判定：数值按 0.5% 相对容差或千分位整形匹配（解读常把数字四舍五入），
> `kind=label` 的关键项（如"最高的月份是 1 月"）按文本包含判定；输出命中率与漏项清单。
> **执行模式 `impl`**（`POST /eval/runs` 请求体）：`real`（必须配置了模型 Key `LLM_API_KEY`，
> 否则 400 **不静默回落**）/ `selfcheck`（**逐题按 gold_sql 回放** + 由 key_numbers 生成的标准解读，
> 用于一条命令验证「题库 → 链路 → 判分 → 指标 → 报告」全通，**正常应≈100%**；报告置顶标注
> "不代表模型能力"）/ `auto`（有 Key 走 real，否则 selfcheck）。多轮题按换行拆轮依次提问，
> 仅最后一轮参与判分。
>
> **判分容差调整（v1.19.6，真实评测暴露的"判分过严"）**：原 1e-6 绝对容差把"展示级舍入"也判成了错——
> 实测 gold `26.0179676902` vs 模型 `26.02`（差 0.002）、`79.5564333333` vs `79.56` 均落 `value_mismatch`，
> 而模型只是做了 `ROUND(x, 2)`。现改为 `max(绝对下限, |值| × 1e-3, 5e-3)`（`5e-3` = 半个末位，
> 仅 `|值| ≥ 0.01` 时生效，避免比率类小值被过度放宽），仍能拦住 0.5% 以上的真实偏差；
> 另新增**年月形态等价**：`'2006-12'` ≈ `12`、`'2006'` ≈ `2006`（模型惯用 `STRFTIME('%Y-%m', date)`、
> gold 用整数 `month` 列，**值对但写法不同**，实测 6 题被判 `type_mismatch`）。
> 回归用例：`tests/test_prompt_iteration.py`、`tests/test_eval.py::test_score_tolerance_numeric_and_percent`。

#### F5.3 统计与评测报告

- 输出指标：总体正确率、分类别正确率（题型/难度/报表）、平均耗时、P95 耗时、首字延迟、错误类型分布、重试次数分布。
- 生成 `eval_report.md` + `eval_result.jsonl`（逐题明细），支持与历史版本对比（正确率变化、回归失败的题目清单）。

> **实现（v1.17.0 落地）**：指标 = 总体/按题型/按难度/按陷阱题正确率 + 结论命中率 +
> 平均与 P95 耗时 + 重试总次数 + 差异类型分布 + 错误码分布 + 判分档命中分布
> （第一/二/三档各多少题，用于判断"正确率里有多少是靠宽松档兜住的"）。
> 报告为 **Markdown**（`GET /eval/runs/{run_code}/report` 直接下载），落
> `02.data/eval/reports/{run_code}.md`，含：自检警示（仅自检模式）/ 指标摘要 /
> 分类正确率表 / 差异与失败分布 / **bad case 归因** / 逐题明细表 / 错题复盘（生成 SQL vs 标准 SQL）。
> **逐题明细存 `eval_runs.result_json`**（TBD6 结论：**不拆 `eval_run_items` 表**，见下），
> 按题型/难度的聚合在 service 内读 JSON 完成。
> **如实记录的取舍**：① `first_token_avg_ms` 恒 NULL——LLM 客户端是单次 POST（非流式），
> 拿不到首字时间；② `llm_calls.eval_run_id` 在批次结束后**批量回填**（按 `analysis_id` 反查），
> 避免把评测 ID 穿透进分析链路。

#### F5.4 bad case 归因与迭代

- 归因分类：Schema 描述缺失 → 补字段说明；量纲/口径错误 → 补口径红线规则；SQL 语法错误 → 补少样本示例；slot 继承错误 → 补多轮规则；超出范围问题 → 拒答策略。
- 每次迭代记录「改动点 → 正确率变化」，写入评测报告，形成可追溯的优化闭环。

> **实现（v1.17.0 落地，启发式）**：错题按**优先级顺序**归入五类并在报告"bad case 归因"段落输出计数：
> ① 口径理解错误（口径陷阱题答错）；② SQL 语法与函数（被守卫拦截或执行报错，含 pandas 代码拦截）；
> ③ slot 继承错误（多轮题答错）；④ 执行失败未重试成功（链路失败或触发过重试仍错）；
> ⑤ 结果口径偏差（链路正常但数值/列/行不一致）。UIUX 5.4 的四类归因卡片由前四类直接驱动。
> **未落地部分（如实标注）**：「改动点 → 正确率变化」的**跨批次对比**与 Schema/提示词级归因
> （如"Schema 描述缺失 → 补字段说明"）需前端评测页与多批次基线管理，属后续批次。

> **TBD6 结论（v1.17.0，交付物 8 定案）**：**不拆 `eval_run_items` 表**——保持 PRD 7.4 /
> 数据库设计 5.7 的"10 张表"约定，逐题明细（生成 SQL/代码、是否命中、`diff_type`、耗时、
> 错误码、判分档、分析记录 ID）以 JSON 存 `eval_runs.result_json`；120 题明细约 200–400KB，
> 单列 TEXT 足够；按题型/难度的聚合在 service 内读 JSON 完成（当前无 SQL 聚合需求）。

### 5.7 模块 F6：用户管理

| 功能 | 需求 |
| --- | --- |
| F6.1 注册 | 用户名（`^[A-Za-z0-9_]{4,20}$`，唯一且**不区分大小写**，服务端统一小写存储）+ 密码（**8–64 字符**，须同时含字母与数字，且 UTF-8 编码后 **≤ 72 字节**——bcrypt 硬限制）；密码 bcrypt 加盐哈希存储，禁止明文与可逆加密；**注册成功即自动登录并签发 JWT**（`{ token, token_type, expires_at, user }`） |
| F6.2 登录 | 校验通过后签发 JWT（有效期 24h）；连续 5 次失败锁定 5 分钟，**锁定期内登录返回 429 且不再校验密码**；**锁定到期不清零失败计数（仅成功登录才清零）**；用户名不存在与密码错误返回同一文案（防账号枚举）；`is_active = 0` 返回 403；支持退出登录（前端清除 token，服务端落 `auth_logout` 审计） |
| F6.3 会话与记录 | 会话列表（标题自动取首问摘要）、消息历史、分析记录列表（问题/SQL/代码/结果/图表/耗时）；支持重命名、**置顶（每用户上限 5 条，超出自动挤出最早置顶，对应 UIUX 5.1「最多 5 条」）**、删除；支持按关键词与时间筛选；消息历史采用**游标式分页**（默认最近 50 条） |
| F6.4 数据隔离与删除 | 所有报表、会话、分析记录均带 `user_id`，接口层强制校验归属；删除报表时级联清理；**个人中心四件事（v1.19.12 起闭环）**：编辑资料（显示名 / 邮箱）、修改密码（校验当前密码）、**清空历史记录**（`scope=records` 只清分析记录、`all` 连会话与对话历史；均二次确认）、**删除账号**（密码 + 用户名双确认 → 级联删除上传报表 / 会话 / 消息 / 分析记录 / 评测批次，**安全审计日志保留且归属置空**）；四类操作均写 `audit_logs` |

**安全要求**：接口鉴权采用 `Authorization: Bearer <token>`；上传目录按用户隔离；日志中对密码、token、文件路径脱敏；**认证类事件（注册 / 登录成功 / 登录失败 / 账号锁定 / 登出）与安全拦截事件全部写入 `audit_logs`**（`auth_*` 五类，见数据库设计文档 4.8）；生产环境建议启用 HTTPS（本机演示环境见部署手册）。

## 6. 非功能需求

### 6.1 性能需求

| 编号 | 指标 | 目标值 | 说明 |
| --- | --- | --- | --- |
| N1 | 首字响应 | ≤ 2s | SSE 首个状态事件（「正在解析问题」）到达浏览器 |
| N2 | 单轮平均响应 | ≤ 8s | 简单问数（不需澄清、不需重试）端到端；评测统计口径 |

#### 6.1.1 延迟优化与实测（v1.19.11，延迟专项三项）

> **背景**：正确率达标后，G2/N2（平均 ≤8s）与 G3/N1（首字 ≤2s）尚未验证。实测发现
> **98% 的耗时都在 3 次串行模型调用上**（slot 1.5–2.5s / gen_sql 3.0–3.2s / narrative 2.4–3.2s），
> 本地开销几乎为零；且**首字延迟其实不达标**——端点此前是"等链路跑完再回放事件"。

| 优化 | 做法 | 实测效果 |
| --- | --- | --- |
| **① SSE 真流式** | 新增 `EventSink`（list 子类覆盖 `append`，事件产生即回调入队）+ 端点 `_stream_run`（链路放 `asyncio.Task` 并发跑、边收边推；客户端断开即取消链路） | **首字 5,927ms → 10–16ms**（G3 达标）；事件真正增量到达（`status`→`slot`→`table`→`narrative`→`done`） |
| **② slot 规则快通道** | `slot_service.fast_slot`：**指标唯一 + 不含 40 个复杂语义拦截词 + 会话条件干净 + 时间可规则确定**四个条件同时成立才出手，否则照旧走 LLM；开关 `FASTPATH_ENABLED` | 命中 **2/10**（最简的两题），端到端平均 **8,387 → 7,937ms**；调用数 3.1 → 2.9 次/题 |
| **④ 阶段超时兜底** | slot 超 **6s** → `fallback_slot`（宽松规则）兜底继续；narrative 超 **8s** → **跳过解读**（表格/图表照给、`status` 仍 success、异常提示如实说明） | 压长尾（此前单阶段最长 21s）；简单问数端到端 **5.5s**、`slot` 段 **355ms** |

> **如实说明**：G2 的达成与**问题构成**强相关——按 N2 字面"简单问数"（stat/agg/compare）实测 **7.6–7.9s 达标**；
> 含多轮题的批次（多轮会跑两轮）会到 9s 上下。跨模型延迟也不同（narrative 段 deepseek 2.4s vs qwen3.8-flash 3.7s），
> 因此**归档数字应在最终选型模型上复测**。
| N3 | 单轮 P95 | ≤ 15s | 含图表生成 |
| N4 | 单文件解析 | 200 万行 ≤ 60s（**端到端实测达成**） | 首次上传解析 + 建表；**实测 207 万行：上传 32.1s + 确认入库 17.8s = 49.9s** |
| N5 | 报表列表/切换 | ≤ 1s | 直读元数据 |
| N6 | 并发 | ≥ 5 用户并发会话不降级 | 演示环境指标 |
| N7 | 大结果集保护 | 默认 LIMIT 1000 行 | 超出提示「结果过大，请细化条件」 |

> **N4 实测口径**（v1.10.0 回填，端到端）：以 PRD F1.1 验收用例 `household_power_consumption.txt`
> （2,075,259 行 × 9 列，126.8MB）走**完整 API 链路 + 真实库**实测——`POST /reports/upload` **32.1s**
> （编码/分隔符探测 + 全量解析 + 规范化中间文件落盘 + 质量报告）+ `POST /reports/{code}/confirm`
> **17.8s**（动态建表 + 2,075,259 行分批灌数 + 5 个索引），合计 **49.9s ≤ 60s**。
> 同批实测的相邻指标：重复上传（sha256 复用）**1.8s**；删除该 207 万行动态表 **1.0s**（回收 83,394 页，
> 未执行 VACUUM）。上传期间后端**不阻塞**（长耗时段落在线程池执行），其他用户的列表/预览/健康检查仍可响应。

**响应优化手段**：SSE 流式分段推进（不阻塞等待全链路）；**模型分级**——slot 抽取使用**轻量模型** + 精简提示词，SQL/代码生成与结果解读使用**主力模型**（两级模型名由 `.env` 配置，与厂商无关）；同一问题 + 同一 slot 命中缓存（会话级，5 分钟）；图表生成与文字解读并行。

### 6.2 可用性需求

- 首次使用者无需培训：新用户进入即看到「当前报表」与 8 个示例问题（点选即问）；

- 错误提示必须可操作：说清「什么错了 + 怎么改」（如「未识别到时间列，请确保表头包含 Date/日期 或 时间戳列」）；
- 支持一键重试失败的分析，支持复制 SQL/代码，支持查看执行明细。

| 编号 | 需求 | 实现要点 |
| --- | --- | --- |
| S1 | 生成代码沙箱 | sqlglot 只读白名单 + AST 预检 + 子进程隔离（超时强杀/禁网禁文件写；RestrictedPython 预留） |

### 6.5 可维护性需求

- 后端分层：`api / services / models / schemas / core`，与示例项目风格一致；
- 提示词集中管理：`app/prompts/*.md`，不硬编码在业务代码中；
- 口径规则集中管理：`app/core/config.py`（峰平谷时段、异常阈值、LIMIT、超时）+ `02.data/schema/schema_text.md`（注入用）；
- 全链路日志：请求 ID 贯穿，关键节点记录耗时与 token 消耗；
- 配置外置：`.env` 管理模型 API Key（`LLM_API_KEY`，兼容旧名 `DASHSCOPE_API_KEY`）、模型端点与模型名、数据库路径、端口；禁止硬编码密钥，`.env` 必须加入 `.gitignore`。

> **不做用户级 BYOK（v1.19.4 决策，需求方提问后明确）**：模型 API Key 属**部署级配置**，
> 个人中心**既不提供填写入口、也不展示模型/密钥内容**——该页只承载"我的账号与我的数据"；
> 当前模型口径由 `GET /system/health`（`llm` 字段：`provider` / `protocol` / `model_main` /
> `model_light` / `base_url` / `key_source`，**永不含密钥值**）与评测中心页面呈现。理由：
> ① 用户级填写必然引入"密钥落库（需加密方案与迁移）或前端存储（XSS 直取）"的泄露面，与本条
> "配置外置、禁止硬编码"的既定原则相悖；② 评测中心的价值在**同一模型口径下跨批次对比正确率**，
> Key/模型随人而变会让 `eval_runs.model_name` 的对比失去意义（F5 同源要求）；
> ③ 单机实训场景下 Key 写 `.env` 即可，未配置时链路已自动回落离线脚本模型（如实回报 `configured=false`）。
> 若后续确需 BYOK（P2）：最小方案 = 请求头 `X-LLM-Key`（**不落库**）→ 后端 `ContextVar` → `get_llm()`
> 按上下文构造客户端；**评测中心仍强制使用服务端 Key**以保持口径可比。前端不落地，见 UIUX v1.14.2。

> **多厂商适配（v1.18.0 落地）**：系统**只实现一种协议——OpenAI 兼容**
> （`POST {LLM_BASE_URL}/chat/completions` + `Authorization: Bearer <key>`），因此
> **换厂商只改 `.env`、代码零改动**：阿里云百炼（含阿里云 MaaS 专属端点）、DeepSeek、Moonshot、
> 智谱、OpenAI、本地 Ollama / vLLM 等均可直接接入；`LLM_PROVIDER_LABEL` 仅用于健康检查展示，
> **不参与任何协议分支**（避免"厂商名硬编码"渗透进业务逻辑）。厂商差异只在两处兜底：
> ① `json_mode` 被端点拒绝（400 且提示 `response_format`）时自动去参重试一次
> （`LLM_JSON_MODE_FALLBACK`，默认开）；② 模型分级按**能力位** `supports_model_tiers` 判断
> （支持分级的 OpenAI 兼容客户端传轻量模型，脚本模型不传）。
> **不在支持范围**：Anthropic Messages API / Gemini 原生协议（请求体、响应体、工具 schema 全不同），
> 如需接入须新增独立 adapter 类（P2）。`/system/health` 如实回报
> `provider` / `protocol`（恒为 `openai-compatible`）/ `impl` / `configured` / `key_source`。
> **模板占位值防护**：`.env.example` 的 `sk-xxxxxx` / `请填入` 等占位值被**一律视为"未配置"**
> ——使用者原样复制模板时不会拿假 Key 去调厂商（否则每次分析都以 `E_LLM` 失败），
> 而是自动回落离线脚本模型并在健康检查里如实回报 `configured=false`。

### 6.6 可扩展性需求

- 新增报表类型：只需实现解析器并注册 Schema，不改 Agent 主流程；
- 更换/升降级 LLM：统一 `LLMClient` 抽象，基于 **OpenAI 兼容协议**接入（百炼 / DeepSeek / Moonshot / 智谱 / OpenAI / 本地 vLLM·Ollama 等），`base_url`、API Key 与模型名全部由 `.env` 提供；**换厂商或切换模型（含轻量 ↔ 主力分级）只改配置、不改业务代码**；
- 新增工具：在生成阶段的提示词中增加 `route` 取值与工具描述，并在状态图里**加一个节点 + 条件边**（守卫与沙箱可复用；如图表导出 / 报告生成 / PDF 导出；新节点会自动出现在导出的架构图里）；
- 新增大数据源：预留「数据源适配器」接口（未来接 MySQL/PostgreSQL 只读库）。

> **编排形态的实现口径（v1.19.31 更新：已接入 LangGraph 状态图）**：
> 分析流水线由 `app/agent/graph.py` 的 **StateGraph** 编排（13 节点；**重写环 / 形态自检环 / 澄清环都是条件边**），

> 会话级持久化由 `app/agent/checkpointer.py`（`AsyncSqliteSaver`，`thread_id = 会话编号`）承担，

## 8. 数据口径与报表规范

> 本章是本项目的**核心技术资产**。所有报表字段、提示词、Schema 描述、示例问题集、评测题都必须遵循本章规则。任何口径变更必须**同步修改三处**：清洗脚本注释、`manifest.json` 口径版本、Schema 描述文本。

### 8.1 量纲统一规则

| 原始字段 | 原始单位 | 统一口径（kWh） | 换算公式 |
| --- | --- | --- | --- |
| `Global_active_power`（GAP） | kW（分钟级功率均值） | 分钟电量 kWh | `GAP / 60` |
| `Global_reactive_power` | kW（无功功率） | 不换算为电量 | 仅用于统计功率特性 |
| `Sub_metering_1/2/3` | Wh | kWh | `/ 1000` |

**红线规则 R1**：报表中所有以 `_kwh` 结尾的字段均为**电量（kWh）**；以 `_kw` 结尾的字段为**功率（kW）**。两者不可相加、不可混用于同一聚合表达式。

### 8.2 未计量用电（Unmetered）计算规则

官方定义：总线电量减去三个分表电量，代表未被分表计量的其他电器用电。

```
未计量用电(kWh) = GAP(kW) / 60 − SM1(Wh)/1000 − SM2(Wh)/1000 − SM3(Wh)/1000
```

**红线规则 R2**：未计量用电是**派生指标**，其含义是「其他电器」，**不等于**总用电量的剩余项之外的任何概念；报表中必须显式提供该列，禁止让模型自行臆测公式。

### 8.3 两套正交拆分规则（最易错点）

| 拆分维度 | 构成项 | 求和关系 |
| --- | --- | --- |
| 按用途 | 厨房（SM1）+ 洗衣房（SM2）+ 热水器与空调（SM3）+ 未计量（其他） | 四项之和 = 总用电量 |
| 按时段 | 峰段 + 平段 + 谷段 | 三项之和 = 总用电量 |

**红线规则 R3**：两套拆分**相互正交**（同一份电量既可按用途拆、也可按时段拆），**混加会得到约 2 倍于实际电量的错误结果**。任何聚合问题必须先明确是「按用途」还是「按时段」，不得同时求和。Schema 描述与提示词中必须以醒目规则列出。

### 8.4 峰平谷时段定义

| 时段 | 小时区间（整点） | 字段前缀 |
| --- | --- | --- |
| 谷 | 00:00–07:59 | `valley` |
| 平 | 08:00–17:59 | `flat` |
| 峰 | 18:00–23:59 | `peak` |

- 三段恰好覆盖 24 小时，**无空缺、无重叠**；
- 区间写法说明：`00:00–07:59` 表示时间线区间 `00:00:00 ≤ t < 08:00:00`（即包含 00:00:00 至 07:59:59 的每一个整分钟），**不是**以 07:59 这个整点为界；另两段同理（`08:00–17:59` 即 `08:00:00 ≤ t < 18:00:00`，`18:00–23:59` 即 `18:00:00 ≤ t < 24:00:00`）；
- 时段边界在 `app/core/config.py` 中定义成常量表，可整体替换为其他地区口径；
- 时段划分属于报表生成口径，**报表一旦生成即固化**，界面展示时必须显示当前口径说明；
- 分钟级明细按分钟所属小时归入对应时段；小时/日/月级报表按各小时段电量累加。

### 8.5 覆盖率与自然时间口径

| 概念 | 定义 |
| --- | --- |
| `expected_minutes` | 该周期**自然时间长度**（与是否有数据无关）：小时恒为 60，日恒为 1440，月为「当月天数 × 1440」 |
| `active_minutes` | 该周期内**实际有有效数值**的分钟数（缺失行不计入） |
| `coverage` | `active_minutes / expected_minutes`，比率型 |

**红线规则 R4**：`expected_minutes` 用自然时间，因此报表首日（数据从当天 17:24 才开始）覆盖率约 0.27 属正常**边界效应**，不得据此判定为数据异常。

### 8.6 日均用电折算规则

```
日均用电(kWh/日) = 周期总电量(kWh) × 1440 / active_minutes
```

**红线规则 R5**：日均用电按**有效数据**折算（不是按自然天数简单相除），否则缺采周期会被严重低估；该字段为派生指标，命名固定为 `daily_avg_kwh`，禁止再用 `avg_daily_kwh` 等其他名称表示同一含义。

**边界规则**：当 `active_minutes = 0`（该周期整段数据缺失）时，`daily_avg_kwh` 置为 `NULL`，**不参与任何后续聚合、平均与对比计算**（统计均值时须先剔除 NULL），避免出现除零错误与 0 值污染。

**口径区分（v1.19.6 补，真实模型评测暴露的歧义）**：上句的"统计均值时须先剔除 NULL"**仅指 `daily_avg_kwh` 自身在参与计算时的 NULL 处理**，**不等于**"全期日均用电要对 `daily_avg_kwh` 求平均"。两个口径必须分开：

| 问法 | 正确算法 | 实测值（r_daily，全期） |
| --- | --- | --- |
| 「全期平均每天用多少电 / 全期日均是多少」 | **`AVG(consumption_kwh)`**（全期总电量 ÷ 有数据天数） | **26.0179676902 kWh/日** |
| 「7 月 3 日的日均用电是多少」 | `daily_avg_kwh`（按有效数据折算到整日，用于缺采日可比） | 该日折算值 |

两者在数据上相差约 0.2 kWh/日（26.21 vs 26.02），**不可互换**。该区分已写入注入文本 R5 段（`02.data/schema/schema_text.md`），并由评测题 q002 固化回归。

### 8.7 比率型字段规则

凡列名含 `ratio` / `rate` / `factor` / `coverage` / `share` 的字段（如 `sm1_ratio`、`peak_ratio`、`unmetered_ratio`、`load_factor`、`power_factor`、`coverage`）均为**比率型**。

**红线规则 R6**：比率型字段**不可 SUM**，跨周期汇总必须用「分子求和 ÷ 分母求和」重算。Schema 描述中逐列标注 `agg: none`。

### 8.8 用电结构报表的特殊规则

- 该报表以 `period` 维度组织，取值形如 `2006`、`2007`、…、`2010`（年份行）与 `全期`（合计行）；
- **红线规则 R7**：`period = '全期'` 的行是各年份行的合计，**求和时绝不可与年份行一起 SUM**，否则结果翻倍；
- 结构报表同时提供按用途与按时段两套列，遵循 R3。

### 8.10 数据质量与清洗规则

| 项 | 规则 |

| 缺失处理 | `?` → 缺失（NaN）；缺失分钟**不参与求和**，但计入 `expected_minutes` 从而降低 `coverage` |
| 重复行 | 按时间戳去重，保留首条并记录日志 |
| 时间解析 | 显式按 `%d/%m/%Y %H:%M:%S` 解析原始的 `Date`+`Time` 组合 |
| 负值处理 | 电量/功率出现负值视为异常，置为缺失并计入质量报告 |
| 越界处理 | 电压 **<210V 或 >250V** 标记为可疑，**不删除**但在质量报告中列出；异常判定附加**当日累计越界 ≥30 分钟**门槛（阈值按实测分布 223–254V 收紧；原 200–260V 实测命中 0 次，已废弃） |
| 日界处理 | 报表周期为完整自然日范围；首日仅从 17:24 起有数据，属正常边界（见 R4） |
| 数值精度 | 电量类字段保留 6 位小数，比率类保留 6 位小数，功率类保留 3 位小数 |

> ② 与 8.12.1 的 94.2% **不可直接比较**（模型与提示词双变量）。详见测试报告 7.3.3。

#### 8.12.3 档位对照：速度档 vs 质量档（PRD 10.3 模型分级的实测落地）

| 档位 | 模型 | 提示词 | 题量 | 执行正确率 | 命中率 | 平均 / P95 | N2 / N3 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 质量档 | `kimi-k3` | v3.7 | 120 | **99.2%** | 86.2% | 14.5s / 28.1s | ✗ / ✗ |
| 速度档 | `qwen3.7-flash` | v3.9 | 97 | **93.8%** | 79.4% | **8.1s / 10.3s**（单轮批） | **≈✓ / ✓** |

（速度档题量为 97 而非 120：其 1M 额度实测装不下——单条记录 8,565–8,821 tokens × 135 条 ≈ 113–119 万 ✗。）

**错题性质（逐题核对 SQL 后的结论）**：速度档 6 道错题里 **5 道的规则早已在提示词中明文存在**
（R6 比率须重算、求极值须排除 NULL、追问须继承维度），只是**档位不照做**；
⇒ **"再补一条提示词"的边际收益已很低**，下一步应做**生成后可机检的结构校验**
（例如"问题含'比例'却返回 1000 行明细"）——这比继续加文字更对症。

**选型建议**：N2/N3 是硬指标 ⇒ **默认用速度档**；质量档留给"要准确率、可接受十几秒"的场景，
或在产品上做成**用户可切换的档位**（PRD 10.3 的分级设计本就允许这样落地）。详见测试报告 7.3.5。

**后续修复（v1.19.23 / v1.19.24）：把"能机检的形态"改由代码保证**——针对上面"规则已明文、档位不照做"的形态问题，
不再补提示词，而是：① **守卫自动补 Top-N 极值的 `IS NOT NULL`**（确定性、零模型调用）；
② **三类结果形态自检**接进重写环（占比回明细 / 极值回明细 / 筛选型追问丢分组维度；均只在汇总粒度或
筛选型追问时生效，带原因重写一次）。
两批各五题验证均 **5/5**，`pytest 301 passed`。**这条"把能机检的事从'指望模型'改成'代码保证'"是本轮评测最可复用的结论。**

>
> **报表读路径契约**（v1.8.0 落地）： 
> - `GET /reports/{report_code}/preview`：默认 50 行，`?limit=` 取值 1–200（越界返回 400 `E_VALIDATION`），**对象数组**返回，按时间列正序，并**自动过滤自增主键等代理键**（被过滤列由 `excluded_columns` 回显），保证预览列与 Schema 字典列一致；
> - `GET /reports/{report_code}/schema`：`structured` 取 `uploaded_reports.schema_json`，`text` 取注入用的 `schema_text.md` **原文切段**（前端数据字典与模型注入文本逐字一致；上传的动态表回退为由 `schema_json` 渲染）；
> - `GET /reports/{report_code}/quality`：`uploaded_reports.quality_json`，含数据集级质量 `dataset` 与**与本报表相关的**口径校验 `checks`；
> - 可见性：预置报表全用户共享可读；他人上传的报表返回 403 `E_FORBIDDEN`（不泄露资源是否存在）。
>
> **会话读取契约**（v1.9.0 落地）：
> - `POST /conversations`：`active_report_code` 可不传，按**三级回落**推导（请求体显式 > 该用户最近一条会话 > 系统默认活跃报表 `is_active = 1`），响应 `active_report_source` 回显来源；
> - `GET /conversations`：**不分页**，支持 `?q=`（标题模糊）与 `?date_from=` / `?date_to=`（更新时间范围）；排序为**置顶组在前**（`pinned_at DESC`）再按 `updated_at DESC`；`message_count` 由一次分组 COUNT 实时计算（不依赖快照列）；
> - `PATCH /conversations/{conversation_code}`：可组合提交 `title` / `active_report_code` / `is_pinned`，三者至少给一个（否则 400 `E_VALIDATION`）；**置顶每用户上限 5 条，超出自动挤出最早置顶的那条**并在 `evicted_pinned_code` 回显（UIUX 5.1「最多 5 条」的落地方式）；
> - `POST /reports/{report_code}/activate`（body 带 `conversation_code`）与 `PATCH` 的 `active_report_code` **完全等价**（同一 service 实现）：前者供报表管理页、后者供会话列表使用；
> - `GET /conversations/{conversation_code}/messages`：**游标式**分页，默认最近 50 条（`?limit=` 取值 1–200，越界 400）、`?before_seq=` 向历史翻页，响应含 `has_more` / `oldest_seq` / `newest_seq`；
> - 归属校验：他人会话 / 报表一律 403 `E_FORBIDDEN`；删除会话级联清理消息与分析记录，并落 `audit_logs(cascade_delete)`；
> - **消息携带记录编号**（v1.19.0 前端第一批补）：助手消息的 `record_code` 由 `analysis_id` 解析而来
>   （`null` 表示澄清轮或用户消息）。前端刷新后用调 `GET /analysis/records/{record_code}` 回放
>   **表格 / 图表 / 执行信息**——只给数字主键 `analysis_id` 无法反查业务编号，右栏在刷新后只能是空的。
>
> **分析记录契约**（v1.13.0 落地，交付物 4 第二批）：
> - `GET /analysis/records`：**offset 分页 + `total`**（`?page=1&page_size=20`，`page_size` 上限 100，
>   越界一律 400 `E_VALIDATION`）；筛选为 `conversation_code` / `report_code` / `status` / `q`（问题关键词模糊）/
>   `date_from` / `date_to`（含当天）；排序固定 `created_at DESC, id DESC`（id 作次键，避免同一秒翻页错位）；
>   列表项为**轻字段**（问题/会话/报表/状态/耗时/tokens/模型），**不含** SQL 与解读正文；
>   响应另带 `status_count`（**统计时排除 status 条件本身**，使「全部/成功/失败」页签数字在切换时不跳变）；
> - `GET /analysis/records/{record_code}`：**全量详情**——meta（含 `prompt_version` / `schema_version` /
>   `error_code`）+ `slot`（8 字段）+ **实际执行的 SQL**（含守卫补的 LIMIT）+ 结果快照（列/行/`row_count`/`truncated`）
>   + `narrative` / `key_numbers` / `anomalies` + **`llm_calls[]`**（每阶段的模型、tokens、耗时）+
>   `can_replay`（原报表仍可用时为 true）+
>   **`retries` / `path_switched`**（v1.19.0 补：与 SSE `meta` 事件同源，供前端"执行信息"区块回放
>   "重试 N 次 / 已切换到 pandas 路径"）；
> - `POST /analysis/records/{record_code}/replay`：**整轮重跑**（重新抽 slot → 重新生成 SQL → 守卫 → 执行 → 解读），
>   沿用原问题、**报表锁定为原记录的报表**（不跟随会话当前活跃报表，保证前后可比且不改变用户会话状态），
>   落一条**新记录**并在响应里回显 `replayed_from`（血缘）；**非流式**返回新记录详情；
> - `DELETE /analysis/records/{record_code}`：删除记录本身（`llm_calls` 级联删除、关联消息**保留**但解除引用），
>   响应回显 `deleted_messages` / `deleted_llm_calls`；
> - 归属隔离：四个接口一律按当前用户过滤，他人记录返回 404（不泄露资源是否存在）。
>
> **分析链路契约**（v1.12.0 落地，交付物 4 第一批：单轮问答最小闭环）：
> - `POST /analysis/chat`：**SSE 流式**，事件顺序成功为
>   `status(parsing) → slot → code → status(executing) → table → chart → narrative → meta → done`；
>   失败为 `status → [slot → code] → error → done`——**`error` 之后仍发 `done`**，前端据此停止 loading 并拿到
>   `record_id` 跳详情；上下文级失败（会话不存在/不属于本人）直接以 `error` 事件收尾，不留空流；
> - 请求体的 `report_code` 可选：给出且与会话活跃报表不同时**先切换再分析**（PRD F1.6），未给出则用会话活跃报表；
> - **SQL 白名单只含当前活跃报表的表名**：模型若生成其它表的查询会被守卫拒绝（`E_SQL_FORBIDDEN`），
>   这是"后续提问作用于活跃报表"的落地方式；
> - 失败三类（守卫拦截 / 执行报错 / 模型输出不可解析）**全部落库留痕**：`analyses.status='failed'` + `error_code`，
>   助手消息为固定文案（"本次未生成结果…"），**不写 `narrative` / `key_numbers_json`**（P4 不编造）；
> - **本批不含**：图表、pandas 沙箱、澄清回路、重试环、多轮 slot 继承（继承需与澄清同批，见 F4.4）。
>
> **澄清回路契约**（v1.15.0 落地，交付物 4 第四批：多轮 slot 继承 + 澄清）：
> - **slot 继承**：以会话 `slot_json` 为基线做**增量抽取**合并（标量非 null 即覆盖、null 即继承；
>   `filters` 同 field 替换、异 field 追加）；`time_range` 缺省「全期」——**不因缺时间而澄清**；
>   `metric` 缺失 → 必澄清（UIUX 6.3：metric 必填不可清除）；
> - **澄清轮**（不落 analyses、不回写 slot_json）：事件序列
>   `status → slot(部分) → clarify → meta → done(record_id=null)`；落 messages×2
>   （user=原问题、assistant=澄清卡 **JSON**，前端按 `type` 渲染可还原）；
>   `clarify` 载荷 `{question, options[], missing_slot, partial_slot}`，选项由**规则查表生成**
>   （零 LLM，value 与 slot 合入值同域，`value=null` 表示自定义/不限）；
> - **`POST /analysis/clarify`**（SSE，鉴权**是**）：请求体 `{conversation_code, question, slot_patch}`，
>   回填合入会话 `slot_json` 并持久化后**就地继续完整链路**（跳过二次增量抽取，
>   `llm_calls` 为 `[gen_sql, narrative]`）；执行轮**不再落 user 消息**（原问题澄清轮已落）；
> - **replay 基线**：重跑以**原记录的 slot_json** 为继承基线（增量抽取照常跑，保住「整轮重跑」），
>   会话后续追问改过的条件不污染并排比较；
> - **切表重置**：切换活跃报表即清空会话 slot（旧表条件对新表可能不存在）；
> - `POST /analysis/chat` 请求体新增可选 `slot_patch`（条件芯片编辑后重算，与 clarify 共用校验）；
> - prompt 升 **prompt-v2.0**（SLOT_SYSTEM 增量抽取 + 澄清教学）。
>
> **Schema 注入文本契约**（v1.11.0 落地，交付物 3）：
> - `GET /reports/{report_code}/schema`：`structured` 取 `schema_json`；`text` 为**完整注入文本**
>   （全局头 + 本表字段 + 口径红线 + SQLite 可用函数 + 常用问题示例 + 使用提示），并回显
>   `text_source`（`schema_text.md` / `generated`）、`est_tokens`、`truncated`；
> - `GET /system/schema-text`：**当前活跃报表**的注入文本，取值规则为**会话优先**——
>   传 `?conversation_code=` 时取该会话的 `active_report_id`（会话级唯一权威），不传则回落
>   `uploaded_reports.is_active = 1` 的**系统默认活跃报表**；响应回显 `report_code` / `source`
>   （`conversation` / `system_default`）/ `caliber_version`，调用方永远知道拿到的是哪张表的口径；
> - 两接口的 `text` **同源同构**（同一 service 产出），保证「前端数据字典 = 模型注入文本」。
>
> **报表写路径契约**（v1.10.0 落地，两段式上传）：
> - `POST /reports/upload`（`multipart/form-data`，字段名 `file`）：**一次全量解析**并登记为 `status='pending'`，返回
>   `report_code` / `table_name` / `row_count` / `column_count` / `encoding` / `delimiter` / `time_column` /
>   `column_mapping`（原始列名 → 安全列名，仅列有变化的）/ `columns[]`（含 `origin_name` 与 `can SUM`）/ `preview`
>   （前 20 行）/ `quality`（数据集级质量）/ `pending_expires_at`（24h 内未确认即被回收）；
>   **此阶段不建物理表**，因此 `pending` 报表不出现在 `GET /reports`，其 `/preview` 会明确返回 400 提示先 confirm；
> - **重复上传复用**：同一用户此前上传过 sha256 相同的文件且未删除时，不再解析，直接返回既有报表并置 `is_duplicate=true`
>   （去重**限本人**，不会泄露他人是否传过同一文件）；
> - `POST /reports/{report_code}/confirm`：读规范化中间文件 → 动态建表 → 分批灌数 → 建索引 → `status='ready'`，
>   返回 `inserted_rows` / `indexes[]` / `elapsed_ms`；**幂等**（已 `ready` 时返回 `already_confirmed=true` 不重建）；
> - `DELETE /reports/{report_code}`：**预置报表返回 403 `E_FORBIDDEN`**（规则不允许，非请求不合法）；上传报表返回
>   `dropped_table` / `dropped_indexes` / `affected_conversations`（活跃报表被置空的会话数）/ `freed_pages`（**仅报告回收页数，不执行 VACUUM**）。

> **评测契约**（v1.17.0 落地，交付物 8 / M5）：
> - `GET /eval/questions`：题库列表（全局资产、不做用户隔离），筛选 `qtype` / `difficulty` / `is_trap`，
>   offset 分页（`page` / `page_size` ≤200）；返回题面、题型、难度、目标报表、gold_sql 与关键数值；
> - `POST /eval/runs`：请求体 `{"impl": "auto"|"real"|"selfcheck", "name"?, "question_codes"?: [...],
>   "limit"?, "include_narrative"?: true}`。**批次是异步的**：120 题 × 完整链路远超单次请求时限，
>   接口立即返回 `{run_code, status: "pending", impl, model_name, question_total}`，
>   前端轮询 `GET /eval/runs/{run_code}` 直到 `finished/failed`（PRD 9.1 未定义评测进度 SSE 事件）；
>   `impl=real` 且未配置模型 Key（`LLM_API_KEY`）→ 400 `E_VALIDATION`（`hint` 指向 selfcheck，**不静默回落**）；
>   题库为空 → 400（`hint` 给出 `04_build_eval_set.py` 构建命令）；
> - `GET /eval/runs`：批次列表（**仅本人**，按 `created_at DESC, id DESC`，offset 分页）；
> - `GET /eval/runs/{run_code}`：详情 = 指标汇总 + `metrics`（分类正确率/差异分布/错误分布/判分档/
>   归因分布）+ 逐题明细 `questions[]`（含 `generated_sql_or_code`、`matched_tier`、`diff_type`、
>   `key_hit_rate`、`elapsed_ms`、`retries`、`error_code`）；`include_questions=false` 可只要指标；
> - `GET /eval/runs/{run_code}/report`：**Markdown** 报告（`text/markdown` + `Content-Disposition` 下载），
>   批次未完成 → 400、报告缺失 → 404；
> - 归属隔离：他人批次 / 不存在的批次一律 **404**；未登录 **401**。

### 9.2 关键接口示例：`POST /analysis/chat`（SSE）

**请求**

```json
{
  "conversation_code": "c_20260914_001",
  "report_code": "r_daily",
  "message": "先看全年用电趋势，只看周末的，再按月汇总一次",
  "options": { "with_chart": true, "with_narrative": true }
}
```

**SSE 事件序列**

| 事件 | 数据 | 说明 |
| --- | --- | --- |
| `status` | `{"stage":"parsing","text":"正在解析问题…"}` | 首字事件，目标 ≤2s |
| `slot` | `{"time_range":"全期","granularity":"月","metric":"consumption_kwh","filters":[{"field":"is_weekend","op":"=","value":true}]}` | 解析出的查询条件（前端渲染为条件芯片）。`filters` 统一为**对象数组**，每项含 `field`（字段名）、`op`（`=` / `!=` / `>` / `<` / `>=` / `<=` / `in` / `between`）、`value`（值或数组），便于前端规范化渲染与用户编辑 |
| `clarify` | `{"question":"你指的是哪张报表？","options":[{"label":"日报","value":"r_daily"},…,{"label":"自定义","value":null}],"missing_slot":"report","partial_slot":{…合并后、填默认前的部分 slot…}}` | **歧义澄清**事件（v1.15.0 已落地）：信息不足时不猜测，返回确认问题与 2–3 个可点选选项（规则查表生成，`value` 与 slot 合入值同域、`null`=自定义/不限）；**本轮以 `done(record_id=null)` 收尾、不产生分析记录**；用户点选后前端调 `POST /analysis/clarify`（带原问题与回填值）就地继续执行，已解析条件经 `partial_slot` + 会话 `slot_json` 不丢失（对应 F2.6 / F4.4） |
| `code` | `{"route":"sql","sql":"SELECT year_month, SUM(consumption_kwh) …"}` 或 `{"route":"pandas","code":"result = df[\"total_kwh\"].sum()"}` | 生成的 SQL/代码（可展开查看；**v1.16.0 起字段为 `route`+`sql`/`code`**，前端按 route 显示路径标签；重写/换路时本事件会多次出现，前端以最后一次为准） |
| `status` | `{"stage":"executing"}` | 执行中 |
| `table` | `{"columns":[…],"rows":[…],"row_count":48}` | 结果表格数据 |
| `chart` | `{"figure":{…Plotly figure JSON…} \| null,"chart_type":"line","fallback":null,"reason":null,"unit":"kWh","series":[…],"top_n":12,"merged_count":8,"r3_adjusted":false,"dropped_columns":[…],"excluded_columns":[…]}` | 图表（**本地计算、不调 LLM**，与 `table` 同源）。画不出来时 `figure=null` + `fallback="table"` + `reason`，**主流程不受影响**（`status` 仍为 `success`）；口径标记同时写在 `figure.layout.meta`，随 `chart_json` 落库 |
| `narrative` | `{"text":"…","key_numbers":[…],"anomalies":[…]}` | 文字解读（可分段流式） |
| `meta` | `{"elapsed_ms":5120,"retries":1,"llm_tokens":1840,"model":"qwen-max","llm_impl":"dashscope"}` | 元信息（`retries` = 自愈重试次数，v1.16.0 起为真实计数） |
| `done` | `{"record_id":"a_000123"}` | 结束 |
| `error` | `{"code":"E_SQL_EXEC","message":"…","detail":"route=sql rule=-","retries":1,"path_switched":true}` | 失败（明确反馈，不编造结果；v1.16.0 起带 `retries`/`path_switched` 供前端提示"已自动重试/已换路"） |

### 9.3 错误码规范

| 错误码 | 场景 | 前端提示策略 |
| --- | --- | --- |
| `E_NO_TIME_COLUMN` | 上传文件无时间列 | 指出缺少的列并给示例表头 |
| `E_ENCODING` | 编码无法识别 | 建议另存为 UTF-8 |
| `E_FILE_TOO_LARGE` | 上传文件超过 200MB | 提示按时间拆分后上传（413） |
| `E_FILE_TYPE` | 扩展名不是 `.csv` / `.txt` | 提示 Excel 需先另存为 UTF-8 CSV |
| `E_HEADER_INVALID` | 表头为空 / 含空列名 / 列名重复 | 回传冲突列名并提示加序号区分 |
| `E_NO_NUMERIC_COLUMN` | 无可解析为数值的列 | 检查千分位、单位后缀等文本污染 |
| `E_PARSE` | 行列数不齐 / 解析中断 | 回传首个出错行号，提示另存为 UTF-8 CSV |
| `E_INGEST_FAILED` | 动态建表或灌数失败 | 动态表已回滚、报表标记失败可重传；检查磁盘空间 |
| `E_SQL_FORBIDDEN` | SQL 未通过白名单 | 提示已拦截，展示原因 |
| `E_SQL_EXEC` | SQL 执行失败 | 展示错误 + 重试按钮 |
| `E_SANDBOX_TIMEOUT` | 代码超时 | 建议缩小时间范围 |
| `E_OUT_OF_SCOPE` | 问题超出报表范围 | 显示拒答说明与可问指标建议 |
| `E_AUTH` / `E_FORBIDDEN` | 未登录 / 越权 | 跳登录 / 提示无权限 |
| `E_LLM` | 模型调用失败 | 提示稍后重试，记录 request_id |
| `E_CODE_FORBIDDEN` | pandas 代码未通过 AST 预检（对应 SQL 路径的 E_SQL_FORBIDDEN） | 提示已拦截，展示原因（400，v1.16.0） |
| `E_CODE_EXEC` | 沙箱内代码运行报错（`data.error_type`/`line_no`/`trace_tail`） | 展示错误 + 重试按钮（500，v1.16.0） |
| `E_CHART_UNSUPPORTED` | 显式指定的图表类型与数据形状不符（`data.supported` 列出可用类型） | 提示可改用的类型（400，v1.14.0） |
| `E_GRANULARITY_UNAVAILABLE` | 结果快照不含可再聚合的明细，或请求粒度比结果更细 | 提示重新提问以获得期望粒度（400，v1.14.0） |
| `E_NOT_IMPLEMENTED` | 能力未启用（当前仅 `chart.png` 服务端导出，kaleido 属预留） | 如实说明未启用并给出前端替代方案（501，v1.14.0） |

**错误码与 HTTP 状态码映射（双轨制）**：响应包络 `{ code, message, data, request_id }` 中，**`code` = HTTP 状态码（成功为 0）**，业务错误码放 **`data.error_code`**（即上表的 `E_*`）。

| HTTP | code | error_code | 场景 |
| --- | --- | --- | --- |
| 400 | 400 | `E_VALIDATION` | 业务级参数校验失败（如密码不含数字、密码超 72 字节） |
| 401 | 401 | `E_AUTH` | 未登录 / token 缺失、非法或过期 |
| 401 | 401 | `E_CREDENTIALS` | 用户名或密码错误（不区分账号是否存在） |
| 403 | 403 | `E_FORBIDDEN` | 越权访问他人资源 |
| 403 | 403 | `E_ACCOUNT_DISABLED` | 账号已停用 |
| 404 | 404 | `E_NOT_FOUND` | 资源不存在 |
| 409 | 409 | `E_USERNAME_TAKEN` | 用户名已被占用 |
| 413 | 413 | `E_FILE_TOO_LARGE` | 上传文件超过 200MB 上限（`data.size_mb` / `data.limit_mb`） |
| 422 | 422 | `E_VALIDATION` | 请求体结构 / 类型校验失败（框架层） |
| 429 | 429 | `E_AUTH_LOCKED` | 账号锁定中（`data.locked_seconds` 返回剩余秒数） |
| 500 | 500 | `E_INGEST_FAILED` | 动态建表/灌数失败（动态表已回滚，报表标记 `failed` 可重传） |
| 500 | 500 | `E_INTERNAL` | 服务内部错误 |
| 400 | 400 | `E_CHART_UNSUPPORTED` | 显式指定的图表类型画不出来（`data.supported` 列出可用类型） |
| 400 | 400 | `E_GRANULARITY_UNAVAILABLE` | 结果无法重聚合到目标粒度 |
| 501 | 501 | `E_NOT_IMPLEMENTED` | 能力未启用（`chart.png` 服务端导出为 P2 预留） |
| 400 | 400 | `E_CODE_FORBIDDEN` | pandas 代码未通过 AST 预检（`data.rule_id` 给出规则） |
| 500 | 500 | `E_CODE_EXEC` | 沙箱内代码运行报错（`data.error_type`/`line_no`/`trace_tail`） |

> 落地位置：异常类与错误码常量集中在 `app/core/errors.py`，由 `app/main.py` 的异常处理器统一转换为响应包络。
>
> **修复建议字段**（v1.10.0 落地）：所有上传类错误在 `data.hint` 中给出**可执行的下一步**（如"请确保首行是列名、
> 列名非空且不重复"），对应 UIUX 9.4「说清原因 + 给出下一步」的两行呈现；`data` 中还会按需带上定位信息
> （`duplicate_columns` / `line_no` / `found_columns` / `size_mb`）。

## 11. 风险评估

### 11.1 技术风险

| 编号 | 风险 | 影响 | 应对措施 |
| --- | --- | --- | --- |
| T1 | 量纲/口径混算导致答案错误且不报错 | 直接打击正确率与可信度 | 第 8 章红线规则写入 Schema 与提示词；设置口径陷阱评测题；结果集自动比对兜底 |

| T4 | 沙箱被绕过（提示词注入） | 安全漏洞 | AST 预检 + 子进程隔离（超时强杀/池重建）+ 超时/禁网/禁文件；已备**恶意样例 40 条 + 合法惯用法 13 条**（tests/test_sandbox.py，G6 验收用；实测恶意 100% 拦截、合法零误杀） |
| T5 | 动态建表引入 SQL 注入 | 数据被破坏 | 表名/列名严格白名单化（正则 + 长度限制），标识符不可直接拼接用户输入 |
| T6 | 200 万行解析慢或内存溢出 | 体验差 | 分块读取 + 指定 dtype + 只对必要列建索引；解析耗时写入质量报告 |
| T7 | 模型生成代码不可复现（同题不同结果） | 评测波动 | 评测固定提示词版本与温度参数（temperature=0），记录版本号 |
| T8 | SQLite 缺少 STDDEV/POWER 等函数导致 SQL 生成失败 | 正确率下降 | Schema 中显式给出可用函数清单与替代表达式（如 `SQRT(AVG(x*x)-AVG(x)*AVG(x))`） |
