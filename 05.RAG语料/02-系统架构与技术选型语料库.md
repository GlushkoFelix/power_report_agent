# 系统架构与技术选型语料库

**主题：** 智电析报系统架构设计、技术选型与关键决策
**适用范围：** 架构师、技术负责人、开发人员
**版本：** v1.1（2026-10-13：编排改 LangGraph 状态图，见 ADR-021）

---

## Q: 智电析报的整体架构分为哪几层？

**A:** 前后端分离的四层架构：
1. **接入层**：React 前端（5 个页面 + SSE 客户端）；
2. **接口层**：FastAPI 路由（39 条端点）+ SSE 流式响应；
3. **服务与 Agent 层**：分析编排、slot 解析、双工具路由（SQL / pandas）、
   SQL 与代码守卫、沙箱执行、图表与解读；
4. **数据层**：两个 SQLite 库（`reports.db` 只读 + `power_agent.db` 读写）。

**标签：** 系统架构, 四层架构, 前后端分离, 分层设计

## Q: 前端技术栈是什么？为什么 React 停在 18.x？

**A:** 以 `package.json` 实际安装版本为准：**Vite 6、React 18.3、TypeScript 5.7、
Ant Design 5.22、Tailwind CSS 3.4（关闭 preflight）、zustand 5、
plotly.js-dist-min 2.35、axios、@microsoft/fetch-event-source**。
React 停在 18.x 是刻意选择——**Ant Design 5 对 React 19 的兼容尚未完全收敛**；
Tailwind 关闭 `preflight` 是为了不与 AntD 的基础样式冲突。

**标签：** 前端技术栈, React 18, Ant Design 5, Tailwind 3, 版本口径

## Q: 后端技术栈是什么？有哪些"刻意不装"的依赖？

**A:** 核心：**FastAPI、SQLAlchemy 2.0、Pydantic v2、aiosqlite、sse-starlette、
bcrypt（直调 5.x）、PyJWT、sqlglot（SQL 守卫）、json-repair、httpx、plotly 7、narwhals、RestrictedPython（已装未接入）**。
"刻意不装"的两个（**LangGraph 已于 2026-10-13 接入，不再是"不装"项**）：
- **`openai` SDK**——用已装的 httpx 直调兼容端点即可，装它会额外拖 4 个包；
- **`kaleido`**——服务端图片导出是预留能力（装上即生效，未装时接口返回 501）。

**已接入的编排依赖**：`langgraph 1.2.14` + `langgraph-checkpoint-sqlite 3.1.2`（状态图 + 会话级检查点；
连带把 `websockets` 降级、带入 `httpx2`/`httpcore2`——与"不装 `openai` SDK 以避开这俩"的初衷相抵，
已在架构文档 6.3 如实记录）。

**标签：** 后端技术栈, 依赖选型, 刻意不装, 依赖清单

## Q: Agent 流水线用不用 LangGraph？为什么一度没用、后来又用上了？

**A:** 这是本项目最有代表性的一段技术演进，分三步：
① **早期（ADR-017）刻意不用**：链路是**固定的显式阶段**（slot 解析 → 生成 → 守卫 → 执行 → 图表 → 解读），
用 `analysis_service.run_once()` 的 async 编排即可，状态与分支都代码可见，便于逐阶段加超时兜底、重写环与留痕；
引入状态图会增加一层间接性与依赖，当时判断"对本项目形态没有收益"。
② **后来为什么要用（ADR-021）**：真正的收益不在"把顺序画成图"，而在三件事——
**把两处环变成真正的条件边**（重写环 / 形态自检环：失败分类路由显式可见、可单独测试）、
**检查点**（`thread_id = 会话编号`，状态持久化、可回放）、
以及**澄清的 Human-in-the-loop**（`interrupt()` 挂起 → 用户回填 → `Command(resume=…)` **断点续跑**，
不再"第二跳把整轮重跑一遍"）。
③ **怎么保证"换编排不改行为"**：两条编排**并存**（`ORCHESTRATOR=langgraph` 默认 / `legacy` 回退，一行切换），
用 **9 条等价性用例**逐字段 + 逐事件比对，再用 **120 题 selfcheck 与改造前逐题比对**兜底——
最终全量 **323 条用例在状态图下全绿**、120 题逐题一致，**回退只需改一行配置**。
提示词始终集中在 `agent/prompts.py`（带版本号），与编排解耦；检查点表的 DDL 按项目纪律**手工纳管**
（不让框架 `setup()` 自动建表）。

**标签：** 编排方式, ADR-017, ADR-021, LangGraph, 状态图, 检查点, HITL, 等价性回归

## Q: 为什么用 SSE 而不是 WebSocket？

**A:** 分析过程是**单向的服务端推送**（进度、结果、解读），客户端只在发起时 `POST` 一次，
不需要双向长连接。SSE 的优势是：基于普通 HTTP（鉴权头、代理、日志都沿用现成设施）、
天然支持断线重连语义、服务端实现简单。
注意一个实践约束：**分析接口是 `POST` + `Authorization` 头**，而浏览器原生 `EventSource`
只支持 GET 且不能带自定义头，所以前端用 `@microsoft/fetch-event-source`。

**标签：** SSE, 流式响应, 为什么不用 WebSocket, 事件流

## Q: SQL 守卫为什么用 sqlglot 而不是正则匹配？

**A:** 正则匹配 SQL 既拦不住变形写法，又容易误杀。
用 sqlglot 把 SQL 解析成**语法树**后再判定，可以稳定地做到：
单语句、仅 `SELECT`、表名白名单、强制追加 `LIMIT`、危险函数禁用，
以及两条业务规则——**R3 两套拆分混加检测**与**求极值时自动补 `IS NOT NULL`**。
代价是要处理方言与 CTE（CTE 别名必须先收集，否则会被当成"表不在白名单"误拦）。

**标签：** sqlglot, SQL 守卫, 语法树, 白名单, CTE 误拦

---

## Q: pandas 沙箱为什么用子进程，而不是线程或只做 AST 预检？

**A:** 因为要**真的能杀掉失控代码**：Windows 上没有 Linux 的 `unshare`/cgroup，
线程无法被强制终止（`kill` 不掉死循环）。
所以模型生成的 pandas 代码先在子进程里跑，并设三类硬限制：
**超时 10s 强杀、内存上限 512MB（子进程内自检 RSS，超限自杀）、结果行数 ≤5000**；
网络与文件读写靠 AST 预检禁止（如实说明：不做 OS 级断网）。

**标签：** pandas 沙箱, 子进程隔离, 资源限制, AST 预检

## Q: 数据库为什么用 SQLite？为什么是两个库？

**A:** 选 SQLite 是因为本项目是**单机 Windows 演示形态**：零运维、单文件、可随交付物拷贝，
性能也够（207 万行聚合查询在毫秒级）。
**分两个库**是安全设计：`reports.db` 只放报表数据且应用侧只读，
`power_agent.db` 放用户/会话/记录/评测并读写——让大模型生成的代码只能触达只读的那个库
（配合连接层 `mode=ro`、语句层 `PRAGMA query_only`、表名白名单三重保证）。

**标签：** SQLite, 双库分离, 只读约束, 选型理由

## Q: 项目的部署形态是什么？为什么不用 Docker / Nginx？

**A:** 部署形态是**单机 Windows + 局域网访问**：一个 Python 进程（FastAPI，端口 8000）
+ 一个 Node 进程（Vite 开发服务器，端口 5173，或构建后的静态文件）。
不用 Docker 是因为目标是"老师/同学在一台 Windows 机器上跑起来并演示"，
容器化会增加环境门槛而不带来收益；不用 Nginx 是因为单机演示不需要网关层
（若要用 Nginx/HTTPS，实训附录 B 与语料 17 里有对应做法）。

**标签：** 部署形态, 单机演示, 局域网, 不用 Docker, 不用 Nginx

## Q: 图表为什么自封装 Plotly 容器，而不是用 react-plotly.js？

**A:** `react-plotly.js` 年久失修、类型定义基于 React 17，与 React 18 的 `StrictMode`
双调用配合不好。项目自封装 `ResultChart.tsx`：直接调用
`Plotly.react(div, figure, layout, { responsive: true })`，
好处是**可控**（能精确控制重绘、导出图片、主题注入）且**体积更小**
（只用 `plotly.js-dist-min`，不额外引入绑定层）。
另外约定：后端只产 `figure` 的语义色与文案，**纸面底色/字体/网格由前端注入**。

**标签：** 图表实现, Plotly, react-plotly.js, 自封装容器, 主题注入

## Q: 大模型是怎么接入的？换厂商要改什么？

**A:** 只实现 **OpenAI 兼容协议**一种，配置全走 `.env` 的中性变量：
`LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL_MAIN` / `LLM_MODEL_LIGHT` /
`LLM_TEMPERATURE` / `LLM_MAX_TOKENS` / `LLM_ENABLE_THINKING`。
**换厂商（百炼 / DeepSeek / Moonshot / 智谱 / 本地 vLLM·Ollama）只改 `.env`，代码零改动**；
`/system/health` 会如实回报 `configured` / `provider` / `protocol` / `key_source`。
项目按 PRD 10.3 做**模型分级**：slot 抽取用轻量模型，SQL 生成与解读用主力模型。

**标签：** 大模型接入, OpenAI 兼容, 换厂商, .env, 模型分级

## Q: 后端有哪些主要模块？

**A:** 三类目录：
- `app/api/v1/endpoints/` —— 39 条端点，7 个模块（auth / reports / conversations /
  analysis / charts / eval / system）；
- `app/core/` —— 7 个基础设施模块（config / errors / security / locks / llm_client /
  sql_guard / code_guard）；
- `app/services/` —— 14 个服务（分析编排、slot、Schema、图表、沙箱、上传入库、报表读写、
  评测、鉴权、审计、报告 PDF 等）；
另有 `app/agent/prompts.py`（提示词）、`app/db/`（三连接 + 10 张表映射）、`app/schemas/`（请求响应模型）。

**标签：** 后端模块, 服务层, core, 端点分组

## Q: 项目记录了多少条架构决策（ADR）？

**A:** 共 **20 条**（ADR-001 – ADR-020），每条含"决策 / 备选方案 / 理由 / 代价与缓解"。
写 ADR 的重点是**记录被否决方案的理由**，例如：
"不引入 Docker（单机演示）"、"沙箱用子进程而非线程（Windows 无法真正终止线程）"、
"SQL 守卫用 sqlglot 而非正则"。答辩时最常被追问的就是这类"为什么不用 X"。

**标签：** ADR, 架构决策记录, 决策留痕, 答辩材料

## Q: 架构文档里"组件清单"为什么要带"落地状态"列？

**A:** 因为架构文档天然会先写理想组件（如 `sandbox.py` + RestrictedPython、
`agent/graph.py`），而实现时方案可能变（本项目最终是 `services/sandbox_service.py` 子进程隔离、
**没有 graph.py**）。若组件表不标注状态，读者无法分辨"规划"与"实现"，
评审一核对目录就会认为文档造假。因此约定：组件表逐项标注
**已落地 / 部分落地 / 未落地（含原因）**，且每个路径都要能在仓库里找到。

**标签：** 组件清单, 落地状态, 文档一致性, 如实标注
