# PRD文档编写实训语料库

**主题：** 产品需求规格说明书（PRD）的结构、写法与实训要点
**适用范围：** 产品经理、需求分析学习者
**版本：** v1.0

---

## Q: 智电析报的 PRD 包含哪些章节？

**A:** 12 章：
1 文档概述｜2 产品背景｜3 产品目标｜4 用户角色与场景｜5 功能需求（F1–F6）｜
6 非功能需求（N/S）｜7 数据需求｜8 数据口径与报表规范｜9 接口需求｜
10 项目规划｜11 风险评估｜12 附录（修订记录 / 待回填事项）。
其中**第 8 章（数据口径）与第 9 章（接口）是本项目的重头**——
前者决定分析对不对，后者决定前后端能不能并行开发。

**标签：** PRD 结构, 章节清单, 文档框架

---

## Q: 什么样的需求才算"可验证"？

**A:** 可验证 = **能被一条命令、一个指标或一个页面判定**。
反例："响应要快""结果要准确""支持多用户"——无法判定。
正例（本项目实际写法）：
- "单轮平均响应 ≤8s（简单问数口径，评测统计）"；
- "上传解析入库：200 万行 ≤60s（实测 49.9s）"；
- "执⾏正确率 ≥85%（120 题评测集）"。
写法上就是：**指标 + 口径 + 测量方式**三件齐备。

**标签：** 可验证需求, 指标口径, 验收标准, 反例

## Q: 功能需求为什么要编号（F1–F6）？怎么用？

**A:** 编号让需求可以被**引用、追溯与逐条验收**。
本项目把任务书的 6 个模块映射为 F1–F6（数据接入与 Schema / 自然语言转 SQL 与编排 /
可视化输出 / 多轮追问 / 评测 / 用户管理），每个功能点下再细分子项（如 F2.2 SQL 白名单）。
好处：后续文档（UIUX、接口、评测）都能写"对应 PRD F2.2"，
评审时也能逐个功能点回答"做到哪一步、怎么验证"。

**标签：** 功能编号, F1-F6, 需求追溯, 逐条验收

---

## Q: 非功能需求（N/S）应该怎么写？

**A:** 分两类写：
- **性能类 N1–N7**：首字响应、单轮平均、P95、上传解析入库、列表切换、并发、大结果集保护——
每条都写"目标值 + 口径 + 实测"。例如 "N3 单轮 P95 ≤15s（含图表生成）"，
并如实登记实测未达标的情形。
- **安全类 S1–S8**：沙箱、提示词注入防护、危险操作拦截、鉴权与隔离、
  数据保护（日志脱敏 / 两库只读）、审计留痕等——每条都要写**落地方式**，
  而不是只写"要安全"。

**标签：** 非功能需求, N1-N7, S1-S8, 安全需求, 性能指标

## Q: 数据口径类需求怎么写才不留歧义？

**A:** 三条经验：
① **把边界写死到秒/字节这一级**——"谷段 00:00–07:59"要补注"即 00:00:00 至 07:59:59，
左闭右开"，否则模型与实现都会理解成包含 07:59 整点；
② **把 NULL 规则写清**——"`active_minutes = 0` 时 `daily_avg_kwh` 置为 NULL，不参与后续计算"；
③ **把"不可混加"写成红线**——按用途与按时段两套拆分各自求和等于总电量，
但**不可相加**（红线 R3），并在 SQL 守卫、Schema 文本、图表色板三处同步约束。
凡是"程序要照着做"的条款，都必须写到**能用一句 SQL 或一条断言验证**。

**标签：** 数据口径, 边界写法, NULL 规则, 口径红线

## Q: 接口需求应该在 PRD 写到什么程度？

**A:** 写到**能冻结契约**的程度即可，细节交给《API 接口文档》：
① 逐个端点写清 method / path / 请求体 / 响应体（用业务编号
`report_code` / `conversation_code` / `record_code` / `run_code`，**不暴露自增主键**）；
② 统一响应包络 `{code, message, data, request_id}`；
③ 错误码双轨制（HTTP 与业务 `code` 同值 + `data.error_code` + `data.hint`）；
④ SSE 事件清单与顺序（本项目 10 个事件）。
契约冻结的价值：前后端可以**并行开发**，本项目联调阶段没有因契约模糊返工。

**标签：** 接口需求, 契约冻结, 响应包络, 双轨制

## Q: 什么是"需求 → 交付物 → 验收方式"对照表？

**A:** 是 PRD 第 10 章的一张表，把功能需求（F1–F6）映射到任务书的交付物编号，
并写明每项**怎么验收**（命令 / 指标 / 页面）。
例如：F1 → 交付物 2/3（清洗脚本 + Schema 模块）→ `pytest` 与 A1–A5 口径校验；
F5 → 交付物 8 → 120 题评测报告。
它的价值在答辩：评审问"你怎么证明需求都实现了"，直接指着表逐条给证据。

**标签：** 需求追溯, 对照表, 验收方式, 答辩材料

## Q: 什么是"待回填事项（TBD）"？怎么管理？

**A:** 指**当下无法定、但必须定**的事项（如"前端依赖实际版本""所选厂商的模型名与限流参数"），
用统一编号 `TBD1…TBD6` 登记在 PRD 附录，写明"回填时机"与"回填位置"。
管理原则：**不写计划版本、一律以实测结果为准**——例如前端依赖版本
以 `package.json` 实际安装为准（最终回填为 React 18.3 / AntD 5.22 / Tailwind 3.4），
回填后同步更新引用它的其它文档（UIUX、架构文档），做到版本闭环。

**标签：** TBD, 待回填事项, 实测回填, 版本闭环

---

## Q: 文档版本与修订记录该怎么管？

**A:** 三条：
① **每次实质修改升版本号**（本项目 PRD 已到 v1.19.x），修订记录写清"改了什么、为什么"；
② **保留历史版本**（`AI共创过程文档/历史版本/` 下逐版留档），便于回溯"文档如何随决策演进"；
③ **版本互相引用要闭环**——PRD 头部标注配套文档版本，配套文档头部标注"对应 PRD 版本"，
改一处要同步另一处（本项目专门做过版本引用对齐修订）。

**标签：** 版本管理, 修订记录, 历史版本, 版本闭环

## Q: PRD 评审怎么做才有效？

**A:** 用**清单式评审**：逐条给出"章节号 + 具体改法"，
例如"第 5.3 节 F2.2：建议补一句——对聚合查询，LIMIT 仅作为安全兜底，不改变业务语义"。
评审关注两类问题：
① **可执行性**（凡是程序/模型要照做的条款有没有写到无歧义）；
② **口径一致性**（多处描述同一件事时是否一致，例如日报/月报是否都列了峰平谷三个字段）。
每条意见都要能在修订记录里回溯。

**标签：** PRD 评审, 清单式, 可执行性, 口径一致

---

## Q: 需求变更怎么处理？

**A:** 按"先判性质，再改文档"的顺序：
① **口径类变更**（如电压越界阈值收紧为 210–250V 且 ≥30 分钟）——
必须同步改 PRD、数据脚本、数据库文档与 Schema 文本，并升 `caliber_version`，
说明历史数据是否重算；
② **功能增减**（如个人中心四件事从"置灰待后续版本"变为闭环）——
更新功能表，并在旧描述处**如实标注变化**，不是悄悄改掉；
③ **接口变更**——同时更新接口文档与前端契约类型，且在报告里体现版本。

**标签：** 需求变更, 口径变更, 版本同步, 如实标注
