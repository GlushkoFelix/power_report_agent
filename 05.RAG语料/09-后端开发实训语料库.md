# 后端开发实训语料库

**主题：** 后端分层、关键实现、守卫与沙箱
**适用范围：** 后端开发者、全栈开发者
**版本：** v1.0

## Q: 后端是怎么分层的？各层职责是什么？

**A:** 六大目录：
- `app/api/v1/endpoints/`（**接口层**）——39 条端点，负责鉴权、参数校验、包络封装、SSE 输出；
- `app/services/`（**服务层**）——14 个模块承载全部业务逻辑（分析编排、slot、Schema、
  图表、沙箱、上传入库、报表读写、评测、鉴权、审计、报告 PDF 等）；
- `app/core/`（**基础设施**）——配置、错误码、安全（bcrypt/JWT）、锁、
  LLM 客户端、SQL 守卫、代码守卫；
- `app/agent/`（**提示词**）——`prompts.py` 集中管理三条系统提示词与版本号；
- `app/db/`（**数据访问**）——三连接工厂 + 10 张表查询映射；
- `app/schemas/`（**契约**）——统一包络与各组请求/响应模型。
分层的价值：端点只做"转译与校验"，业务逻辑可被直接单测。

**标签：** 后端分层, 目录职责, 服务层, 可测性

## Q: 三种数据库连接分别是什么？

**A:** ① **控制面读写连接**（`power_agent.db`，WAL 模式，供业务读写）；
② **数据面只读连接**（`reports.db`，`mode=ro` + `PRAGMA query_only`，
用 NullPool 避免连接跨事件循环复用报错）；
③ **报表库独占写连接**（只有上传入库服务使用，原生 sqlite3 + 进程内写锁 + 分批提交）。
**LLM 生成的 SQL 永远走 ②，代码永远走沙箱**——这样"AI 能造成的影响"被限制在只读范围内。

**标签：** 三连接, 只读连接, 独占写, 写锁

## Q: 鉴权是怎么实现的？有哪些安全细节？

**A:** bcrypt（直调 5.x）+ JWT：
- 注册校验：用户名 `^[A-Za-z0-9_]{4,20}$`（不区分大小写，统一转小写存储）；
  密码 8–64 位且必须同时含字母与数字，**UTF-8 编码后 ≤72 字节**（超出直接拒绝，不静默截断）；
- 登录失败 **5 次锁定 5 分钟**（返回 429 + `E_AUTH_LOCKED` 带剩余秒数）；
  用户名不存在与密码错误给**同一文案**（防账号枚举）；账号停用返回 403；
- JWT 单 access token 24h；**`JWT_SECRET_KEY` 缺失则启动报错**并打印生成命令
  （刻意设计：避免每次重启换密钥导致已签发 token 全部失效）；
- 越权访问他人资源返回 **404**（不泄露资源是否存在）；
- 注册/登录/失败/锁定/登出/改密/清记录/删账号等事件全部落审计。
不用 `passlib` 的原因：该库自 2020 年起停更，与 bcrypt 5.x 不兼容。

**标签：** 鉴权, bcrypt, JWT, 登录锁定, 防枚举, 审计

## Q: 统一响应包络与错误码是怎么设计的？

**A:** 所有接口返回 `{code, message, data, request_id}`：
- **`code` 与 HTTP 状态码同值**（成功为 0）——保留 HTTP 语义，网关/日志/监控照常工作；
- **业务错误码放 `data.error_code`**（如 `E_SQL_FORBIDDEN` / `E_CODE_FORBIDDEN` /
  `E_AUTH_LOCKED` / `E_VALIDATION`）；
- **`data.hint`** 给出"为什么失败、怎么修"的具体建议；
- 每个请求生成 `request_id`（同时写响应头），排障时按它串日志。
约定：业务级参数越界返回 **400 + `E_VALIDATION`**，而不是框架默认的 422。

**标签：** 响应包络, 双轨制, 错误码, hint, request_id

## Q: 报表读路径包含哪些接口？

**A:** 5 个：
`GET /reports`（列表，全量不分页，含 `table_exists` 自检、`is_deletable`、`is_active`）；
`GET /reports/{code}`（单表详情）；
`GET /reports/{code}/preview`（预览，默认 50 行、`limit` 1–200，
**过滤自增主键等代理键**并在 `excluded_columns` 回显，按时间列正序）；
`GET /reports/{code}/quality`（数据质量报告 + 口径校验 A1–A5 结论）；
`GET /reports/{code}/schema`（结构化列清单 + **完整注入文本**，含 `text_source` 标明来源）。
设计要点：**Schema 注入文本在上传阶段一次落库，读取零拼装**——
保证"前端字段字典"与"喂给模型的文本"逐字一致。

**标签：** 报表读路径, 预览, 质量, 字段字典, 注入文本

## Q: 上传写路径为什么要"两段式"？

**A:** 因为上传大文件耗时较长（207 万行约 50s），不能让用户"点了按钮干等还不知道成没成"，
也不能让半个报表进入可用状态。两段式：
① `POST /reports/upload`——计算 **sha256**（命中已有文件直接复用，`is_duplicate=true`）
→ 登记 `pending` → 流式解析 → 落规范化中间文件；
② `POST /reports/{code}/confirm`——动态建表（表名由文件名规范化 + 白名单正则 + 长度限制）
→ **先灌数后建索引**（分批 `executemany` 提交）→ 生成 Schema 注入文本落库 → 置 `ready`。
实测：upload **32.1s** + confirm **17.8s** = **49.9s**（目标 ≤60s）；重复上传命中 sha256 仅约 1.8s。

**标签：** 上传两段式, sha256 复用, 动态建表, 性能实测

## Q: 分析链路（`POST /analysis/chat`）分哪些阶段？

**A:** 按 SSE 事件推进的 6 步：
① **status(parsing)**：插入占位卡片；
② **slot**：轻量模型做增量抽取（或规则快通道）→ 与会话 slot 合并 → 澄清检查；
③ **code**：主力模型生成 SQL 或 pandas 代码（自报 route）；
④ **table/chart**：守卫校验（SQL 白名单 / AST 预检）→ 执行（只读连接 / 子进程沙箱）→ 结果表与图表；
⑤ **narrative**：主力模型生成文字解读与关键数值；
⑥ **meta/done**：耗时与 token 汇总、`record_id` 收尾。
留痕：`messages ×2` + `analyses ×1` + `llm_calls ×N`（含 `is_retry`）+ 回写 `conversations.slot_json`。

**标签：** 分析链路, 阶段划分, SSE 事件, 全留痕

## Q: SQL 守卫（`sql_guard`）具体拦什么、放什么？

**A:** 拦：非 `SELECT` 语句（含 `DROP` / `DELETE` / `UPDATE` / 多语句）、
表名不在白名单、危险函数、**R3 两套拆分混加**（按用途与按时段字段出现在同一聚合表达式里）、
未加 `LIMIT` 的明细查询（守卫强制追加，默认 1000 行，聚合查询的 LIMIT 仅作安全兜底）。
放：合法的多表 JOIN / CTE / 子查询 / 窗口函数（**CTE 别名要先收集，否则会被误判为"表不在白名单"**）。
另外守卫还会**自动为求极值的 Top-N 补 `IS NOT NULL`**（确定性规则，零模型调用）。
拦截结果落 `audit_logs`，且**不重试、不换路**（越权/危险信号，重试等于教模型试探边界）。

**标签：** SQL 守卫, 白名单, R3 混加, 强制 LIMIT, 不重试

## Q: pandas 沙箱的执行约束有哪些？

**A:** 两道关：
① **AST 预检**（`code_guard`）——禁非白名单 `import`、禁 dunder 属性、
禁 `open`/`eval`/`exec`/`__import__`/`subprocess`/`socket`；不通过直接拒绝，不进沙箱；
② **子进程执行**——超时 **10s 强杀**、内存上限 **512MB**（子进程内自检 RSS 超限自杀）、
结果行数上限 **5000**、**禁网禁写**（如实说明：靠 AST 预检，不做 OS 级断网）。
输入约定 `df / pd / np / px / go`，输出约定 `result`（DataFrame/Series/标量）与可选的 `fig`。
另有一条路由闸门：报表行数超过阈值（默认 10 万）时禁用 pandas 路径，提示改用 SQL 聚合。

**标签：** pandas 沙箱, 子进程, 资源限制, 路由闸门

## Q: 图表服务（`chart_service`）做了什么？

**A:** 按结果集形态**自动选图型**（时序→折线、分类对比→柱状、单行多指标→柱状、占比→饼图/堆叠），
并处理四类工程细节：**TopN 合并**（避免图例爆炸）、**大结果集抽稀**、
**缺采断点**（缺失时段断开而不是连成直线）、**粒度重聚合**（切换粒度时不重新查库）。
trace 颜色用**语义色**（峰/平/谷/未计量/异常/缺采），
但**不写主题色**（纸面/字体/网格由前端注入），并把口径标记写进 `layout.meta`
（刷新回放要用）。另提供 `POST /charts/rerender`（换图型/粒度，**不调用模型**）。

**标签：** 图表服务, 图型选择, 语义色, meta 标记, rerender

## Q: 模型分级（轻量/主力）是怎么用的？

**A:** 按 PRD 10.3：
- **轻量模型**用于 **slot 抽取**——短输出、结构化、并发量大，不需要强推理；
- **主力模型**用于 **SQL/代码生成与文字解读**——需要理解 Schema 与口径。
配置上是两个独立变量（`LLM_MODEL_LIGHT` / `LLM_MODEL_MAIN`），
每条 `llm_calls` 都会记录实际使用的模型与阶段，因此能按阶段统计成本。
另外：**关闭推理型模型的思考过程**（`LLM_ENABLE_THINKING=false`）——
本项目输出都是结构化短文本，开思考等于白烧额度（实测 4.0s/195 tokens → 0.9s/5 tokens）。

**标签：** 模型分级, 轻量模型, 主力模型, 关闭思考

## Q: 多厂商适配是怎么做的？

**A:** 只实现 OpenAI 兼容协议，配置全走 `.env` 中性变量：
`LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL_MAIN` / `LLM_MODEL_LIGHT` /
`LLM_TEMPERATURE` / `LLM_MAX_TOKENS` / `LLM_ENABLE_THINKING`。
`/system/health` 如实回报 `configured` / `provider` / `protocol` / `key_source`；
**模板占位值（如 `sk-xxxxxx`）一律视为"未配置"**并回落离线脚本模型（`ScriptedLLM`），
保证无 Key 时链路与回归测试仍能跑通。
已实测可切换：阿里云百炼（默认）、DeepSeek、Moonshot、智谱、本地 vLLM/Ollama 等。

**标签：** 多厂商, OpenAI 兼容, .env, 未配置回落, ScriptedLLM
