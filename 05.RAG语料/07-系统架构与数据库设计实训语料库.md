## Q: "架构约束"为什么要写"排除了什么方案"？

**A:** 因为约束的价值就在于**它剔除了哪些选项**。
本项目在约束章写明：前后端分离、两库分离与只读、单机 Windows 演示（**不引入 Docker / Nginx**）、
LLM 生成的代码必须在受控环境执行、分析过程用 SSE 推送。
每条都对应一个被排除的方案，例如"不引入 Docker"直接决定了部署与沙箱的实现形态
（沙箱必须自己用子进程 + 资源限制来做，而不能依赖容器）。
约束越早写清，后面越少返工。

**标签：** 架构约束, 排除方案, 部署形态, 早定边界

## Q: 时序图（sequenceDiagram）应该画哪几条？

**A:** 画**跨层协作且最容易出错**的几条流程，本项目 5 张：
① 提问全链路（含守卫拦截与重写分支）；
② 上传入库（sha256 去重分支 + 分批提交）；
③ 批量评测（逐题循环 + 报告生成）；
④ 澄清回路（澄清卡 → 回填 → 原地继续执行）；
⑤ 回归自检（**32 条**断言的执行链）。
画图要点：每张都要有**异常分支**（正常路径谁都会画）；
消息文本避免 `**`、`--`、`±`、`…` 等会让 Mermaid 渲染失败的字符。

**标签：** 时序图, 跨层协作, 异常分支, Mermaid

## Q: 架构图的"源码"和"PNG"怎么共存？

**A:** **Mermaid 源码留在 Markdown 内**（可读、可改、可 diff），
用脚本 `tools/mermaid2png.py` 离线渲染成 PNG（可交付、无网也能看）。
图名由代码块上一行的 HTML 注释指定（如 `<!-- name: seq_chat -->`），
脚本按名批量导出，本项目共 **11 张**（6 张流程图 + 5 张时序图）。
一个避坑点：若所有 PNG 体积几乎相同，先怀疑渲染成了"错误页"
（临时目录被提前删除导致 `ERR_FILE_NOT_FOUND`），而不是图内容有问题。

**标签：** Mermaid, PNG 导出, 图名约定, 错误页排查

## Q: 两个库各放什么？为什么这样分？

**A:** `reports.db`（**数据面**）只放报表数据：5 张预置表
（分钟 / 小时 / 日 / 月 / 用电结构）+ 用户上传生成的动态表；
**应用侧只读**（`mode=ro` + `PRAGMA query_only` + 表名白名单）。
`power_agent.db`（**控制面**）放用户、会话、消息、分析记录、报表元数据、
评测题库与批次，读写。
这样分的原因：系统要执行大模型生成的 SQL 与 pandas 代码，
**必须让它只能触达"只读的分析对象"**；系统数据与用户数据放在另一个库，
从架构上杜绝"AI 生成代码改坏系统表"的可能。

**标签：** 两库分离, 数据面, 控制面, 只读设计

## Q: 系统库有哪些表？各自职责是什么？

**A:** 10 张（实测）：
`users`（账号）｜`uploaded_reports`（报表元数据：含 `caliber_version` 口径版本、
`is_active` 系统默认活跃、`is_preset` 预置标记）｜`upload_files`（上传文件与 sha256，
支持重复文件复用）｜`conversations`（会话：含 `slot_json` 条件权威、`is_pinned` 置顶）｜
`messages`（消息：`content` 两种形态——普通文本或澄清卡 JSON）｜
`analyses`（分析记录：SQL/代码、结果快照、解读、重试、口径与提示词版本）｜
`llm_calls`（逐阶段模型调用：token、耗时、`is_retry`）｜
`audit_logs`（审计：事件类型白名单 17 类）｜
`eval_questions`（题库：120 题含 gold）｜`eval_runs`（评测批次：逐题明细存 `result_json`）。

**标签：** 系统表清单, 表职责, 核心字段, 10 张表

## Q: 数据库的表数量怎么核对？

**A:** 用 SQLite 查 `sqlite_master`，但**必须排除 SQLite 内部表**——
每个库都会有一个 `sqlite_sequence`（自增计数用），直接用 `count(*)` 会多算一张。
正确口径：**报表库 5 张 + 系统库 10 张 = 15 张**。
核对的命令要在 `where` 里加 `name not like 'sqlite_%'`：
一个容易踩的坑是在 PowerShell 里写 `python -c "..."` 时引号被吞掉
（写成 `type=table`），应改为在 SQL 里用 `?` 占位符传参、SQL 内不出现双引号。

**标签：** 表数核对, sqlite_sequence, 内部表, PowerShell 引号

## Q: 初始化、迁移与校验流程是怎样的？

**A:** 数据准备有 4 个脚本，**顺序不可颠倒**：
① `01_build_reports.py`——原始分钟数据 → 5 张报表 + 质量报告 + 口径锚点（A1–A5 在此算）；
② `02_build_schema.py`——→ Schema 结构化描述 + 注入文本；
③ `03_init_db.py`——按 DDL 事实源建库（`--force` 可重建；它**在库上重跑 A1–A5**，
校验"真正被分析的数据"）；
④ `04_build_eval_set.py`——→ 120 题评测集（gold 对真实库反算）。
另有 `05_migrate_audit_events.py`：审计事件白名单扩容的**幂等迁移**
（SQLite 无法 `ALTER CHECK`，只能重建表，正式库迁移时保留了 258 行历史审计）。

**标签：** 初始化流程, 脚本顺序, DDL 事实源, 幂等迁移

## Q: 什么是 DDL 事实源？为什么模型不调 `create_all()`？

**A:** 指**手写的 `scripts/sql/reports.sql` 与 `power_agent.sql` 是表结构的唯一权威**，
建库脚本执行它，SQLAlchemy 模型只做查询映射、不调用 `create_all()`。
这样做的原因：如果模型也能建表，就会出现"模型与 DDL 各说各话"，
改字段时容易只改一处；单一事实源让"改表"变成"改 SQL + 重建 + 回填文档"的固定三步。
配套惯例——**改 DDL 三件事**：改 SQL 文件 → 重建库并核对表结构 → 回填数据库文档与变更记录。

**标签：** DDL 事实源, 不 create_all, 三件事惯例, 单一权威

## Q: 删除行为（外键级联）应该怎么设计？

**A:** 在文档里维护一张**删除行为矩阵**，逐条写清 `ON DELETE` 取值与理由：
- 用户删除账号 → 其会话/消息/分析记录级联删除（`CASCADE`）——数据归属清晰；
- 会话删除 → 消息级联删除，但**分析记录保留**（`messages.analysis_id` 置空）——
  因为"清空历史"有两种口径：只清分析记录、或连会话一起清，要能给用户选择；
- 报表删除 → 回显受影响会话数（不静默影响用户当前会话）；
- **安全审计日志不随账号删除而清除**（合规要求），仅把 `user_id` 置空。

**标签：** 删除行为, 级联矩阵, 合规保留, 归属隔离

## Q: 容量与性能估算怎么写才可信？

**A:** 用**实测值**而不是估算：报表库约 408MB（分钟明细 207 万行占主要体积）、
系统库约 200KB；灌数实测 207 万行 × 16 列 **17.8s**（约 8.6µs/行）；
全量重建两库（解析 + 灌数 + 校验）约 29s。
另外记录一条工程经验：**批量灌数不要逐行走 ORM**——
实测 SQLAlchemy + `to_dict` 是 19.5µs/行，原生 sqlite3 + `itertuples` 是 12.7µs/行（ADR-011），
而且"**先灌数后建索引**"比边写边更新索引更快。

**标签：** 容量估算, 实测性能, 灌数优化, ADR-011
