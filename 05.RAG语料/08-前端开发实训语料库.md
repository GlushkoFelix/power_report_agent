## Q: 前端怎么调用 SSE 接口？为什么不用原生 EventSource？

**A:** 分析接口是 **`POST` + `Authorization` 请求头 + SSE**，
而浏览器原生 `EventSource` **只支持 GET、无法带自定义请求头**，
所以用 `@microsoft/fetch-event-source`（或自写 fetch 流式读取）。
两条工程约定：
① **不自动重连**——分析是有副作用的写操作（会落记录、会调用模型），断线重连等于"再问一遍"；
② 暴露 `AbortController` 支持**用户主动中断**（断开后后端链路随之取消）。
另外：**HTTP 已是 200 也要监听 `error` 事件**（业务失败通过 SSE 事件下发）。

**标签：** SSE 客户端, fetch-event-source, 不自动重连, 中途取消

## Q: 登录态与 401 是怎么处理的？

**A:** token 存 localStorage（键 `zdxb.token`），axios 请求拦截器自动加
`Authorization: Bearer <token>`；响应拦截器统一解包络 `{code, message, data, request_id}`，
`code !== 0` 时抛业务错误（`ApiError`，含 `error_code` / `hint` / `request_id`）。
**401 时**：清 token → Toast 提示 → 跳登录页，
并且**保留用户尚未发送的输入**（存 `zdxb.draft`）——
这条是用户实测反馈出来的体验点：不能因为登录过期把用户刚敲的一段话弄丢。

**标签：** 登录态, axios 拦截器, 401 处理, 草稿保留

## Q: API 层为什么要"统一包络拆解"？

**A:** 后端所有接口都返回 `{code, message, data, request_id}`，
若每个调用点都写 `res.data.data` 既啰嗦又易错。
前端在 axios 响应拦截器里**统一拆解成功包络**（业务代码直接拿到 `data`），
失败则统一抛 `ApiError` 并在页面按四级层次呈现。
好处：业务代码干净、错误处理只有一处、`request_id` 随手可用（排障时按 `rid=` 串日志）。

**标签：** API 层, 包络拆解, 统一错误, request_id

## Q: 前端契约类型为什么手写，不用自动生成？

**A:** 本项目选择**手写对齐后端 schemas**（`api/types.ts`）。
理由是：代码量不大、类型显式可读，且能在评审时"逐字段对着后端 schema 核"；
自动生成会引入额外工具链与构建耦合，收益不明显。
风险是可能过期，因此约定：**后端改契约必须同步改 `types.ts`**，
且用 `npx tsc -b --noEmit` 在 CI/回归里兜底（类型对不上立刻报错）。

**标签：** 契约类型, 手写类型, types.ts, 类型检查

## Q: 刷新页面后结果为什么能"回放"出来？

**A:** 靠两处数据：① 助手消息带 **`record_code`**，前端据此重拉
`GET /analysis/records/{code}` 拿回 SQL / 结果表 / 解读；
② 图表的**口径标记**写在 figure 的 `layout.meta` 里，
前端读回后重新注入主题即可复现同款图表。
这两条是前后端一起定的约定——没有它们，刷新后右栏就是一片空白（前端实测踩到过）。

**标签：** 刷新回放, record_code, layout.meta, 前后端约定

## Q: 为什么不用 `react-plotly.js`？

**A:** 该库年久失修、类型定义基于 React 17，与 React 18 的 `StrictMode` 双调用配合不好。
项目**自封装容器** `ResultChart.tsx`：直接 `Plotly.react(div, figure, layout, {responsive:true})`，
自己控制主题注入、重绘、点击回调与图片导出（`toImage`）。
额外收益是体积更小，并且能在构建时把 plotly 拆成独立 chunk（约 4.6MB），
避免拖慢首屏。

**标签：** Plotly 容器, 自封装, 首屏优化, 独立 chunk

## Q: 长等待时界面怎么反馈？为什么不做"假进度"？

**A:** 长等待必须有**阶段化反馈**（阶段时间线），但不能编造进度。
两条实际决策：
① 评测批次的运行期只显示"运行中 · 共 N 题 + 已耗时"，
**不显示"已完成 x/120"与实时正确率**——后端没有逐题进度端点，编不出来就不编；
② 评测的"中断"按钮实质是"停止轮询"，文案如实写"已停止跟踪（服务端仍会跑完）"
（批次是服务端 asyncio 任务，没有取消接口）。
原则：**宁可显示得保守，也不要给用户假的确定性**。

**标签：** 等待反馈, 阶段时间线, 不编进度, 如实降级

## Q: `ui_flow_check.mjs` 是做什么的？为什么必须串行跑？

**A:** 它是**端到端界面回归脚本**（无头 Edge + CDP），把用户实测反馈过的交互缺陷
固化成 **32 条可重跑的断言**（2026-10-14 复跑 32/32 通过）（如空态上传入口、连点新建会话不产生重复会话、
删除会话后主区同步、字段字典随报表切换更新、退出登录后重新登录回首页等）。
两条工程细节：
① 断言必须**与运行顺序无关**——脚本开头先做状态归一（走接口清理、不调模型、零 token）；
② 与 `ui_shot.mjs` **必须串行**——两者都操作同一账号的数据，并行会互相打乱计数断言，
因此用锁文件强制互斥，第二个启动者直接退出并提示（而不是给出一堆假失败）。

**标签：** 界面回归, 32 条断言, 顺序无关, 互斥锁

## Q: 前端开发最常见的三个问题是什么？

**A:** ① **CORS / 404**——开发期应配 Vite 代理（`/api` → `http://127.0.0.1:8000`），
前端同源调用，SSE 也不受跨域限制；② **AntD 样式被 Tailwind 覆盖**——
Tailwind 必须关闭 `preflight`；③ **窄屏"看不到结果"**——
右栏收进了抽屉，要在输入区上方留明显的「查看图表与表格」入口，否则用户以为查询失败。

**标签：** 常见问题, 代理配置, 样式冲突, 窄屏入口
