# 部署运维语料库

**主题：** 首次部署、启停探活、日常运维与故障排查
**适用范围：** 部署人员、运维人员
**版本：** v1.0

---

## Q: 系统的部署形态是什么？

**A:** **单机 + 无外部中间件**：
- 两个 SQLite 库（`reports.db` 只读 / `power_agent.db` 读写）都是本地文件；
- 大模型走 OpenAI 兼容 HTTP 接口（默认阿里云百炼）；
- 后端一个 Python 进程（FastAPI + uvicorn，端口 8000），
  前端一个 Node 进程（Vite，端口 5173）或构建后的静态文件。
两层拓扑：`浏览器 → 前端（5173） → 代理 /api → 后端（8000） → 两个 SQLite 文件`。

**标签：** 部署形态, 单机部署, 无中间件, 拓扑

## Q: 首次部署的步骤是什么？

**A:** 七步（详细见《部署运维手册》）：
① 准备环境（Windows 11 + Python 3.12+ + Node）；
② 在**项目根**建统一虚拟环境 `.venv` 并装依赖（`pip install -r 01.code/backend/requirements.txt`）；
③ 复制 `.env.example` 为 `.env` 并填 `JWT_SECRET_KEY` 与 `LLM_API_KEY`
（**`JWT_SECRET_KEY` 缺失会直接启动报错**，这是刻意设计）；
④ 装前端依赖（`cd 01.code/frontend && npm install`）；
⑤ **按顺序**跑数据脚本建库：`01_build_reports.py` → `02_build_schema.py` →
   `03_init_db.py`（`--force` 重建）→ `04_build_eval_set.py`（顺序不可颠倒）；
⑥ 启动后端（工作目录 `01.code/backend`）；
⑦ 启动前端（`npm run dev`）。

**标签：** 首次部署, 七步, 建库顺序, .env

## Q: 怎么启动、停止与探活？

**A:** **启动**（两个终端）：
```powershell
# 后端（工作目录必须是 01.code\backend）
cd e:\power_report_agent\01.code\backend
$env:PYTHONIOENCODING = "utf-8"
..\..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 前端
cd e:\power_report_agent\01.code\frontend
npm run dev
```
**探活**三层次：① 进程在不在（`Get-NetTCPConnection -LocalPort 8000 -State Listen`）；
② 接口通不通（`Invoke-RestMethod .../api/v1/system/health` → `status=healthy`）；
③ 依赖好不好（health 里的 `databases` 与 `llm.configured`）。
**停止**：按端口精确停止——
`Stop-Process -Id (Get-NetTCPConnection -LocalPort 8000 -State Listen).OwningProcess -Force`
（变量别用 `$pid`，那是 PowerShell 只读自动变量）。

**标签：** 启动停止, 探活三层次, 按端口停止, 环境变量

## Q: 怎么让局域网内其它机器访问？

**A:** 两步：
① 后端监听所有网卡：`--host 0.0.0.0`；
② 前端 Vite 也要允许外部访问（`vite.config.ts` 里设 `host: '0.0.0.0'` 或用 `--host`），
并让后端 CORS 允许该来源；
然后其它机器用 `http://<本机局域网IP>:5173` 访问。
注意 Windows 防火墙首次会弹"是否允许"，需要放行；演示前建议先用本机 `127.0.0.1`
跑通再切局域网。详细步骤与常见问题见《实训附录B》。

**标签：** 局域网访问, 0.0.0.0, 防火墙, 演示准备

## Q: 日志在哪里？怎么按一次请求排障？

**A:** 三处来源：
① **后端进程日志**（uvicorn 的标准输出/错误，含每个请求的访问日志）；
② **业务日志**（分析链路的关键节点：slot 兜底、形态自检触发、守卫拦截、超时等）；
③ **数据库留痕**（`analyses` / `llm_calls` / `audit_logs`——事后复盘最完整的证据）。
排障方法：拿用户界面上的 **`request_id`**，在后端日志里按 `rid=` 检索，
即可串起该请求的全过程（哪个阶段慢、哪次调用失败、是否触发重写或兜底）。

**标签：** 日志, rid 排障, 三类留痕, 复盘证据

## Q: 日常巡检要做什么？

**A:** 五条：
① 服务与端口（8000 / 5173）是否在监听；
② `health` 返回是否 `healthy`（两库可达 + 模型已配置）；
③ 磁盘：`02.data` 会随上传增长（库文件 408MB+，另有上传文件与日志），确认剩余空间；
④ 额度：按 `llm_calls` 统计各模型累计 token，避免演示当天才发现额度不够；
⑤ 数据基线：`quality_report.json` 的 A1–A5 是否仍通过（数据被改坏时最早在这里暴露）。

**标签：** 日常巡检, 五条, 磁盘与额度, 数据基线

## Q: 怎么做冷备份？

**A:** 三个要点：
① **不要直接复制正在被写入的库文件**（可能拿到不一致的页状态）——
   要么停服务后复制，要么用 `VACUUM INTO` 导出快照；
② 备份范围：`02.data/power_agent.db`（用户/会话/记录/评测）+ `02.data/reports.db`
   （若允许重建则可从脚本重建，不必备份 408MB）+ `.env`（含密钥，注意别提交到版本库）；
③ 恢复后要**复核口径锚点 A1–A5**，确认数据完整。
另注意：删除大表后 SQLite 文件体积不会自动缩小（需要 `VACUUM`），
所以"库文件大小不变"不代表删除没生效（可以用 `page_count` 变化判断）。

**标签：** 冷备份, VACUUM INTO, 不复制写入中文件, 恢复复核

## Q: 数据库结构变更（迁移）怎么做？

**A:** 本项目用"**重建表型迁移**"：
SQLite 不支持 `ALTER` 修改 `CHECK` 约束，所以当约束需要扩展时
（例如审计事件白名单从 10 类扩到 17 类），做法是：
新建带新约束的表 → 复制数据 → 删旧表 → 改名 → 单事务提交；
并写成**幂等脚本**（`05_migrate_audit_events.py`，可重复执行）。
一条真实教训：**约束是 CHECK 白名单时，新增取值必须同步改约束**——
本项目曾因漏改导致"解读编造数字"的告警在插入时被静默拒绝
（调用处有 `try/except` 掩盖），后来把白名单补齐并补了迁移脚本与用例。

**标签：** 迁移, 重建表, 幂等脚本, CHECK 白名单教训

## Q: 配置参数在哪里改？

**A:** 分两类：
① **环境类**（`.env`）：LLM 的 Key/端点/模型名/温度/思考开关、JWT 参数、
   应用端口、两个库的路径——**改完必须重启后端**；
② **代码内置常量**（改动需改代码）：登录锁定次数与时长、slot 超时（12s）与解读超时（8s）、
   沙箱超时/内存/行数上限、pandas 行数闸门（默认 10 万）、
   结果形态自检阈值（100 行）、各分页上限、SQL 强制 LIMIT（1000 行）等。
《部署运维手册》第 7 章有完整的参数表（含代码位置），换模型档位时**务必复核超时类常量**。

**标签：** 配置参数, .env, 内置常量, 换档位复核

## Q: 演示前要准备什么？

**A:** 四件事：
① 先跑 **`selfcheck`** 批次（零 token）确认链路、判分、报告全通；
② 检查**模型额度**是否够演示用（可在评测中心看历史批次的 token 消耗估算）；
③ 准备好数据：预置 5 张报表是否在、`reports.db` 与 `power_agent.db` 是否完好（A1–A5 通过）；
④ 若网络不稳，准备好**离线路径**：未配 Key 时链路会回落离线脚本模型，
   `selfcheck` 也能出报告（如实标注"不代表模型能力"）。

**标签：** 演示准备, selfcheck 预热, 额度检查, 离线预案
