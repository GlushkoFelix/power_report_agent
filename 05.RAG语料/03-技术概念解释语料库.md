**主题：** 智电析报涉及的核心技术概念与名词解释

## Q: 什么是 Text2SQL？在本项目里怎么落地？

**A:** Text2SQL 指把自然语言问题转译为 SQL 查询语句。
本项目落地为两步：先用**轻量模型**做 slot（槽位）抽取，把问题结构化为 8 个字段
（时间范围 / 粒度 / 指标 / 维度 / 过滤 / 对比 / 意图 / 图表倾向）；
再用**主力模型**结合 Schema 注入文本生成 SQL 或 pandas 代码，经守卫校验后在只读环境执行。

**标签：** Text2SQL, 落地方式, slot 抽取, 两阶段生成

## Q: 什么是 Schema 注入？为什么要单独维护一份注入文本？

**A:** 大模型不知道数据库里有什么表、什么列、什么口径，必须把数据结构"喂"给它，
这份文本就是 Schema 注入文本：逐列标注**单位、口径、是否可聚合、两套拆分不可混加**等约束。
项目约定它**在上传入库阶段一次生成并落库**，读取时零拼装——
这样"前端字段字典"与"喂给模型的文本"**逐字一致**，不会出现"文档说一套、模型看另一套"。

**标签：** Schema 注入, 注入文本, 口径标注, 单一数据源

## Q: 什么是 slot（槽位）？为什么用"增量抽取"？

**A:** slot 是问题的结构化表示，本项目固定 8 个键。
**增量抽取**指每次只抽"本轮提到的字段"，未提到的留 `null`，再与会话已有 slot 合并
（规则：显式给出即覆盖、未提及即继承、维度变更即替换）。
这样做是为了支撑多轮追问——"只看工作日的"只需要带上 `filters`，
不必让模型重复理解前几轮的全部条件。合并结果回写 `conversations.slot_json`，
是会话级条件的唯一权威。

**标签：** slot, 增量抽取, 多轮继承, 合并规则

## Q: 什么是澄清回路（clarify）？

**A:** 当关键槽位缺失（本项目是 **metric 必填**）时，系统不猜、而是返回一张**澄清卡**
（含 2–3 个可点选选项与"都不是，我重新描述"），用户点选后**原地继续执行**原问题。
要点：澄清是正常交互（用主色描边，不是红色错误）；**澄清轮不落 `analyses` 记录**
（它没有执行任何东西），事件序列是 `status → slot → clarify → meta → done(record_id=null)`。

**标签：** 澄清回路, clarify, 澄清卡, 不落记录

## Q: SSE 是什么？本项目定义了哪些事件？

**A:** SSE（Server-Sent Events）是服务端向浏览器的单向流式推送，基于普通 HTTP。
本项目共 **10 个事件**：`status`（阶段推进）/ `slot`（条件）/ `clarify`（澄清卡）/
`code`（SQL 或 pandas 代码）/ `table`（结果表）/ `chart`（图表 figure）/
`narrative`（文字解读）/ `meta`（耗时与 token）/ `error`（失败）/ `done`（结束，带 `record_id`）。
关键约定：**业务失败时 HTTP 仍是 200**，失败信息通过 `error` 事件下发，因此前端必须监听 `error`。

**标签：** SSE, 事件契约, 10 个事件, error 事件

## Q: 什么是"双轨制"错误码？

**A:** 指响应包络 `{code, message, data, request_id}` 里：
`code` 与 **HTTP 状态码同值**（成功为 0，保留 HTTP 语义，网关/日志/监控照常工作），
而**业务错误码放 `data.error_code`**（如 `E_SQL_FORBIDDEN`、`E_AUTH_LOCKED`），
并附 `data.hint` 给出"为什么失败、怎么修"。
好处：前端既能按 HTTP 做通用处理，又能按业务码给精准文案（UIUX 据此做分级错误呈现）。

**标签：** 错误码, 双轨制, 响应包络, hint

## Q: 什么是 sqlglot？它在项目里做什么？

**A:** sqlglot 是一个纯 Python 的 SQL 解析/转换库，能把 SQL 解析成**抽象语法树**。
项目用它实现 SQL 守卫：判定单语句、仅 `SELECT`、表名白名单、危险函数、
追加 `LIMIT`，以及两条业务规则（R3 两套拆分混加检测、求极值时补 `IS NOT NULL`）。
比正则匹配可靠得多，但要处理 CTE 别名（先收集 CTE 名再判白名单，否则误拦）。

**标签：** sqlglot, SQL 解析, 语法树, 守卫实现

## Q: 什么是 AST 预检？

**A:** 在执行模型生成的 pandas 代码前，先用 Python 的 `ast` 模块解析代码，
**在语法树层面**禁止危险操作：非白名单 `import`、双下划线（dunder）属性、
`open` / `eval` / `exec` / `__import__` / `subprocess` / `socket` 等。
预检不通过直接拒绝（不进沙箱）；通过后才在子进程里执行。
预检 + 子进程隔离是两道互补的防线：前者拦"明面上的危险"，后者兜"跑飞了"。

**标签：** AST 预检, code_guard, 危险调用, 沙箱前置

## Q: 什么是 RAG？本项目的 `05.RAG语料` 是做什么的？

**A:** RAG（Retrieval-Augmented Generation）指先检索知识库、再让模型基于检索内容回答，
用于把答案约束在可信资料范围内。
本项目的 `05.RAG语料/` 是**为教学与技术问答准备的语料库**（按主题分文件、以 Q/A 形式组织），
**不进入系统运行时**——它服务于"AI 助教"场景（例如把语料挂到平台的知识库助手上），
让回答有据可查、不编造。

**标签：** RAG, 语料库, 知识问答, 不进运行时

## Q: FastAPI 的依赖注入在本项目怎么用？

**A:** 用 `Depends` 把"鉴权后的当前用户"、数据库会话、请求上下文注入到端点函数里。
典型用法是 `user: CurrentUser = Depends(get_current_user)`——
端点只声明"我需要一个已登录用户"，token 解析、401/403 处理都在依赖里统一完成，
端点代码因此保持干净；测试时也可以很方便地替换依赖。

**标签：** FastAPI, 依赖注入, Depends, 鉴权依赖

## Q: Pydantic 在项目里承担什么角色？

**A:** 三件事：
① **请求校验**（如 `ChatIn` 要求 `conversation_code` 与 `message`，密码强度、limit 范围）；
② **响应序列化**（把内部对象转成对外契约字段，避免泄露多余字段）；
③ **配置加载**（`pydantic-settings` 读 `.env`，缺 `JWT_SECRET_KEY` 直接在启动时报错）。
注意一个约定：**业务级参数越界返回 400 + `E_VALIDATION`**，而不是框架默认的 422。

**标签：** Pydantic, 请求校验, 响应模型, 配置加载

## Q: SQLAlchemy 在项目里怎么用？

**A:** 只用它做**查询映射**（`db/models/` 下 10 张表的 Declarative 模型），
**不调用 `create_all()`**——DDL 的唯一事实源是手写的 `scripts/sql/*.sql`，
由建库脚本执行。这样做的好处是：表结构只在一处维护，模型与库不可能"各说各话"；
写路径（上传入库）刻意**不走 ORM**，用原生 sqlite3 + `executemany` 分批提交
（实测 12.7µs/行 vs ORM 逐行 19.5µs/行）。

**标签：** SQLAlchemy, 查询映射, 不 create_all, DDL 事实源

## Q: 什么是口径版本（caliber_version）？

**A:** 是给"数据口径"打的版本号（本项目为 `caliber-v1.0`），随报表元数据一起落库、
也写进每条分析记录。作用是**回归识别**：口径变更（例如电压越界阈值从 200–260V 收紧为
210–250V 且 ≥30 分钟）后，能一眼分辨哪些历史记录是旧口径下产出的，避免拿不同口径的数字对比。

**标签：** 口径版本, caliber_version, 回归识别, 口径变更

## Q: 为什么评测要固定 `temperature = 0`？

**A:** 评测的目的是比较"配置与模型的差异"，而不是比较"采样随机性"。
`temperature = 0` 让同一题在同样输入下尽量产出同样输出，
这样两次跑批的差异才能归因到"提示词改了 / 模型换了"；否则分不清是改动生效还是运气。
同理，报告要求写明**模型名 / 提示词版本 / 温度 / 是否合并批次**四要素。

**标签：** 评测口径, temperature, 可复现, 报告四要素

## Q: 什么是"分层子集"与"跨批合并"？为什么要如实标注？

**A:** 受模型额度限制，有时跑不完 120 题，只能跑一个**分层子集**（按题型/难度抽样），
或把 120 题拆成几批跑再**合并**。
两者都会影响口径：子集覆盖不全、合并批次不是"同批同配置跑出"。
所以项目规定：**报告头部必须写明是子集还是全量、是否合并、各批的模型与提示词版本**，
引用数字时也要一并说明——否则"120 题成绩"这种说法会被误解为单批单配置的结果。

**标签：** 分层子集, 跨批合并, 口径标注, 如实报告

## Q: 什么是"结果形态自检"？

**A:** 指执行之后检查**结果的形状**是否与问题匹配（不看数值对错）：
问"占比"却返回上千行明细、问"最高/最低"却返回明细行、
"只看工作日"这类**筛选型追问**却把上一轮的分组维度整列丢掉——这三类都判为形态错误，
带原因交给重写环重写一次。
之所以要做：这类问题**语法合法、守卫放行、执行也不报错**，只有看结果形态才能发现。
判定取保守口径（只对"全期/年"这类汇总粒度与筛选型追问生效），避免误伤"逐日给出比率"这类合法形态。

**标签：** 结果形态自检, 可机检, 重写环, 保守口径
