# 错误处理方案语料库

**主题：** 错误码体系、界面呈现与常见故障排查
**适用范围：** 开发者、运维人员、用户支持
**版本：** v1.0

---

## Q: 项目怎么处理错误？分哪几层？

**A:** 四层配合：
① **HTTP 语义**：401/403/404/400/413/429/500 表达"类别"；
② **业务错误码 `E_*`**：放在 `data.error_code`，表达"具体原因"；
③ **`data.hint`**：给出"为什么失败、怎么修"的可执行建议（前端会显示成第二行灰色文字）；
④ **界面呈现**：按五种层次渲染（内联校验 / 卡片错误块 / Toast / 拒答卡片 / 澄清卡片）。
设计原则：**红色只留给真正的执行失败与安全拦截**；澄清用主色、拒答用中性灰。

**标签：** 错误处理, 四层配合, 错误码, hint, 呈现层次

## Q: 前端的五种呈现层次分别用在什么场景？

**A:** | 层次 | 场景 | 样式 |
| --- | --- | --- |
| 内联校验 | 表单/上传字段错误 | 输入框红描边 2px + 就地 11px 红字提示 |
| 卡片错误块 | 分析执行失败（SQL/代码/沙箱超时） | 红描边卡片：错误码 + 原因 + 已尝试路径 + 操作按钮 |
| Toast | 鉴权失效、限流、网络异常、成功提示 | 右上角，4s 消失，带 `request_id` |
| 拒答卡片 | 超出报表范围、预测类问题 | **中性灰** + 为什么不能答 + 2 个推荐问法 |
| 澄清卡片 | 信息不足（时间/指标/报表/粒度） | **主色描边** + 2–3 个可点选选项 + "都不是，我重新描述" |

**标签：** 五种呈现, 使用场景, 颜色语义, 卡片设计

## Q: 安全拦截的错误信息为什么"不能重试"？

**A:** 危险请求（`DROP TABLE`、文件访问、提示词注入）被拦截后，
**重试没有意义**（同样的输入还会被拦），而且"允许重试"等于引导用户/模型去试探守卫边界。
所以安全拦截卡片：
① 红描边 + ⛔ 图标 + 展示被拦截内容摘要 + 命中规则（如 `sqlglot:non_select`）+ 动作 blocked；
② **不提供「重试」按钮**，改为「换个问法」引导；
③ 说明"已写入安全审计日志"；
④ 命中注入规则时**不展示模型原文与完整 system 提示词**（保护提示词资产）。
这与"执行失败"（可修复、给重试）在视觉与交互上都要明显区分。

**标签：** 安全拦截, 不重试, 换个问法, 提示词保护

## Q: 遇到 500 或功能异常，第一步做什么？

**A:** 找 **`request_id`**。每个响应都带它（响应头与包络里都有），
后端日志按 `rid=` 串起一次请求的全部阶段日志；
把它抄给开发，能直接定位到具体请求与异常堆栈位置。
然后按类别分流：
- **500 且 hint 为空** → 后端异常，看日志堆栈；
- **400 `E_VALIDATION`** → 请求参数问题，按 `hint` 修；
- **401/403** → 鉴权/权限问题（注意越权返回的是 **404**）；
- **502/连接被拒** → **后端没起**（前端代理转发失败），这是最常见的"假故障"。

**标签：** 排障第一步, request_id, 日志串联, 502 假故障

## Q: 前端页面能打开但一提问就失败，是什么原因？

**A:** 大概率是**后端没启动**（或端口不对）。
前端通过 Vite 代理把 `/api` 转发到 `http://127.0.0.1:8000`，
后端不在时表现为代理层 `ECONNREFUSED`/502。
排查顺序：
① `Invoke-RestMethod "http://127.0.0.1:8000/api/v1/system/health"` 看后端是否活着；
② `Get-NetTCPConnection -LocalPort 8000 -State Listen` 看端口是否被占/被谁占；
③ 确认后端的**工作目录是 `01.code\backend`**（否则 `app.main:app` 找不到模块）。
若想换端口，前端可用环境变量 `VITE_BACKEND` 指向别的地址。

**标签：** 后端没起, 代理失败, 502, 工作目录

## Q: 启动后端报 `WinError 10048`（端口占用）怎么办？

**A:** 这说明**已经有一个后端在 8000 上跑着**（不是启动失败）。
先确认占用者是谁，再决定"直接用"还是"停掉重启"：
```powershell
# 看占用进程
Get-NetTCPConnection -LocalPort 8000 -State Listen | Select-Object LocalAddress, Port, OwningProcess
Get-Process -Id (Get-NetTCPConnection -LocalPort 8000 -State Listen).OwningProcess |
  Select-Object Id, ProcessName, StartTime, Path

# 确认可用后直接用；要重启就先按端口精确停止
$procId = (Get-NetTCPConnection -LocalPort 8000 -State Listen).OwningProcess
Stop-Process -Id $procId -Force
```
注意：变量别取名 `$pid`（PowerShell 只读自动变量）。
前端则相反——`strictPort: false`，5173 被占会自动换到 5174。

**标签：** 10048, 端口占用, 精确停止, strictPort

## Q: 报 `E_LLM`（模型调用失败）常见原因是什么？

**A:** 三种：
① **未配置 Key 或 Key 失效** → 看 `/system/health` 的 `llm.configured` 与 `key_source`；
② **模型名与该厂商不匹配**，或该模型不接受 `response_format`（JSON 模式）——
   客户端会做"去参重试"兜底，但仍应换成受支持的写法；
③ **限流**（批量评测时更明显）——降低并发/加大退避，或在控制台确认该模型的 QPS 限制。
另注意：未配置 Key 时链路会**回落离线脚本模型**（可跑通但不代表模型能力），
而评测的 `impl=real` 会**直接 400 并提示改用 `selfcheck`**，不会静默回落。

**标签：** E_LLM, Key 失效, 模型名不匹配, 限流

## Q: `database is locked` 怎么解决？

**A:** SQLite 是单写者模型，长事务或大量小事务会长时间持写锁。
处理办法：
① 写路径（上传入库）用**独占写连接 + 分批提交**缩短持锁时间；
② 读路径用**只读连接**（`mode=ro` + `query_only`），不参与写锁竞争；
③ 批量灌数**先灌数后建索引**（避免边写边更新索引）；
④ 确认没有另一个进程（如手工开的 sqlite3 客户端）在写同一个库。
本项目实测：207 万行灌数 17.8s，端到端上传两段式 49.9s，过程中未出现锁等待失败。

**标签：** database is locked, 单写者, 分批提交, 只读连接

## Q: 登录被锁定了怎么办？

**A:** 这是**安全策略**而非故障：连续 5 次密码错误起**锁定 5 分钟**
（返回 429 + `E_AUTH_LOCKED`，带剩余秒数，前端展示倒计时）。
要点：
① 锁定期间**即使密码正确也不放行**；② 只有**成功登录**才清零失败计数；
③ 锁定到期后计数不清零（防"卡点刷密码"）；
④ 用户名不存在与密码错误给**同一文案**（防账号枚举）。
用户处理方式就是等倒计时结束；管理员若确需立即解锁，按运维流程清理该账号的失败计数。

**标签：** 登录锁定, 5 次 5 分钟, 防枚举, 倒计时

## Q: 上传 CSV 失败怎么排查？

**A:** 按错误码分流：
- `E_FILE_TYPE` → 非 CSV/编码不对（建议 UTF-8 CSV）；
- `E_FILE_TOO_LARGE`（413）→ 超过大小上限；
- `E_NO_TIME_COLUMN` → 缺时间列（表头需含 Date/日期/时间戳 等），
  错误详情里会列出**实际发现的列名**，用户不用回看文件就能改；
- `E_INGEST_FAILED` → 入库阶段失败（看是否重复列名、类型异常）；
- 重复文件 → 不算错误：返回 `is_duplicate=true` 并定位已有报表（sha256 复用）。
失败详情里通常带"定位信息"（`duplicate_columns` / `found_columns` / `size_mb`），
前端把它们拼进提示第一行，让用户可直接改对。

**标签：** 上传失败, 错误码分流, 定位信息, 重复文件

## Q: SSE 一直停在第 1 阶段（"正在解析问题"）怎么办？

**A:** 四个检查点：
① 是否用了原生 `EventSource`（不支持 POST 与鉴权头）→ 换 `fetch-event-source`；
② 中间层是否**缓冲/压缩**了 `text/event-stream`（反向代理攒批会让事件"迟迟不来"）；
③ **是否监听了 `error` 事件**——业务失败仍返回 HTTP 200，只看状态码会误以为"在跑"；
④ 后端模型是否卡在某个阶段 → 有**阶段超时兜底**（slot 12s 走规则兜底、解读 8s 跳过），
正常情况下不会无限等待。
用项目自带 `sse_probe.py` 可以直接看各事件到达时间与是否"攒批回放"。

**标签：** SSE 卡住, 事件缓冲, error 事件, 阶段超时
