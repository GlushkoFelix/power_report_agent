**主题：** 测试分层、口径校验、评测执行与结果解读
**适用范围：** 测试者、项目验收与答辩准备
**版本：** v1.0

## Q: 项目的测试分成哪几层？

**A:** 四层，各管一段：
① **单元测试**（pytest，**365 条用例 / 25 个文件**；2026-10-19 更新）——后端行为与安全边界；
② **契约冒烟**——用 `Invoke-RestMethod`/curl 验接口包络与错误码；
③ **端到端界面回归**（无头 Edge + CDP，**32 条断言**）——界面交互与用户反馈缺陷；
④ **效果评测**（**120 题**）——模型能力与 bad case 归因。
四层互不替代：单元测试全绿不等于界面正确，界面全对不等于模型答得准。

**标签：** 测试分层, 303 用例, 31 断言, 互不替代

## Q: 数据口径校验（A1–A5）为什么排在最前面？

**A:** 因为**口径错了，后面所有分析都错**——图表再漂亮也是错的结论。
A1–A5 校验的是数据底座本身：
三级总量一致（A1）、未计量占比（A2）、有效分钟占比（A3）、异常日（A4）、各表行数（A5）。
实测全部通过：三级总量三处均 **37283.7477 kWh**（偏差 0）、未计量 **51.1977%**、
有效分钟 **98.7486%**、异常日 **81/1442**。
校验内建在数据脚本里（01 用未舍入值算、03 在库上重跑），A1/A2 失败时脚本返回非 0，可当门禁。

**标签：** 口径校验, A1-A5, 数据底座, 门禁

## Q: 评测判分是怎么做的？容差是多少？

**A:** **三级兜底**（全不过才判错）：
① **列位置对齐**（生成的列数与 gold 相同则按位置比对，**行序无关**）；
② **列名归一**后比对；
③ **单列宽松**（日期/数值形态等价，如 `'2006-12'` ≈ `12`）。
数值容差 `max(绝对下限, |值| × 1e-3, 展示级舍入 5e-3)`，
其中普通列绝对下限 **1e-6**、比率列 **1e-4**（百分比 ±0.01 个百分点）。
**放宽的是"展示级舍入"，不是口径错误**——比率用错分子分母、混加两套拆分这类问题照样判错。
报告里还会给"判分档命中分布"，用来区分"答案对但列位置不同"与"真的算错"。

**标签：** 判分, 三级兜底, 容差, 判分档

## Q: 120 题评测集是怎么构成的？跑完要多少记录？

**A:** **120 题**，6 类题型（stat / agg / compare / anomaly / structure / multi_turn）、
3 档难度（easy / medium / hard），其中 **18 道口径陷阱题**（标注 R1/R3/R6/R7 红线）。
**15 道多轮题各要跑两轮**，因此完整跑批是 **135 条记录**——
这一点直接影响额度预算（单条记录成本 × 135）。多选题真句按换行拆轮顺序提问，判分只看最后一轮。

**标签：** 评测集构成, 120 题, 135 条记录, 多轮两轮

## Q: "结论命中率"为什么比执行正确率难达标？

**A:** 执行正确率看"SQL 与结果对不对"，判断标准是确定的；
结论命中率看"**文字解读里有没有说到关键数值**"（如"峰段占比 33.2%"），
它对**措辞**极敏感——同一个正确结果，解读写成"三分之一左右"就可能不命中锚点。
实测：执行正确率常 94–100%，而命中率在 **82.5%–90.0%** 区间波动，
只有个别批次单批达标 ≥90%。所以项目把它作为**独立未达标项**登记，
并明确它不是链路问题，而是"解读表达"的问题。

**标签：** 结论命中率, 未达标, 措辞敏感, 独立登记

## Q: `selfcheck` 与 `real` 两种评测模式有什么区别？

**A:** `selfcheck` 用**离线脚本模型逐题回放题库 gold_sql**，
用来验证"**题库 → 分析链路 → 判分 → 指标 → 报告**"整条链路自洽——
正常结果应≈100%，**任何偏差都说明链路坏了**（而不是模型不好），且**零 token 消耗**。
`real` 走真实模型，未配 Key 时**返回 400 并给 hint**、**绝不静默回落**。
两者共用同一套判分与指标代码（避免两套口径）；
自检批次的报告与前端指标卡都**置顶标注"不代表模型能力"**。

**标签：** selfcheck, real, 链路自洽, 不代表模型能力

## Q: 一次真实评测要花多少 token？怎么预算？

**A:** 先测"单条记录成本"，再乘记录数（120 题 = **135 条记录**）：
| 模型 | 单条记录实测 | 135 条外推 |
| --- | --- | --- |
| deepseek-v4-flash-0731 | 7,144 | ≈96 万（实测 957,305 ✓ 装得下 1M） |
| kimi-k3 | 7,374 | ≈100 万（实测 995,533 ✓ 贴线） |
| qwen3.8-max 族 | **8,342–8,411** | **≈113 万 ✗ 单份 1M 装不下** |
因此换模型后**必须重算**：装不下就先分段（例如主段 100 题用新额度模型、
尾段用同族模型的剩余额度补齐），**不要跑到一半爆额度**——那会让整批变成"额度错误污染"的脏数据。
另外：slot 命中规则快通道能省一次调用（实测 4,569 vs ~8,400 tokens/条）。

**标签：** 额度预算, 单条记录成本, 135 条, 分段跑

## Q: 遇到错题怎么归因与迭代？

**A:** 报告会给**五类归因**（口径理解错误 / SQL 语法与函数 / slot 继承错误 /
执行失败未重试成功 / 结果口径偏差），并对每题给出：题号、现象、根因、修法与验证方式。
根因**必须读生成的 SQL 与 slot** 才能定位（只看"对/错"没法归因）。
迭代原则：
① 先分清"**模型答错**"与"**链路失败**"——两者混在一起会让方向跑偏；
② 若某类错误属于"**规则早已明文但模型不照做**"，就不要再加提示词文字，
改成**生成后的确定性校验**（守卫补 NULL、结果形态自检、词面兜底）；
③ 修完必须**回归**并用数字说明（如"q096 修复后单题 1/1，且少一次模型调用"）。

**标签：** 错题归因, 五类归因, 迭代方向, 回归验证

## Q: 复查时最容易发现哪类问题？

**A:** **"文档写的数字过期了"**。本项目一次全仓一致性核对就修出多处，例如：
用例数 254 → 293 → **303**、断言 27 → **31**、截图 7 → **8** 张、
端点数 43 → **39**、安全用例 35+10 → **40+13**、
前端技术栈被误写为 React 19 / AntD v6 / Tailwind v4（实际 **React 18.3 / AntD 5.22 / Tailwind 3.4**）。
教训：**凡是可核对的数字，都要在收尾时逐处对一遍**；
且历史版本目录**不要改**（它记录"当时是什么样"），只改当前版本文档。

**标签：** 全仓核对, 过期数字, 一致性, 历史版本不改
