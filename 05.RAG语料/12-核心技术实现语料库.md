# 核心技术实现语料库

**主题：** 分析链路的关键技术实现（含踩坑与设计取舍）
**适用范围：** 后端开发者、Agent 开发者
**版本：** v1.0

---

## Q: 一次提问从自然语言到图表，中间发生了什么？

**A:** 六个阶段：
① **slot 增量抽取**（轻量模型或规则快通道）→ 与会话 `slot_json` 合并 → 澄清检查；
② **生成**（主力模型）：结合 Schema 注入文本生成 SQL 或 pandas 代码，并自报 `route`；
③ **守卫**：SQL 走 `sql_guard`（语法树白名单），pandas 代码走 `code_guard`（AST 预检）；
④ **执行**：SQL 走只读连接；pandas 走子进程沙箱（超时/内存/行数限制）；
⑤ **结果形态自检** + 失败**带原因重写一次**（必要时换路径）；
⑥ **图表与解读**：图表服务按结果形态选图型，主力模型生成文字解读与关键数值；
全程 SSE 推送，并落 `messages` / `analyses` / `llm_calls` 三类留痕。

**标签：** 分析链路, 六阶段, 双工具路由, 留痕

## Q: 什么是"规则快通道"？它省了什么？

**A:** 当问题足够简单明确时，slot 抽取不必调用模型——用规则直接产出增量。
出手条件（四个同时成立）：**指标唯一**（词面恰好命中一个指标）、
**不含复杂语义**（对比/分组/占比/趋势/过滤等约 40 个拦截词都不出现）、
**会话条件干净**（无 `filters`、无 `compare`）、**时间范围可规则确定**。
收益：省掉一次 LLM 往返（约 1.5–2.0s），端到端平均 8,387ms → 7,937ms。
开关是 `FASTPATH_ENABLED`（关掉即回到"每次都调模型"的旧行为，便于 A/B 与回归）。

**标签：** 规则快通道, 出手条件, 省一次往返, FASTPATH_ENABLED

## Q: 多轮追问是怎么继承条件的？

**A:** 靠会话级 `slot_json` 与"增量抽取 + 合并"：
**只抽本轮提到的字段**（未提及留 `null`），再按三类规则合并——
**显式给出即覆盖**（"改成 2020 年 8 月"）、**未提及即继承**（"只看工作日的"只加 `filters`）、
**维度变更即替换**（"再按月汇总一次"改 `granularity`）。
合并结果回写会话，成为后续追问的基线。
`filters` 是对象数组 `{field, op, value}`，同一字段后一次会**替换**前一次（避免两条矛盾过滤）。

**标签：** 多轮继承, 增量合并, 覆盖与替换, slot_json

## Q: 什么时候会触发澄清？怎么避免"过度澄清"？

**A:** 触发规则（优先级从高到低）：
① 模型输出 `intent=澄清` 且 `missing_slot` 在合法白名单内（语义级歧义）；
② 规则兜底：合并后**`metric` 仍缺失**（metric 必填不可清除）；
③ `time_range` 缺失**不澄清**（继承会话，再没有就默认"全期"，避免每题都弹框）。
**防过度澄清**（实测曾有 15% 的题只返回澄清卡、拿不到结果）：
① 若模型报"缺指标"但问题里**确有指标词** → **驳回模型判断**，按词面补齐指标继续执行；
② 澄清卡选项从 Schema 全量指标清单取（而非只取前 3 个）；
③ **元数据类问题**（问"表里有多少行"）也纳入词面兜底，
否则会被判"缺指标"而永远拿不到结果（这是实测踩过的坑）。
另一个事实：**澄清轮不落 `analyses` 记录**，事件是 `status → slot → clarify → meta → done(record_id=null)`。

**标签：** 澄清触发, 过度澄清, 词面兜底, 澄清轮不落库

## Q: 生成失败或结果不对时怎么"自愈"？

**A:** 一张**重试/换路矩阵**（总预算额外尝试 ≤2 次）：
- SQL **执行报错**（列不存在等）→ 把错误信息喂回模型**重写**一次；
- **R3 混加命中** → 原路径回灌重写一次（这是"可自动修复"的错误）；
- pandas 代码被 AST 拦或执行异常 → **换 SQL 路径**；
- SQL 路径重写仍失败 → 换 pandas 路径；
- **守卫基础拦截**（非 SELECT / 表名不在白名单 / 危险函数）→ **不重试不换路**，直接失败并落审计
  （越权/恶意信号，重试等于教模型试探守卫边界）。
重试与换路都会落库（`retries` / `path_switched`），前端在"执行信息"里可见
（如"已自动重写 1 次，并已切换到 pandas 路径"）。

**标签：** 自愈, 重试矩阵, 换路径, 守卫不重试

## Q: "结果形态自检"解决什么问题？判定条件是什么？

**A:** 解决三类"**语法合法、守卫放行、执行也不报错**"的隐蔽错误：
① 问**占比/比例**却返回上千行明细（把逐行比率列当答案）；
② 问**极值/排名**却返回明细行；
③ **筛选型追问**（"只看工作日的"）把上一轮的分组维度整列丢掉。
判定取保守口径：
①② 只在**汇总粒度**（全期/年）+ 结果行数超阈值（100）时触发；
③ 只在**筛选型追问词面**（只看/只要/仅看/只保留/排除）+ 槽位有分组维度 + 生成的 SQL
**没有 `GROUP BY`** 时触发。
触发后当作一次失败，**带原因交给重写环重写一次**。设计意图是那句总结：
**"能在代码里机检的事，就别指望模型。"**

**标签：** 结果形态自检, 三类形态, 保守口径, 可机检

## Q: 守卫为什么要"自动补 `IS NOT NULL`"？

**A:** 因为"求极值必须排除 NULL"是一条**早就写在提示词里的规则**，但实测中弱档位模型
仍会生成 `ORDER BY x ASC LIMIT 1` 而取到 NULL 行（SQLite 里 `ORDER BY` 会把 NULL 排最前，
于是"最低的那天"落到了没有数据的那天）。
既然这是**确定性规则**，就下沉到代码：守卫识别"求极值的 `ORDER BY ... LIMIT k`"（k ≤ 5）
后自动追加 `AND 列 IS NOT NULL`，**零模型调用**。
配套加了一条守卫日志——因为落库的 SQL 无法区分 `IS NOT NULL` 是模型写的还是守卫补的，
这条日志是唯一可核验的痕迹。

**标签：** 守卫补 NULL, 确定性规则, 零模型调用, 可核验日志

## Q: 图表怎么自动选类型？

**A:** 按结果集的**形态**判断（而不是按问题字面）：
单行多指标 → 柱状（避免画成一个孤点）；时序（含日期/月列）→ 折线；
分类对比 → 柱状；占比 → 饼图或堆叠柱。
另外四个细节：**TopN 合并**（类别过多时合并为"其他 N 项"）、
**抽稀**（点太多时降采样）、**缺采断点**（缺失时段断开，不连成直线误导趋势）、
**粒度重聚合**（切换粒度时在已有结果上重算，不重新查库）。
选型结果与口径标记写进 `layout.meta`，供刷新回放与前端二次渲染使用。

**标签：** 图表选型, 形态判断, TopN, 缺采断点, layout.meta

## Q: 为什么强调"SSE 真流式"？怎么做到的？

**A:** 因为"攒完整批再一次性推"会让首字延迟等于总耗时（实测 5,927ms），
用户会觉得系统卡死。做法是引入 `EventSink`（`list` 子类，覆盖 `append`——
事件一产生就回调入队），端点侧把链路放进 `asyncio.Task` 并发跑、边收边推，
客户端断开即取消链路。
效果：**首字 5,927ms → 10–16ms**，且事件真正增量到达
（`status` → `slot` → `code` → `table` → `chart` → `narrative` → `meta` → `done`）。

**标签：** SSE 真流式, EventSink, 首字延迟, 断开取消

## Q: 为什么要有"阶段超时兜底"？

**A:** 因为大模型的响应时间不稳定，某个阶段卡住会让整题失败或拖到 20s+。
兜底设计：
- **slot 阶段超时 12s** → 用**规则兜底**（比快通道宽松：不查拦截词、允许多指标）
  直接产出增量继续走；
- **解读阶段超时 8s** → **跳过解读**（结果表与图表照给，`status` 仍成功，
  界面如实说明"解读未生成"）。
一条重要教训：**超时阈值与兜底规则必须随模型档位复核**——
本项目曾把 slot 超时按快档（1.5–2.5s/次）定为 6s，
换到慢档（3–5s/次）后频繁触发，加上兜底当时"多指标一律拒绝"，
把本可答对的 5 题判成了失败（后修正为 12s + 允许多指标）。

**标签：** 阶段超时, 规则兜底, 跳过解读, 阈值随档位复核
