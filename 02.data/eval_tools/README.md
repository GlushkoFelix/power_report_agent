# 评测工具（端点健康门禁 + 20 题配对读数）

> 2026-10-19 归档。来源是工作区 `02.data/tmp/` 下的临时脚本，**已改成可移植版本**
> （路径全部从 `__file__` 推出，不再硬编码 `e:\power_report_agent`）。

## 为什么有这套东西

做「干净读数」时踩到一个坑：**上游端点会降级**，而 RAG/评测链路对此没有感知。

2026-10-19 上午实测：直连探测 4 次里 1 次 `502`，成功的那些"只回 4 个 token"却要 **9–38 秒**
（健康时 ≈1 秒）。20 题批次里直接出现 4 道 `E_LLM / 502 Bad Gateway`，而且**1.9–4.9 秒就快速失败**。
这种状态下跑出来的正确率反映的是**上游抖动**，不是模型能力 —— 拿它当成绩就是一纸假账。

所以加了这道门禁：**端点真的快起来了才开跑**。

## 文件

| 文件 | 用途 |
| --- | --- |
| `_endpoint_gate.py` | **主入口**。健康门禁 → 自动起 8003 → 跑 20 题真模型批次 → 验真 → 出报告。带"绝不重复花钱"护栏。 |
| `_run_watch.py` | 任一批次的实时进度；**打印 `distinct model_name` 做验真**（这是识破"静默 scripted"的唯一可靠手段）。 |
| `_cur20_r2_report.py` | 同题配对对照报告（`--base` / `--new` 换批次名）。 |
| `_abort_run_generic.py` | 把人工中止的"幽灵 running"批次标 `failed`，并核算该批 / 当天消耗。 |
| `_cur20_plan.json` | 20 题题单（分层抽样，已排除 T2 与复测用过的题）。 |
| `_cur20_r2_report.md` | 2026-10-19 的**实测结果**（19/20），数字随本目录一起走。 |

## 健康判据

连续 `--need 2` 轮 HTTP 200 **且** 单次 4-token 请求 ≤ `--max-latency 6` 秒。两条同时满足才算健康。

为什么不是"有 200 就行"：10-19 那天 26 轮探测里，200 其实不少，但多数耗时 13–36 秒，
只有 2 轮同时满足"200 且 ≤6 秒"—— 而真正跑成功的批次正是卡在那 2 轮之后。
放宽到"看到 200 就开跑"，就会再买一次假账。

## 用法

```powershell
# ① 只盯健康，不跑批次（0 花费，每次探测 ≈4 token）
python _endpoint_gate.py --interval 120 --max-wait 2

# ② 盯到健康就自动跑 20 题 + 验真 + 出报告
python _endpoint_gate.py --interval 120 --need 2 --max-latency 6 --max-wait 1.5 --launch --name cur20-20261019b

# ③ 看某批次进度与验真
python _run_watch.py --name cur20-20261019b --tail 5

# ④ 出配对报告（默认与 10-16 基线对比）
python _cur20_r2_report.py --base cur20-20261016 --new cur20-20261019b

# ⑤ 中止后清幽灵
python _abort_run_generic.py --run run_20261019_02 --reason "人工中止：上游降级"
```

## 防重复花钱的护栏（重点）

`--launch` 动手前**先查库**，按批次名判断：

| 已有状态 | 行为 |
| --- | --- |
| `running` / `pending` | 直接跳过（别人正在跑） |
| `finished` | 直接跳过（读数已拿到） |
| `failed` 次数 ≥ `--max-attempts`（默认 2） | 停止重试并提示人工介入 |

**这个护栏必须靠批次名生效**，所以：**不要拿"马上要跑的那个名字"去测护栏**。
10-19 我就是这么踩的 —— 拿 `cur20-20261019b` 去试，它本来没有历史批次，护栏不命中，
等于直接按了开跑键，白花 24,202 tokens。测护栏要用一个**必然命中**的名字（比如已 finished 的 `cur20-20261016`）。

## 已知坑（都是实测踩出来的）

1. **超时那次不落 `llm_calls`**。`model_name` 是 NOT NULL，超时没有回复对象，所以这一行根本不写。
   ⇒ 读 `llm_calls` 得到的 slot 调用次数**低于**实际发起次数，别拿它算超时率。
2. **`eval_runs.model_name` 不可信**。它写的是"发起时的 impl"，不是实际调用模型。
   验真只能看 `llm_calls.model_name` 的 `distinct` 里有没有 `scripted`。
3. **上游会返回多种模型别名**（`deepseek-v4-flash-0731` / `DeepSeek-V4-Flash-0731` /
   `deepseek-v4-flash-ga-260731` / `cb/deepseek-v4.1-flash`）。所以验真判据是"**不含 scripted**"，
   不能写成"必须等于某个名字"。
4. **进程被掐会留幽灵批次**。后端没有取消端点，任务随进程消失，`eval_runs` 会永远停在 `running`
   ⇒ 用 `_abort_run_generic.py` 手动收尸。
5. **不要把 20 题读数与 120 题全量成绩比**。题集与时段都不同；引用时四要素（配置 / 端点 / 提示词版本 / 时段）缺一不可。
